# B10 abrupt diagnostic contract

This contract defines the diagnostic-only B10 abrupt restart execution: its wire objects, state machine, fixed policy values and failure names. It is diagnostic-only and not active for scientific publication. ADR-021 in [the blueprint](../blueprint.md) owns the scientific rules; this page restates none of them.

On this page, PR1, PR2 and PR3 are the three pull requests of [issue 404](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404): PR1 recorded the design, PR2 adds this diagnostic execution, and PR3 is planned to add the verifier support. A decision named by a number is Hari's comment of that number on issue 404, linked where it appears.

For local file hand-offs and the supervisor-exit cleanup dependency, see the [implementation receipt](../../items/404/pr2-receipt.md#local-file-hand-offs-and-supervisor-exit).

During diagnostic collection, `b10_abrupt_first_termination_unknown` at boundary `successor_termination` means the successor pod could not be observed. The collection code reuses the termination-observation helper and retains `safety_stop`; the gap name alone does not identify which pod was unobservable. Read it together with the boundary in `b10_abrupt_diagnostics`. This explains the existing mapping without adding a failure name or changing its safety handling.

The supervisor polls its events pipe with a one millisecond idle delay. Acceptance must reach the supervisor before it sends STOP, so polling and scheduler delay can widen the acceptance-to-STOP interval in which a terminal report arrives. Local synthetic path measurements and their limits are recorded in the [receipt](../../items/404/pr2-receipt.md#measured-synthetic-acceptance-to-stop-path); they do not isolate the added timer delay or establish a latency bound. An empty selection cannot be attributed to service behavior independently of that scheduling effect. The stopped checkpoint drains available bytes directly under the existing arm deadline.

## Wire and state machine

Every wire object carries `schema_version: 2`, `dialect: "b10_abrupt"`, `purpose: "diagnostic_trial"`, `synthetic: true`, `scientific_admissible: false`, `kind`, and `identity`. Identity exact members: `run_id,scenario_id,configuration_id,phase,repeat,source_commit,image_reference,job_name,pod_name,pod_uid,instance_id,predecessor_instance_id`; predecessor is null for first instance and required for successor. Local owned-child observations add a separate `process` object, never a third producer identity. Process fields are `pid,parent_pid,boot_id,start_identity`; no caller-selected PID is accepted. Strings use the existing run/source/image/instance validation. UTC and monotonic observations are explicitly distinguished and never compared across boot/clock domains as if interchangeable.

Journal frame exact common members are `schema_version,dialect,purpose,synthetic,scientific_admissible,kind,identity,sequence,observed_utc,monotonic_ticks,clock_frequency,data`. Sequence is strictly increasing with no unexplained gap; Int64 values must be integral, finite, nonnegative and checked for arithmetic overflow. No duplicate JSON member, trailing content, unknown member/tag or schema coercion. `data` is a closed per-kind object:

- `prepared`: `attempt_id,invocation_ordinal,cohort,probe_id,key,sequence,payload_length,payload_sha256,predecessor_attempt_id`. Cohort is exactly timeout/same_instance/cross_restart. Probe `sequence` is the burst index from 0 to 4; a resend keeps its selected original's sequence. Only probe records use the journal's per-attempt stream; timeout inventory is separately sealed.
- `accepted`: `attempt_id,prepared_sequence`; appended after normal return from Produce, durably acknowledged by supervisor. A synchronous rejection has its own `synchronous_rejection` record with actual error and no accepted record.
- `synchronous_rejection`: `attempt_id,prepared_sequence,error_code,error_reason`; recorded when `Produce` throws.
- `terminal`: `attempt_id,completion_source,delivered,error_code,persistence_status`; only genuine reports populate it. Preserve callback-before-acceptance by joining attempt ID; do not discard a callback whose accepted frame is later. No-report attempts never acquire delivered, error or persistence values.
- `checkpoint`: `arm,accepted_attempt_ids,selected_attempt_ids,last_complete_sequence,pre_acceptance_report,process,checkpoint_utc,checkpoint_monotonic_ticks,release_utc`. `accepted_attempt_ids` contains exactly the five durably accepted burst originals in invocation order. `selected_attempt_ids` is their subset without a captured terminal report, in the same order. Report descriptor binds actual raw bytes and parsed identity/sequence/time. `pre_acceptance_report` has exact members `name,length,sha256,report_identity,report_sequence,report_capture_utc`: `name` is `abrupt-child/<arm>-pre-acceptance-report.json`, and the other members are copied, with the same JSON types and values, from that arm's verified `pre_acceptance_report` IPC message: `length` from `report_length`, `sha256` from `report_sha256`, and `report_identity`, `report_sequence` and `report_capture_utc` unchanged, each with the source, JSON type and bound that the wire section's `pre_acceptance_report` kind states. It is never null; without a verified message for the arm the checkpoint is not written. A checkpoint is a stable cut of complete available frames after stopped-state confirmation, not a claim about unobserved child buffers.
- `signal`: `arm,requested_signal,process,intent_sequence,request_utc,request_monotonic_ticks,return_value,errno`; intent is a separately flushed record before KILL. Request success is not observed exit.
- `exit`: `process,wait_for_exit_observed,observed_utc,monotonic_ticks,exit_code_local_observation,runtime_version`; status encoding is explicitly a local observation.
- `gap`: `reason,first_missing_sequence` (nullable), `capture_status`. Once a gap is latched, later complete records do not clear it. `reason` is one of `frame_oversize`, `queue_full`, `journal_bytes_exceeded`, `journal_entries_exceeded`, `writer_failed`, `malformed_frame`, `sequence_gap`.

IPC messages are not journal frames. Their exact members are `kind,sequence,data`, where `sequence` is the sender's strictly increasing counter from 1. Child-to-supervisor kinds: `hello` with `data` members `challenge,pid,start_time_ticks,boot_id` (the child reads `pid` from `Environment.ProcessId`, `start_time_ticks` from `/proc/self/stat`, and `boot_id` from `/proc/sys/kernel/random/boot_id`; the supervisor independently reads `/proc/<pid>/stat` and the same boot-ID file. Both parse stat fields after the last `)`, trimming ASCII spaces and ignoring empty tokens; field 3 is suffix index 0 and field 22 is index 19, in clock ticks, not wall-clock time), and `prepared`, `accepted`, `synchronous_rejection`, `terminal` and `capture_gap`, whose `data` equals the journal `data` of the same kind (`capture_gap` maps to `gap`), and `pre_acceptance_report`, which has no journal kind of its own. Its `data` members are exactly `arm,attempt_id,report_length,report_sha256,report_identity,report_sequence,report_capture_utc`. `arm` is `same_instance` or `cross_restart`; `attempt_id` is that arm's sequence-0 original; `report_length` is 1 to 1048576; `report_sha256` is the lowercase SHA-256 of the item-5 file; `report_identity`, `report_sequence` and `report_capture_utc` come from item 9's selected `KafkaStatisticsReport` (`src/Parchwell.Kafka/Statistics/KafkaStatisticsReport.cs:13-19`), as follows. `report_identity` is a JSON object with exact members `scenario_id,run_id,role,client_id`, copied from `KafkaStatisticsReport.Identity`, the `KafkaStatisticsIdentity` record (`KafkaStatisticsIdentity.cs:10-14`), not from `KafkaStatisticsSnapshot.Name` or `ClientId`. `scenario_id` and `run_id` are JSON strings that equal, by ordinal comparison, the supervisor's validated item-2 `ScenarioId` and `RunId`. `role` is the JSON string `"LoadGenProducer"`, written as that literal name and never as the enum's number; it is the only `KafkaClientRole` the existing sink accepts (`src/Parchwell.LoadGen/Run/Evidence/RunEvidenceSession.cs:580-584`). `client_id` is a JSON string of at least one character; the supervisor checks only that, because item 2 gives it no client identifier, and item 9's identity verification in the child covers its value. `report_sequence` is a JSON integer from 1 to 9223372036854775807. Its source is a new child-side counter in item 9's `Observe`: it starts at 0 and adds 1, with checked arithmetic, for every report `Observe` receives through the sink boundary, parsed or not, and the selected report carries the value assigned to it. Main has no statistics report sequence to reuse: `KafkaStatisticsReport` has none, and `RunEvidenceSession`'s `receipt_sequence` (`RunEvidenceSession.cs:45,229,266`) numbers only log and error captures. If the counter would overflow, `Observe` numbers no further report, so no later report can be selected and that arm's `accepted` raises `b10_abrupt_sample_missing`. `report_capture_utc` is the JSON string `KafkaStatisticsReport.ReceivedAt.ToString("O", CultureInfo.InvariantCulture)`, not the native `TimeSeconds`. `ReceivedAt` is set from `TimeProvider.GetUtcNow()` (`src/Parchwell.Kafka/Statistics/KafkaStatisticsSession.cs:105`), which returns a value "whose offset is Zero" ([TimeProvider.GetUtcNow](https://learn.microsoft.com/en-us/dotnet/api/system.timeprovider.getutcnow?view=net-10.0)). For `DateTimeOffset` values, "O" corresponds to the custom format string "yyyy'-'MM'-'dd'T'HH':'mm':'ss'.'fffffffzzz" ([Standard date and time format strings](https://learn.microsoft.com/en-us/dotnet/standard/base-types/standard-date-and-time-format-strings), "The round-trip ("O", "o") format specifier"), so the value is exactly 33 characters and ends `+00:00`. The supervisor requires exactly 33 characters, the suffix `+00:00`, and that `DateTimeOffset.ParseExact(value, "O", CultureInfo.InvariantCulture, DateTimeStyles.None)` succeeds and formats back under `"O"` to the same string. The message body is within the 65536-byte IPC limit and the auxiliary JSON depth 32. At most one is valid per arm, two per repeat. It must arrive after that arm's sequence-0 original `prepared` message and before its `accepted` message, so it precedes accepted durability, STOP and the checkpoint, inside the 30 s arm budget. A `pre_acceptance_report` that is duplicated, names an unknown arm or attempt, has a `report_length` outside 1 to 1048576, arrives out of that order, or whose file is missing, unreadable, over 1048576 bytes, or of a different length or SHA-256, or whose `report_identity`, `report_sequence` or `report_capture_utc` is outside the bound stated above, raises `b10_abrupt_report_binding_invalid`. An arm whose first burst `accepted` message arrives with no prior valid `pre_acceptance_report` raises the existing `b10_abrupt_sample_missing`. Per arm, these two names are exclusive, and the first one raised is that arm's only failure name. The supervisor evaluates that arm's `pre_acceptance_report` and `accepted` messages in IPC arrival order. Once either name is raised for an arm, a later `pre_acceptance_report` or `accepted` message for that arm raises neither name; every other handling of those messages is unchanged. So a report that arrives after `accepted` raises only `b10_abrupt_sample_missing`, raised at `accepted`. A duplicate or invalid report followed by `accepted` raises only `b10_abrupt_report_binding_invalid`. The supervisor sends no `ack` for it, because no journal record is written for it; its content enters the journal only in that arm's `checkpoint` frame. The only supervisor-to-child kind is `ack` with `data` member `acknowledged_sequence`, written only after the matching journal record and `FileStream.Flush(true)`. The supervisor, not the child, assigns journal `sequence`, `observed_utc` and `monotonic_ticks`.

Additional closed objects use the same envelope. `Selection` binds checkpoint descriptor, candidate IDs, terminal exclusions with terminal-record references, and final selected entries including logical identity, payload descriptor and original attempt ID. `CohortSeal` binds cohort, independent inventory/count, ledger descriptor, drain outcome, post-drain statistics descriptor, guard coverage and `fatal_capture_status`. `AbruptManifest` binds journal length/hash/entry count, both cohort seals, selection and sticky gap list. `TerminationReceipt` binds manifest, owned-child chain, before/after cgroup observations, EOF result and `mechanical_status` (`complete` or `incomplete`), with `fatal_capture_status="not_implemented_pr3"` and `native_tail="unknown_due_to_intended_kill"` only when its mechanical kill chain was observed. It has no normal-cleanup-success field. `SuccessorReceipt` binds first termination/selection, new pod identity, ready/release/invocation observations and actual completed ordinary artifacts/cleanup; it remains diagnostic. It is serialized as successor `completion.json` (item 11), written last, and binds successor `registration.json` and the five successor payloads by `{name,length,sha256}`. Arrays and descriptors are charged against the limits before allocation/read; hashes are lowercase SHA-256 of actual bytes.

"Authenticated" has PR1's exact scope: checked SHA-256 and byte-length binding to the accepted publication manifest/receipt plus exact run, configuration, repeat, source/image, instance and Job identity agreement. It is not signing, signer identity or protection against a writer able to replace both bytes and their bindings. The workflow also checks the receipt against observed Job/pod UID and immutable image before mounting it for the successor.

State sequence:

`disabled -> validated_diagnostic -> first_registered -> owned_child_started -> timeout_sealed -> (control_prepared -> control_accepted_durable) per member -> stopped_confirmed -> control_checkpoint -> continued -> control_resend_released -> control_sealed -> (kill_prepared -> kill_accepted_durable) per member -> stopped_confirmed -> kill_checkpoint -> kill_intent_durable -> kill_requested -> exit_observed -> eof_complete -> final_selection_sealed -> abrupt_publication_complete -> first_pod_terminated -> successor_registered_ready -> successor_released -> successor_completed`.

Every transition checks the preceding durable state and identity. Only the control returns to running after its checkpoint. Retain racing callbacks; selection may become empty. Stop confirmation precedes checkpoint. KILL cannot precede the nonempty durable kill checkpoint/intent. Post-death complete frames can remove originals from final selection, but cannot add a newly accepted original beyond the checkpoint. Retain selection history; no extra attempt repairs empty exposure. Final replay payload hashes must match their prepared originals; keys, sequence and payload stay equal, attempt/instance IDs change.

Timeout completes and seals before control; control completes and seals before kill. The first process/client must not be replaced between these cohorts. Timeout/control post-drain checks are cohort barriers, not a claim that the producer has been disposed. Implement their separate bounded sinks/seals in the new diagnostic runner; do not call the ordinary one-shot statistics/evidence Complete method and then silently reuse a closed sink for the next cohort. Keep continuous guard capture across cohort transitions. Fatal coverage beyond existing ordinary capture is explicitly unavailable until PR3.

## Policy

All numbers here are design/governance policy or existing configured limits, not measured capabilities. ADR-021 owns inherited scientific/protocol policy. No timing/exposure success is claimed. Hari's [decision 6710336610](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404#issuecomment-6710336610), points 1 and 2, settles the new mechanical choices (dispatch vehicle and release clock).

| Policy | Exact value/selection | Exhaustion or missing observation |
|---|---|---|
| IPC message body / queued frames / journal bytes / journal entries | 65536 bytes / 256 / 16777216 bytes / 4096 | `record the gap and continue` to diagnostics/cleanup only; sticky invalid capture, no usable selection/receipt |
| Auxiliary diagnostic JSON | 65536 bytes each; depth 32; descriptors/sequence entries bounded by 4096; journal total above applies separately | Same; reject before allocation; no truncated success |
| Timeout workload | Existing profile and LoadGen bounds, including MaxAttempts 186000, payload 900000, row 16384, manifest 67108864, ledger/readback 268435456 bytes | Same existing schedule/ledger failure; no probe admission from incomplete timeout seal |
| Raw reports/evidence | Existing MaxReportBytes 1048576, EvidenceQueueCapacity 2048, MaxEvidenceFileBytes 134217728, MaxBrokerSeries 64 | Sticky gap; no invented report, counter or coverage |
| Aggregate transfer | Existing MaxArtifactBytes 268435456 and MaxAggregateArtifactBytes 1073741824; create-only writes; each upload uses existing 30 s budget | Same; ambiguous/missing publication blocks successor |
| Local proc/cgroup reads | At most 65536 bytes per read; one bound owned target/cgroup; poll within arm/stop deadline, no unbounded directory discovery | Missing/oversize/changed identity invalidates mechanical check |
| Arm/stop | 30 s per arm, from arm request through stopped confirmation/checkpoint; smaller enclosing deadline wins | Same; no exposure retry |
| Kill / reap / EOF | 10 s each, separately recorded; smaller enclosing deadline wins | Same; unknown death/EOF blocks successor |
| Child failure-report grace at clean pre-kill EOF | 10 s total, 10 ms maximum polling delay, clipped by the enclosing deadline | `record the gap and continue` to `b10_abrupt_unexpected_exit`, failed diagnostics and existing mandatory cleanup only; natural exit skips cleanup KILL and never qualifies a termination receipt |
| Release | 120 s from each arm's checkpoint, not from exit, Job completion or download; control and successor both use that boundary | No early replay, no late substitute; missing readiness makes comparison incomplete. Clock basis ([decision 6710336610](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404#issuecomment-6710336610), point 2): release at the authenticated checkpoint UTC plus 120 s; retain source, runner and successor UTC and local monotonic observations; the cross-host timing conclusion is `not_verified` unless an independently checked clock-uncertainty bound establishes readiness at the boundary, and this repository has no such bound |
| Arm order | timeout, same_instance, cross_restart | Never reorder or select favorable arms |
| Keys/probe IDs | `B10/{run_id}/{configuration}/{repeat}/same_instance` and `B10/{run_id}/{configuration}/{repeat}/cross_restart`; invariant decimal repeat; sequence 0 to 4, the burst index | Exact identity required; disjoint from ordinary keys |
| Payload/pacing | Same deterministic configured shape for both arms; choose the first generated profile event as the probe payload template using existing generator/seed, replace only logical key/probe identity; original and resend use identical value bytes/hash | Mismatch invalidates; no runtime-selected size/pacing based on exposure |
| Checkpoint/kill/probes | One checkpoint per arm; one burst of 5 originals and one planned resend per arm; one selected original resent; one kill request per repeat; no replacement | `record the gap and continue` only to diagnostics/cleanup |
| Sample gate | Latest complete parsed report after construction and strictly before the arm's first burst acceptance, with sequence/time and raw binding; unchanged statistics interval | Missing sample blocks arm; never wait for a post-acceptance sample to qualify it |
| Guards | Expected brokers/settings/mandatory fields/stable identities/monotone counters; reject reset, nonzero txerrs/rxerrs, disallowed delivery error, error-level native callback and missing status on a genuine report | Block arm/seal; no relaxed guard after trial |
| OOM exclusion | Same memory cgroup, readable before/after local oom_kill, no reset/increment | Missing or competing evidence fails mechanical intended-kill chain; zero delta does not identify a victim |
| Outer execution | Existing LoadGen 900 s process lifetime, 1140 s Job deadline, 30 s termination grace; existing phase 18000 s orchestration cap; operation budgets clipped to remaining time | `record the gap and continue` to diagnostic collection/mandatory cleanup only; unknown target/pod sets safety_stop |
| Live trial | One C1 repeat, one trial dispatch, no automatic retry | `record the gap and continue` to diagnostics/cleanup only; second trial spends money, hand off to Hari |
| Future witnesses | PR3 (the planned verifier pull request) only: one deterministic checked pair witness per arm/repeat, lexicographic original/resend IDs then coordinates; count all pairs | `record the gap and continue` for excess witnesses without dropping counts; PR2 emits none |
| Dispositions | Per PR, 20 documentation-warning root causes, 20 verification-failure root causes, 20 review-finding root causes | `push -wip and hand off to the next session`; record measured count and remaining estimate with basis/date; unchanged-file doc warnings take the rule-8 blanket disposition |
| Cut computation | If later approved target work requires it: one computation plus one consolidated recomputation per target | `push -wip and hand off to the next session`; never reuse stale cuts |

The child failure-report grace is a mechanical policy choice under [decision 6724662091](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404#issuecomment-6724662091) and [approval 6724978056](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404#issuecomment-6724978056). The 10 s value equals the existing cleanup observation budget and applies only to clean event-stream EOF before a planned kill. The [fourth offline execution](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404#issuecomment-6724575310) measured about 3.07 s from event-stream EOF to natural-exit observation in L1, in a different environment; that single observer interval is context, not a live latency, measured requirement, upper bound or delivery guarantee. The unchanged 10 ms polling interval follows existing local polling granularity. An exited child returns immediately; otherwise the supervisor allows this bounded opportunity for the child's inherited stderr report before its existing cleanup. A smaller enclosing deadline wins. The grace neither authorizes successful termination nor changes the post-kill EOF gate, release, scientific eligibility, lifetime or Job deadlines. This decision authorizes this diagnostic-only grace, not a general amendment of the inherited adjustable-budget list below. Any later grace change requires Hari's recorded decision.

First-pod configured-stage worst-case sum (policy arithmetic, not measured runtime): `4 * 10 + 300 + (30 + 120 + 300) + (30 + 10 + 10 + 10) + 6 * 30 = 1030 s`. The terms are the synthetic timeout profile's four stage durations, timeout drain, control arm/release/drain, kill arm/kill/reap/EOF, and the six post-kill uploads used by the [lifetime calculation in the Revision 1 check](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404#issuecomment-6710268101). Script-read sources on main are `scenarios/profiles/b10-timeout.yaml:29-32`, `charts/parchwell/values.yaml:26,30,32,85`, and this table's unchanged mechanical budgets. The sum exceeds the 900 s process lifetime by 130 s and is below the 1140 s Job deadline by 110 s. This is the sum of listed configured budgets, not a measured duration or a guarantee that all other overhead fits. Smaller enclosing deadlines still win; exhaustion remains `b10_abrupt_deadline_exhausted`, `record the gap and continue` to diagnostics and mandatory cleanup only. No timeout or publication order is changed. Reproduce the arithmetic from repository root with this read-only script:

```python
from pathlib import Path
import yaml
v = yaml.safe_load(Path('charts/parchwell/values.yaml').read_text())
p = yaml.safe_load(Path('scenarios/profiles/b10-timeout.yaml').read_text())
def seconds(value):
    h, m, sec = map(int, value.split(':'))
    return h * 3600 + m * 60 + sec
loadgen = v['runtime']['bounds']['loadgen']
schedule = sum(stage['duration_seconds'] for stage in p['stages'])
drain = seconds(loadgen['ProducerDrainTimeout'])
upload = seconds(loadgen['UploadTimeout'])
lifetime = seconds(loadgen['ProcessLifetimeTimeout'])
job = v['runtime']['bounds']['execution']['loadgen_job_seconds']
# Unchanged ADR-021 policy; six uploads in the linked lifetime calculation.
arm, release, kill, reap, eof, uploads = 30, 120, 10, 10, 10, 6
worst = schedule + drain + (arm + release + drain) + (arm + kill + reap + eof) + uploads * upload
print(worst, worst - lifetime, job - worst)  # 1030 130 110
```

Cohort seals and guard/capture gates are policy too, not adjustable observations. After a failed trial only implementation bugs and mechanical arm/stop, kill/reap, release and journal ceilings may change, each by Hari's recorded decision before science and disclosed later. EOF is not silently added to that adjustable list. Queue/sample, cohort/control/eligibility, OOM exclusion, witness, verdict and expected-outcome policies are not tuned to the trial. Neither policy values nor an unmeasured success probability are reported as observations.

| `b10_abrupt_publication_ambiguous` | Write outcome unknown, or missing or duplicate object | Successor blocked; no overwrite |
| `b10_abrupt_first_termination_unknown` | Workflow cannot bind actual first-pod termination | `safety_stop`; successor blocked |
| `b10_abrupt_successor_binding_invalid` | Successor input missing or changed, or Job, pod UID, source, image, predecessor or selection mismatch, or same pod identity; detail one of `receipt_missing`, `receipt_changed`, `job_mismatch`, `pod_uid_reused`, `source_mismatch`, `image_mismatch`, `predecessor_mismatch`, `selection_stale` | Exit before producer construction |
| `b10_abrupt_successor_late` | Successor not ready at the release boundary | Comparison incomplete; no late resend |
| `b10_abrupt_deadline_exhausted` | An enclosing lifetime, Job or phase deadline leaves no budget | `record the gap and continue` to cleanup |

The closed configuration detail list is `Unclassified`, `MixedPrefix`, `SettingNameOrDuplicate`, `DiagnosticIdentity`, `RequiredIdentity`, `RunSourceOrImage`, `PodOrNamespace`, `JobName`, `BlobEndpoint`, `AbsolutePath`, `FixedPolicy`, `Role`, `Binding`, `ChildFields`, `ChildHandshake`, `ApphostProcessPathMismatch`, `ApphostMissing` (source: [B10AbruptHost.ReportFailure](../../src/Parchwell.LoadGen/Run/Abrupt/B10AbruptHost.cs) and [B10AbruptOptions.ValidationDetail](../../src/Parchwell.LoadGen/Run/Abrupt/B10AbruptOptions.cs)). The configuration detail list is unchanged.

Outcome labels, not failures: `mechanical_status` `complete` or `incomplete`; `fatal_capture_status` `not_implemented_pr3`; `native_tail` `unknown_due_to_intended_kill`; cross-host timing conclusion `not_verified`.

### Failure report observability

Exception type, throw site, facts, exception chain and timeline are diagnostic metadata, not proof of the failed operation or its cause. Clean event-stream EOF does not establish natural child death. The host records `exception.GetType().FullName`, falling back to `Name`, without copying exception messages, stack text, paths, credentials or arbitrary exception data into its failure report. The classifier in [B10AbruptSupervisor.FailureName](../../src/Parchwell.LoadGen/Run/Abrupt/B10AbruptSupervisor.cs) owns the emitted closed-name mapping; unknown exceptions map to the existing `b10_abrupt_capture_gap`, including local `/work` write errors. Explicit configuration failures keep only the closed validation detail. The host does not accept an arbitrary `b10_abrupt_` prefix as a failure label.

Plain stderr is `<closed_failure_name> exception_type=<CLR type> diagnostic=<JSON>` with a newline. Configuration failures instead use `b10_abrupt_configuration_invalid validation_detail=<name> exception_type=<CLR type> diagnostic=<JSON>`. Only the exact literal `kill_too_late:no_unconfirmed_attempt` retains that detail; other exception-message suffixes are not copied. Cancellation retains `b10_abrupt_deadline_exhausted` and its actual exception type. `<JSON>` is one compact JSON object with the members of the diagnostic object below.

[B10AbruptHost.ReportFailure](../../src/Parchwell.LoadGen/Run/Abrupt/B10AbruptHost.cs) emits startup-failure JSON with exact members `failure,exception_type,diagnostic,cleanup_failure,cleanup_exception_type,cleanup_diagnostic,cleanup_signal_observation`; absent cleanup values are null. Signal-failure JSON has exact members `failure,exception_type,diagnostic,signal_observation`. Failure labels are classified closed literals, and type fields identify the actual wrapper or cleanup exception. Actual signal return values, errno and native-import type observations retain their nulls; no exception object is serialized.

The supervisor protects child startup with its diagnostic try/catch. Its `failed_diagnostic` data has exact members `mechanical_status,failure,exception_type,diagnostic,process,kill_requested,has_exited,capture_gaps,arm_failures,fatal_capture_status,signal_observation,cleanup,startup_cleanup,timeline`. When startup returns no process, `process` and `has_exited` are null and `kill_requested` is false. `cleanup` is null unless the supervisor aborted a returned child; then its exact members are `arm,failure,signal_observation,capture_failure,failure_diagnostic,capture_diagnostic`. `failure_diagnostic` describes the exception behind `failure`, and `capture_diagnostic` the exception behind `capture_failure`; each is null when no exception was caught. `startup_cleanup` is null except for a startup wrapper, where its exact members `failure,exception_type,diagnostic,signal_observation` describe the startup cleanup failure, or are all null if cleanup had no failure. Startup cleanup is not repeated. Stderr is written before the bounded create-only `abrupt/failure.json` attempt; a local write failure latches the existing writer gap without replacing the original cause.

A diagnostic object has exact members `exception_chain,detail,inner_detail,reduced`. `exception_chain` has members `entries,truncated`, and each entry has members `exception_type,thrower_type,thrower_method`: the exception's CLR type name, and the declaring type full name and method name of its `TargetSite`, both null when `TargetSite` is null. Entries start at the reported exception and follow `InnerException` only, at most 8; `truncated` is true when more exist. `AggregateException.InnerExceptions` is not walked. `detail` is the throw site of the first exception in that walk that carries one, and `inner_detail` the next; each is null when absent. A throw site has members `file,member,line,facts`: the source file name without directory, and the member name and line from the compiler's caller information. A site is interpreted against the `source_commit` of the same report. `reduced` is true when `exception_chain` was omitted for size.

A fact is a closed snake_case name and a 64-bit integer: a count, whole milliseconds, `1` or `0` for a boolean, raw monotonic timestamp ticks, or a closed code. Arm and cohort codes are `timeout=0`, `same_instance=1`, `cross_restart=2`, `cleanup=3` and `-1` otherwise. Gap-reason codes are positions in `frame_oversize, queue_full, journal_bytes_exceeded, journal_entries_exceeded, writer_failed, malformed_frame, sequence_gap`, and successor-detail codes positions in `receipt_missing, receipt_changed, job_mismatch, pod_uid_reused, source_mismatch, image_mismatch, predecessor_mismatch, selection_stale`; both are `-1` otherwise. Error codes and persistence statuses are the numbers already on the wire, `-1` when absent. A compound check records its operands in source order and stops at the first false one, so the last fact is the failed check. A fact after the first false check is never recorded.

`failed_diagnostic.timeline` has exact members `role,start_utc,origin_ticks,timestamp_frequency,entries,dropped,omitted_for_size`. `origin_ticks` is the monotonic timestamp when the timeline started, and `timestamp_frequency` its ticks per second. `start_utc` is a local wall-clock observation. Each entry has members `stage,elapsed_ms,ticks,facts`: a closed stage name, whole milliseconds since `origin_ticks`, the raw monotonic timestamp and up to 8 facts. Raw ticks from two processes are comparable only when both read the same clock; one scratch observation on 2026-11-09 found .NET timestamps equal to Linux `CLOCK_MONOTONIC` nanoseconds, and that is not a documented guarantee. Each entry is also written to stderr as `b10_abrupt_stage <JSON>` with members `role,stage,elapsed_ms,ticks,facts`. The supervisor holds its stage lines in memory and writes them only when it records `checkpoint_written`, `publication_complete` or `abort_complete`, so it adds no stderr write while the child runs. It records `ack_sent` in memory right after it writes the `accepted` acknowledgement for member 0 or a resend; the entry's `ticks` is the acknowledgement time on the supervisor's clock. Supervisor stages are `supervisor_registered, child_started, frame_prepared, frame_report, frame_accepted, ack_sent, frame_terminal, seal_loaded, stop_requested, stop_confirmed, checkpoint_written, resume_requested, resume_confirmed, kill_intent, kill_requested, exit_observed, eof_complete, selection_finalized, publication_complete, event_stream_ended, grace_ended, failure_observed, abort_complete`.

For burst originals, the supervisor records `frame_prepared`, `frame_accepted`, `ack_sent` and `frame_terminal` stages only for member 0; it also records those stages for resends. The other members' timing is retained in the burst line below.

The child keeps its own timeline with role `child`, `successor` for the successor, and writes each line when it is recorded, except that it holds `probe_produced` and `probe_report_selected` until its next written line; a held line is lost if the child is killed first. It writes `probe_terminal` from its event writer after the terminal frame, or after a probe cohort drain, never from the delivery callback, whose only diagnostic action is to record a timestamp. Child stages are `producer_constructed, timeout_schedule_complete, timeout_drained, post_drain_report, cohort_sealed, probe_prepared, probe_produced, probe_report_selected, probe_accepted, probe_terminal, release_read, release_reached, cohort_drained, successor_ready`.

The child records `probe_prepared`, `probe_produced`, `probe_report_selected`, `probe_accepted` and `probe_terminal` only for member 0 and resends. After the control drain it writes one `b10_abrupt_burst <JSON>` line with this exact shape:

```json
{"role":"child","arm":1,"members":[{"burst_index":0,"produce_ticks":0,"callback_ticks":-1,"terminal_written_ticks":-1}]}
```

The example uses illustrative ticks, not measurements. Each member's `produce_ticks` is the timestamp at its Produce invocation; `callback_ticks` is the timestamp recorded by its delivery callback, or -1 when none was captured. `terminal_written_ticks` is the timestamp taken in `MarkTerminals` after the event writer writes that member's terminal frame, or -1 when it was not written. The kill arm's child line is lost by design.

At `checkpoint_written`, the supervisor writes one `b10_abrupt_burst <JSON>` line for the arm with its held stage lines. Its exact shape is:

```json
{"role":"supervisor","arm":1,"stop_request_ticks":0,"members":[{"burst_index":0,"prepared_ticks":0,"accepted_ticks":0,"ack_sent_ticks":-1,"terminal_ticks":-1,"terminal_before_stop":0}]}
```

The example uses illustrative ticks, not measurements; `arm` uses the arm codes above. `prepared_ticks` is taken after the prepared flush. `accepted_ticks` is taken before the accepted append, at the same instant as the supervisor's accepted-time observation. `ack_sent_ticks` is taken after the acknowledgement write returns, or is -1 when no acknowledgement was sent. `terminal_ticks` is taken after the terminal append, or is -1 when absent. `stop_request_ticks` is the supervisor's timestamp immediately before `Stop()`. `terminal_before_stop` is 1 exactly when `terminal_ticks` is not -1 and is less than `stop_request_ticks`, otherwise 0. All ticks use the emitting process's clock; the timeline's `timestamp_frequency` gives its ticks per second, subject to the cross-process clock limitation above.

Each line contains at most 5 members in invocation order, with `burst_index` from 0 to 4, and only integer values except the closed `role` string. It carries no attempt IDs, keys or payloads. If more than 5 members are supplied, record the gap and continue by omitting the line. The supervisor holds its burst line until it writes held stage lines, with no added stderr write while the child runs. Member 4's `accepted_ticks` to `ack_sent_ticks` separates its accepted append and acknowledgement from the `ack_sent_ticks` to `stop_request_ticks` gap that the first burst trial measures under [decision 6740552975](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404#issuecomment-6740552975). The existing durable-acceptance and stop order is unchanged.

Diagnostic output contains only closed failure, stage, fact, burst field and code names, CLR type and method names, source file and member names, integers and `start_utc`. It never contains exception messages, stack text, `Exception.Data`, payloads, keys, attempt IDs, paths, credentials or configuration values. Throw sites are kept outside the exception object, so exception types, messages and failure names are unchanged.

Policy caps, not measurements: 8 chain entries, 16 facts per site, 8 facts per timeline entry and 48 timeline entries per process. Exhaustion action for each cap: `record the gap and continue`. Extra facts are dropped and the first kept; extra timeline entries increment `dropped` and are neither kept nor written; a longer chain sets `truncated`. If `failed_diagnostic` exceeds 65536 bytes, it is rebuilt with timeline entries omitted and `omitted_for_size` true, then also with every diagnostic object in it reduced. If it still exceeds 65536 bytes, no report is written and the existing writer gap latches. A plain-line, startup-JSON or signal-JSON diagnostic object above 65536 UTF-8 bytes is replaced by its reduced form.

Each `b10_abrupt_diagnostics` entry in the phase status has exact members `reason,boundary,exception_type,validation_detail,site,cause_type`. `site` has exact members `file,function,line,origin_file,origin_function,origin_line`. `file`, `function` and `line` name the innermost frame of `b10_abrupt.py` in the traceback of the recorded exception, or of its cause when a caught exception is converted to a named failure; for an exception that was never raised they name the calling frame. The `origin_` members name the innermost frame of the whole traceback and are null without one. `cause_type` is the class name of the converted exception, or null. File names carry no directory, and sites are interpreted against the `source_commit` in `phase.json`. `reason`, `boundary`, `exception_type` and `validation_detail` keep their existing meaning.

These changes affect local failure diagnostics, not IPC, journal or successful artifact members. The child continues to use inherited stderr without added redirection or parsing. EOF grace observes process exit, not receipt of a failure line; it cannot guarantee delivery or let SIGKILL print an error. Other libraries' logging is outside this report contract. A clean pre-kill EOF remains an incomplete failure after natural exit or grace exhaustion, and never authorizes a selection, termination receipt or successor. Diagnostic metadata never authorizes a selection, seal, termination receipt, successor or scientific admission.
