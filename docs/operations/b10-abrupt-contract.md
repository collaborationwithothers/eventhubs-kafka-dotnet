# B10 abrupt diagnostic contract

This contract defines the diagnostic-only B10 abrupt restart execution: its wire objects, state machine, fixed policy values and failure names. It is diagnostic-only and not active for scientific publication. ADR-021 in [the blueprint](../blueprint.md) owns the scientific rules; this page restates none of them.

On this page, PR1, PR2 and PR3 are the three pull requests of [issue 404](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404): PR1 recorded the design, PR2 adds this diagnostic execution, and PR3 is planned to add the verifier support. A decision named by a number is Hari's comment of that number on issue 404, linked where it appears.

## Wire and state machine

Every wire object carries `schema_version: 2`, `dialect: "b10_abrupt"`, `purpose: "diagnostic_trial"`, `synthetic: true`, `scientific_admissible: false`, `kind`, and `identity`. Identity exact members: `run_id,scenario_id,configuration_id,phase,repeat,source_commit,image_reference,job_name,pod_name,pod_uid,instance_id,predecessor_instance_id`; predecessor is null for first instance and required for successor. Local owned-child observations add a separate `process` object, never a third producer identity. Process fields are `pid,parent_pid,boot_id,start_identity`; no caller-selected PID is accepted. Strings use the existing run/source/image/instance validation. UTC and monotonic observations are explicitly distinguished and never compared across boot/clock domains as if interchangeable.

Journal frame exact common members are `schema_version,dialect,purpose,synthetic,scientific_admissible,kind,identity,sequence,observed_utc,monotonic_ticks,clock_frequency,data`. Sequence is strictly increasing with no unexplained gap; Int64 values must be integral, finite, nonnegative and checked for arithmetic overflow. No duplicate JSON member, trailing content, unknown member/tag or schema coercion. `data` is a closed per-kind object:

- `prepared`: `attempt_id,invocation_ordinal,cohort,probe_id,key,sequence,payload_length,payload_sha256,predecessor_attempt_id`. Cohort is exactly timeout/same_instance/cross_restart. Only probe records use the journal's per-attempt stream; timeout inventory is separately sealed.
- `accepted`: `attempt_id,prepared_sequence`; appended after normal return from Produce, durably acknowledged by supervisor. A synchronous rejection has its own `synchronous_rejection` record with actual error and no accepted record.
- `synchronous_rejection`: `attempt_id,prepared_sequence,error_code,error_reason`; recorded when `Produce` throws.
- `terminal`: `attempt_id,completion_source,delivered,error_code,persistence_status`; only genuine reports populate it. Preserve callback-before-acceptance by joining attempt ID; do not discard a callback whose accepted frame is later. No-report attempts never acquire delivered, error or persistence values.
- `checkpoint`: `arm,accepted_attempt_ids,selected_attempt_ids,last_complete_sequence,pre_acceptance_report,process,checkpoint_utc,checkpoint_monotonic_ticks,release_utc`. Report descriptor binds actual raw bytes and parsed identity/sequence/time. `pre_acceptance_report` has exact members `name,length,sha256,report_identity,report_sequence,report_capture_utc`: `name` is `abrupt-child/<arm>-pre-acceptance-report.json`, and the other members are copied, with the same JSON types and values, from that arm's verified `pre_acceptance_report` IPC message: `length` from `report_length`, `sha256` from `report_sha256`, and `report_identity`, `report_sequence` and `report_capture_utc` unchanged, each with the source, JSON type and bound that the wire section's `pre_acceptance_report` kind states. It is never null; without a verified message for the arm the checkpoint is not written. A checkpoint is a stable cut of complete available frames after stopped-state confirmation, not a claim about unobserved child buffers.
- `signal`: `arm,requested_signal,process,intent_sequence,request_utc,request_monotonic_ticks,return_value,errno`; intent is a separately flushed record before KILL. Request success is not observed exit.
- `exit`: `process,wait_for_exit_observed,observed_utc,monotonic_ticks,exit_code_local_observation,runtime_version`; status encoding is explicitly a local observation.
- `gap`: `reason,first_missing_sequence` (nullable), `capture_status`. Once a gap is latched, later complete records do not clear it. `reason` is one of `frame_oversize`, `queue_full`, `journal_bytes_exceeded`, `journal_entries_exceeded`, `writer_failed`, `malformed_frame`, `sequence_gap`.

IPC messages are not journal frames. Their exact members are `kind,sequence,data`, where `sequence` is the sender's strictly increasing counter from 1. Child-to-supervisor kinds: `hello` with `data` members `challenge,pid,start_time_ticks,boot_id` (the child reads `pid` from `Environment.ProcessId`, `start_time_ticks` from `/proc/self/stat`, and `boot_id` from `/proc/sys/kernel/random/boot_id`; the supervisor independently reads `/proc/<pid>/stat` and the same boot-ID file. Both parse stat fields after the last `)`, trimming ASCII spaces and ignoring empty tokens; field 3 is suffix index 0 and field 22 is index 19, in clock ticks, not wall-clock time), and `prepared`, `accepted`, `synchronous_rejection`, `terminal` and `capture_gap`, whose `data` equals the journal `data` of the same kind (`capture_gap` maps to `gap`), and `pre_acceptance_report`, which has no journal kind of its own. Its `data` members are exactly `arm,attempt_id,report_length,report_sha256,report_identity,report_sequence,report_capture_utc`. `arm` is `same_instance` or `cross_restart`; `attempt_id` is that arm's original; `report_length` is 1 to 1048576; `report_sha256` is the lowercase SHA-256 of the item-5 file; `report_identity`, `report_sequence` and `report_capture_utc` come from item 9's selected `KafkaStatisticsReport` (`src/Parchwell.Kafka/Statistics/KafkaStatisticsReport.cs:13-19`), as follows. `report_identity` is a JSON object with exact members `scenario_id,run_id,role,client_id`, copied from `KafkaStatisticsReport.Identity`, the `KafkaStatisticsIdentity` record (`KafkaStatisticsIdentity.cs:10-14`), not from `KafkaStatisticsSnapshot.Name` or `ClientId`. `scenario_id` and `run_id` are JSON strings that equal, by ordinal comparison, the supervisor's validated item-2 `ScenarioId` and `RunId`. `role` is the JSON string `"LoadGenProducer"`, written as that literal name and never as the enum's number; it is the only `KafkaClientRole` the existing sink accepts (`src/Parchwell.LoadGen/Run/Evidence/RunEvidenceSession.cs:580-584`). `client_id` is a JSON string of at least one character; the supervisor checks only that, because item 2 gives it no client identifier, and item 9's identity verification in the child covers its value. `report_sequence` is a JSON integer from 1 to 9223372036854775807. Its source is a new child-side counter in item 9's `Observe`: it starts at 0 and adds 1, with checked arithmetic, for every report `Observe` receives through the sink boundary, parsed or not, and the selected report carries the value assigned to it. Main has no statistics report sequence to reuse: `KafkaStatisticsReport` has none, and `RunEvidenceSession`'s `receipt_sequence` (`RunEvidenceSession.cs:45,229,266`) numbers only log and error captures. If the counter would overflow, `Observe` numbers no further report, so no later report can be selected and that arm's `accepted` raises `b10_abrupt_sample_missing`. `report_capture_utc` is the JSON string `KafkaStatisticsReport.ReceivedAt.ToString("O", CultureInfo.InvariantCulture)`, not the native `TimeSeconds`. `ReceivedAt` is set from `TimeProvider.GetUtcNow()` (`src/Parchwell.Kafka/Statistics/KafkaStatisticsSession.cs:105`), which returns a value "whose offset is Zero" ([TimeProvider.GetUtcNow](https://learn.microsoft.com/en-us/dotnet/api/system.timeprovider.getutcnow?view=net-10.0)). For `DateTimeOffset` values, "O" corresponds to the custom format string "yyyy'-'MM'-'dd'T'HH':'mm':'ss'.'fffffffzzz" ([Standard date and time format strings](https://learn.microsoft.com/en-us/dotnet/standard/base-types/standard-date-and-time-format-strings), "The round-trip ("O", "o") format specifier"), so the value is exactly 33 characters and ends `+00:00`. The supervisor requires exactly 33 characters, the suffix `+00:00`, and that `DateTimeOffset.ParseExact(value, "O", CultureInfo.InvariantCulture, DateTimeStyles.None)` succeeds and formats back under `"O"` to the same string. The message body is within the 65536-byte IPC limit and the auxiliary JSON depth 32. At most one is valid per arm, two per repeat. It must arrive after that arm's original `prepared` message and before its `accepted` message, so it precedes accepted durability, STOP and the checkpoint, inside the 30 s arm budget. A `pre_acceptance_report` that is duplicated, names an unknown arm or attempt, has a `report_length` outside 1 to 1048576, arrives out of that order, or whose file is missing, unreadable, over 1048576 bytes, or of a different length or SHA-256, or whose `report_identity`, `report_sequence` or `report_capture_utc` is outside the bound stated above, raises `b10_abrupt_report_binding_invalid`. An arm whose `accepted` message arrives with no prior valid `pre_acceptance_report` raises the existing `b10_abrupt_sample_missing`. Per arm, these two names are exclusive, and the first one raised is that arm's only failure name. The supervisor evaluates that arm's `pre_acceptance_report` and `accepted` messages in IPC arrival order. Once either name is raised for an arm, a later `pre_acceptance_report` or `accepted` message for that arm raises neither name; every other handling of those messages is unchanged. So a report that arrives after `accepted` raises only `b10_abrupt_sample_missing`, raised at `accepted`. A duplicate or invalid report followed by `accepted` raises only `b10_abrupt_report_binding_invalid`. The supervisor sends no `ack` for it, because no journal record is written for it; its content enters the journal only in that arm's `checkpoint` frame. The only supervisor-to-child kind is `ack` with `data` member `acknowledged_sequence`, written only after the matching journal record and `FileStream.Flush(true)`. The supervisor, not the child, assigns journal `sequence`, `observed_utc` and `monotonic_ticks`.

Additional closed objects use the same envelope. `Selection` binds checkpoint descriptor, candidate IDs, terminal exclusions with terminal-record references, and final selected entries including logical identity, payload descriptor and original attempt ID. `CohortSeal` binds cohort, independent inventory/count, ledger descriptor, drain outcome, post-drain statistics descriptor, guard coverage and `fatal_capture_status`. `AbruptManifest` binds journal length/hash/entry count, both cohort seals, selection and sticky gap list. `TerminationReceipt` binds manifest, owned-child chain, before/after cgroup observations, EOF result and `mechanical_status` (`complete` or `incomplete`), with `fatal_capture_status="not_implemented_pr3"` and `native_tail="unknown_due_to_intended_kill"` only when its mechanical kill chain was observed. It has no normal-cleanup-success field. `SuccessorReceipt` binds first termination/selection, new pod identity, ready/release/invocation observations and actual completed ordinary artifacts/cleanup; it remains diagnostic. It is serialized as successor `completion.json` (item 11), written last, and binds successor `registration.json` and the five successor payloads by `{name,length,sha256}`. Arrays and descriptors are charged against the limits before allocation/read; hashes are lowercase SHA-256 of actual bytes.

"Authenticated" has PR1's exact scope: checked SHA-256 and byte-length binding to the accepted publication manifest/receipt plus exact run, configuration, repeat, source/image, instance and Job identity agreement. It is not signing, signer identity or protection against a writer able to replace both bytes and their bindings. The workflow also checks the receipt against observed Job/pod UID and immutable image before mounting it for the successor.

State sequence:

`disabled -> validated_diagnostic -> first_registered -> owned_child_started -> timeout_sealed -> control_prepared -> control_accepted_durable -> stopped_confirmed -> control_checkpoint -> continued -> control_resend_released -> control_sealed -> kill_prepared -> kill_accepted_durable -> stopped_confirmed -> kill_checkpoint -> kill_intent_durable -> kill_requested -> exit_observed -> eof_complete -> final_selection_sealed -> abrupt_publication_complete -> first_pod_terminated -> successor_registered_ready -> successor_released -> successor_completed`.

Every transition checks the preceding durable state and identity. Only the control returns to running after its checkpoint. Retain racing callbacks; selection may become empty. Stop confirmation precedes checkpoint. KILL cannot precede the nonempty durable kill checkpoint/intent. Post-death complete frames can remove originals from final selection, but cannot add a newly accepted original beyond the checkpoint. Retain selection history; no extra attempt repairs empty exposure. Final replay payload hashes must match their prepared originals; keys, sequence and payload stay equal, attempt/instance IDs change.

Timeout completes and seals before control; control completes and seals before kill. The first process/client must not be replaced between these cohorts. Timeout/control post-drain checks are cohort barriers, not a claim that the producer has been disposed. Implement their separate bounded sinks/seals in the new diagnostic runner; do not call the ordinary one-shot statistics/evidence Complete method and then silently reuse a closed sink for the next cohort. Keep continuous guard capture across cohort transitions. Fatal coverage beyond existing ordinary capture is explicitly unavailable until PR3.

## Policy

All numbers here are design/governance policy or existing configured limits, not measured capabilities. ADR-021 owns inherited scientific/protocol policy. No timing/exposure success is claimed. Hari's [decision 6710336610](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404#issuecomment-6710336610), points 1 and 2, settles the new mechanical choices (dispatch vehicle and release clock).

| Policy | Exact value/selection | Exhaustion or missing observation |
|---|---|---|
| IPC message body / queued frames / journal bytes / journal entries | 65536 bytes / 256 / 16777216 bytes / 4096 | `record the gap and continue` to diagnostics/cleanup only; sticky invalid capture, no usable selection/receipt |
| Auxiliary diagnostic JSON | 65536 bytes each; depth 32; descriptors/sequence entries bounded by 4096; journal total above applies separately | Same; reject before allocation; no truncated success |
| Timeout workload | Existing profile and LoadGen bounds, including MaxAttempts 186000, payload 900000, row 16384, manifest 67108864, ledger/readback 268435456 bytes | Same existing schedule/ledger failure; no probe admission from incomplete timeout seal |
| Raw reports/evidence | Existing MaxReportBytes 1048576, EvidenceQueueCapacity 2048, MaxEvidenceFileBytes 134217728, MaxBrokerSeries 64 | Sticky gap; no invented report, counter or coverage |
| Aggregate transfer | Existing MaxArtifactBytes 268435456 and MaxAggregateArtifactBytes 1073741824; create-only writes; each upload uses existing 30 s budget | Same; ambiguous/missing publication blocks successor |
| Local proc/cgroup reads | At most 65536 bytes per read; one bound owned target/cgroup; poll within arm/stop deadline, no unbounded directory discovery | Missing/oversize/changed identity invalidates mechanical check |
| Arm/stop | 30 s per arm, from arm request through stopped confirmation/checkpoint; smaller enclosing deadline wins | Same; no exposure retry |
| Kill / reap / EOF | 10 s each, separately recorded; smaller enclosing deadline wins | Same; unknown death/EOF blocks successor |
| Release | 120 s from each arm's checkpoint, not from exit, Job completion or download; control and successor both use that boundary | No early replay, no late substitute; missing readiness makes comparison incomplete. Clock basis ([decision 6710336610](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404#issuecomment-6710336610), point 2): release at the authenticated checkpoint UTC plus 120 s; retain source, runner and successor UTC and local monotonic observations; the cross-host timing conclusion is `not_verified` unless an independently checked clock-uncertainty bound establishes readiness at the boundary, and this repository has no such bound |
| Arm order | timeout, same_instance, cross_restart | Never reorder or select favorable arms |
| Keys/probe IDs | `B10/{run_id}/{configuration}/{repeat}/same_instance` and `B10/{run_id}/{configuration}/{repeat}/cross_restart`; invariant decimal repeat; sequence 0 | Exact identity required; disjoint from ordinary keys |
| Payload/pacing | Same deterministic configured shape for both arms; choose the first generated profile event as the probe payload template using existing generator/seed, replace only logical key/probe identity; original and resend use identical value bytes/hash | Mismatch invalidates; no runtime-selected size/pacing based on exposure |
| Checkpoint/kill/probes | One checkpoint per arm; one original and one planned resend per arm; one kill request per repeat; no replacement | `record the gap and continue` only to diagnostics/cleanup |
| Sample gate | Latest complete parsed report after construction and strictly before acceptance, with sequence/time and raw binding; unchanged statistics interval | Missing sample blocks arm; never wait for a post-acceptance sample to qualify it |
| Guards | Expected brokers/settings/mandatory fields/stable identities/monotone counters; reject reset, nonzero txerrs/rxerrs, disallowed delivery error, error-level native callback and missing status on a genuine report | Block arm/seal; no relaxed guard after trial |
| OOM exclusion | Same memory cgroup, readable before/after local oom_kill, no reset/increment | Missing or competing evidence fails mechanical intended-kill chain; zero delta does not identify a victim |
| Outer execution | Existing LoadGen 900 s process lifetime, 1140 s Job deadline, 30 s termination grace; existing phase 18000 s orchestration cap; operation budgets clipped to remaining time | `record the gap and continue` to diagnostic collection/mandatory cleanup only; unknown target/pod sets safety_stop |
| Live trial | One C1 repeat, one trial dispatch, no automatic retry | `record the gap and continue` to diagnostics/cleanup only; second trial spends money, hand off to Hari |
| Future witnesses | PR3 (the planned verifier pull request) only: one deterministic checked pair witness per arm/repeat, lexicographic original/resend IDs then coordinates; count all pairs | `record the gap and continue` for excess witnesses without dropping counts; PR2 emits none |
| Dispositions | Per PR, 20 documentation-warning root causes, 20 verification-failure root causes, 20 review-finding root causes | `push -wip and hand off to the next session`; record measured count and remaining estimate with basis/date; unchanged-file doc warnings take the rule-8 blanket disposition |
| Cut computation | If later approved target work requires it: one computation plus one consolidated recomputation per target | `push -wip and hand off to the next session`; never reuse stale cuts |

First-pod configured-stage worst-case sum (policy arithmetic, not measured runtime): `4 * 10 + 300 + (30 + 120 + 300) + (30 + 10 + 10 + 10) + 6 * 30 = 1030 s`. The terms are the synthetic timeout profile's four stage durations, timeout drain, control arm/release/drain, kill arm/kill/reap/EOF, and the six post-kill uploads used by the [lifetime calculation in the Revision 1 check](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/404#issuecomment-6710268101). Script-read sources on main are `scenarios/profiles/b10-timeout.yaml:29-32`, `charts/parchwell/values.yaml:26,30,32,85`, and this table's unchanged mechanical budgets. The sum exceeds the 900 s process lifetime by 130 s and is below the 1140 s Job deadline by 110 s. This is the sum of listed configured budgets, not a measured duration or a guarantee that all other overhead fits. Smaller enclosing deadlines still win; exhaustion remains `b10_abrupt_deadline_exhausted`, `record the gap and continue` to diagnostics and mandatory cleanup only. No timeout or publication order is changed. Reproduce the arithmetic from repository root with this read-only script:

```python
from pathlib import Path
import yaml
v = yaml.safe_load(Path('charts/parchwell/values.yaml').read_text())
p = yaml.safe_load(Path('scenarios/profiles/b10-timeout.yaml').read_text())
def seconds(value):
    h, m, sec = map(int, value.split(':'))
    return h * 3600 + m * 60 + sec
loadgen = v['runtime']['bounds']['loadgen']
schedule = sum(stage['duration_seconds'] for stage in p['stages'])
drain = seconds(loadgen['ProducerDrainTimeout'])
upload = seconds(loadgen['UploadTimeout'])
lifetime = seconds(loadgen['ProcessLifetimeTimeout'])
job = v['runtime']['bounds']['execution']['loadgen_job_seconds']
# Unchanged ADR-021 policy; six uploads in the linked lifetime calculation.
arm, release, kill, reap, eof, uploads = 30, 120, 10, 10, 10, 6
worst = schedule + drain + (arm + release + drain) + (arm + kill + reap + eof) + uploads * upload
print(worst, worst - lifetime, job - worst)  # 1030 130 110
```

Cohort seals and guard/capture gates are policy too, not adjustable observations. After a failed trial only implementation bugs and mechanical arm/stop, kill/reap, release and journal ceilings may change, each by Hari's recorded decision before science and disclosed later. EOF is not silently added to that adjustable list. Queue/sample, cohort/control/eligibility, OOM exclusion, witness, verdict and expected-outcome policies are not tuned to the trial. Neither policy values nor an unmeasured success probability are reported as observations.

## Failure and outcome names

These literal strings are the only failure and outcome names PR2 emits. Tests assert them exactly. Each failure stops the step named, preserves diagnostics and continues only to cleanup and collection.

| Name | Raised when | Effect |
|---|---|---|
| `b10_abrupt_diagnostic_not_scientific` | Any ordinary phase, verify, judge or candidate command, or the ordinary host, meets a diagnostic phase, flag or marker | Nonzero exit, `full_allowed=false`, no candidate |
| `b10_abrupt_configuration_invalid` | Diagnostic options, role, identity, child handles, challenge or apphost path fail validation | Exit before token, producer or child |
| `b10_abrupt_platform_unsupported` | `OwnedProducerProcess.Start` on a non-Linux OS | No pipe or process created |
| `b10_abrupt_signal_preflight_failed` | Own-PID null-signal preflight returns nonzero or its native import cannot load, before pipes/child/arms | No child or arm; record actual return/errno or load exception, never fabricated errno |
| `b10_abrupt_child_start_failed` | `Process.Start` returns null or throws | No signal; diagnostic failure |
| `b10_abrupt_child_identity_mismatch` | `hello` missing, late, wrong challenge, PID or start time | Cleanup kill; no arm |
| `b10_abrupt_target_invalid` | Target nonpositive, exited, reused, foreign, traced or of changed start identity before a signal | That signal not sent |
| `b10_abrupt_signal_failed` | `kill` returns nonzero (errno recorded) or its entry point does not load | Arm fails; successor blocked if KILL |
| `b10_abrupt_stop_unconfirmed` | `/proc` stopped state not observed within the arm budget | Arm fails |
| `b10_abrupt_resume_unconfirmed` | No progress after SIGCONT within the arm budget | Control incomplete |
| `b10_abrupt_exit_unobserved` | `WaitForExit(10000)` false after KILL | Successor blocked |
| `b10_abrupt_eof_incomplete` | Events EOF not reached within 10 s after exit | Successor blocked |
| `b10_abrupt_unexpected_exit` | Child exits before KILL was requested | Mechanical chain fails; successor blocked |
| `b10_abrupt_capture_gap` | A gap reason of the wire section latches | Capture invalid; no usable selection or receipt |
| `b10_abrupt_sample_missing` | No complete parsed report strictly before acceptance; not raised for an arm that already raised `b10_abrupt_report_binding_invalid` | Arm blocked |
| `b10_abrupt_report_binding_invalid` | A `pre_acceptance_report` message is duplicated, out of order, names an unknown arm or attempt, has a `report_length` outside 1 to 1048576, or its fixed report file is missing, unreadable, over 1048576 bytes, or of a different length or SHA-256, or its `report_identity`, `report_sequence` or `report_capture_utc` is outside its wire-section bound; not raised for an arm that already raised `b10_abrupt_sample_missing` | Arm blocked; no checkpoint for that arm |
| `b10_abrupt_guard_failed` | A guard of the policy table fails | Arm or seal blocked |
| `b10_abrupt_control_incomplete` | Control drain, rows, count, post-drain sample, seal or release resend missing | Kill exposure blocked |
| `kill_too_early` | No durably accepted original at kill checkpoint | Exposure ineligible; no extra attempt |
| `kill_too_late` | Final selection empty after post-death reconciliation; detail `no_unconfirmed_attempt` | Exposure ineligible; no extra attempt |
| `b10_abrupt_cgroup_unavailable` | `memory.events.local` missing, unreadable, malformed or of changed identity | Mechanical check fails |
| `b10_abrupt_oom_conflict` | `oom_kill` reset or increment | Mechanical check fails |
| `b10_abrupt_publication_failed` | A create-only write fails or read-back differs | Successor blocked |
| `b10_abrupt_publication_ambiguous` | Write outcome unknown, or missing or duplicate object | Successor blocked; no overwrite |
| `b10_abrupt_first_termination_unknown` | Workflow cannot bind actual first-pod termination | `safety_stop`; successor blocked |
| `b10_abrupt_successor_binding_invalid` | Successor input missing or changed, or Job, pod UID, source, image, predecessor or selection mismatch, or same pod identity; detail one of `receipt_missing`, `receipt_changed`, `job_mismatch`, `pod_uid_reused`, `source_mismatch`, `image_mismatch`, `predecessor_mismatch`, `selection_stale` | Exit before producer construction |
| `b10_abrupt_successor_late` | Successor not ready at the release boundary | Comparison incomplete; no late resend |
| `b10_abrupt_deadline_exhausted` | An enclosing lifetime, Job or phase deadline leaves no budget | `record the gap and continue` to cleanup |

Outcome labels, not failures: `mechanical_status` `complete` or `incomplete`; `fatal_capture_status` `not_implemented_pr3`; `native_tail` `unknown_due_to_intended_kill`; cross-host timing conclusion `not_verified`.
