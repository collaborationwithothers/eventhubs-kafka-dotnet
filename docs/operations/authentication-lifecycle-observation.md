# Authentication lifecycle observations

These observations prepare the renewal and projected-token rotation experiments. They preserve SDK-owned acquisition and caching and librdkafka-owned scheduling. They do not establish a new Entra exchange, a credential file re-read or broker acceptance.

## Purpose

The library exposes two opt-in diagnostic capabilities for a later approved live plan. A Kafka session can retain a bounded sequence of native callback, credential return, successful installation and sanitized failure observations. A separate observer can sample stable metadata for the configured projected token file. Neither capability starts automatically, changes the authentication path, or decides whether a run is successful.

The session snapshot is local evidence about callback handling. A successful installation means the native client accepted the token-install call; it does not establish that Event Hubs accepted the token or that a later exchange occurred. The file observer reports a stable filesystem generation only. It does not establish JWT rotation, an SDK re-read, or use of that generation by a credential exchange.

## Capture API and bounds

`KafkaAuthenticationFactory.CreateObservedSession` creates a session with capture enabled. Existing `CreateSession` calls remain unobserved. `GetLifecycleSnapshot` returns a defensive read-only copy and never calls the credential, polls a Kafka client, reads a file, or samples a clock.

The session retains at most the first 128 callback attempts and at most three events per attempt, for a maximum of 384 events. Events have increasing one-based sequence and attempt numbers. The phases are `initial` and `refresh`; stages are `callback_started`, `acquisition_returned`, `installation_succeeded`, and `failed`. Acquired expiry is absent before acquisition returns and is retained for later events in that attempt. Installed expiry changes only after the existing token-install operation succeeds. Failure reasons are the existing sanitized values `acquisition`, `token_validation`, and `installation`; exception text and credential material are never included.

When capture is disabled, the snapshot is empty and reports `capture_disabled`. An enabled session with no callback is a complete empty snapshot and does not imply success. Attempt 129 and later set `attempt_limit`, retain existing events, perform no further observation clock calls, and continue the existing authentication path. Observation clock errors leave the related clock fields null and set `clock_unavailable`; the core token-validation clock and error behavior stay independent. `attempt_limit` takes precedence over `clock_unavailable`.

`KafkaAuthenticationFactory.CreateProjectedTokenFileObserver` constructs an independent observer without reading the configured path. Each explicit `Observe` call takes two independent metadata snapshots. Each snapshot resolves directory and file symlinks component by component before comparing the resolved full path, UTC last-write ticks and file length. Matching snapshots establish a stable generation: the first is generation 1, a later different stable tuple increments it, and an unchanged tuple retains it. A missing/inaccessible target, a non-directory intermediate component, a resolution failure or limit, a mismatch between snapshots, or a clock error returns `unavailable` with no generation while preserving prior stable state.

Each snapshot permits at most 256 component visits and 40 link expansions, with a maximum of 4096 characters in the input and each expanded pending path including its resolved prefix. These are diagnostic policy limits. Exhaustion returns `unavailable` for that sample without retry; only a later explicit call samples again. The resolver's limits are defined in `ProjectedTokenPathResolver`; they bound managed traversal work, not OS-call latency. A `token -> ..data/token` directory-target switch can change the compared path even when length and last-write time remain equal. Two matching snapshots are not an atomic filesystem transaction. Unobserved changes between samples, hard-link changes, or content changes at the same resolved path with equal length and time can remain invisible. Generation does not prove JWT rotation, SDK re-read, exchange provenance or broker acceptance.

On .NET runtime `v10.0.13`, `FileSystemInfo.LinkTarget` exposes raw link text, while `ResolveLinkTarget` resolves the final component; `Path.GetFullPath` removes lexical relative segments but does not resolve directory links. The observer therefore walks components itself and uses refreshed file metadata without opening token contents. Sources: [FileSystemInfo.cs](https://github.com/dotnet/runtime/blob/v10.0.13/src/libraries/System.Private.CoreLib/src/System/IO/FileSystemInfo.cs), [FileSystem.Unix.cs](https://github.com/dotnet/runtime/blob/v10.0.13/src/libraries/System.Private.CoreLib/src/System/IO/FileSystem.Unix.cs), [Path.Unix.cs](https://github.com/dotnet/runtime/blob/v10.0.13/src/libraries/System.Private.CoreLib/src/System/IO/Path.Unix.cs) and [FileInfo.cs](https://github.com/dotnet/runtime/blob/v10.0.13/src/libraries/System.Private.CoreLib/src/System/IO/FileInfo.cs).

The observer serializes calls and performs at most 4096 sample attempts. Attempt 4097 and every later call returns sample 4097 with status `sample_limit`, null clock values and generation, without reading metadata or sampling a clock. These limits bound this diagnostic capability; they are not measured credential lifetimes or rotation rates. Public sample fields are limited to sample number, observation time, monotonic timestamp, timestamp frequency, generation and status. The observer never opens token contents, parses JWTs, persists the comparison tuple, or exposes paths, hashes, file lengths, modification times or exceptions.

## Missing live evidence

The following requirements are for a subsequent approved live plan. They are not implemented experiments or authorization to run.

- **Renewal:** Keep one native producer or consumer session alive. Record its first successful installed expiry E0, later callback/acquisition/install observations and actual operations before and after the relevant boundary. A callback returning E0 is credential reuse of an expiry, not a new issuance. Claim replacement installation only when a separately reviewed safe provenance method establishes a genuinely replacement token. A changed expiry alone does not establish an Entra exchange. SDK cache hit versus exchange remains unknown without positive supported evidence.
- **Projected-token rotation:** Correlate an independently observed filesystem-generation change with later callback, acquisition, installation and real service operations in the same session. A generation change alone is not proof of JWT rotation, SDK re-read or exchange use. The later plan must specify safe supported evidence for actual projection rotation and its use by the credential path. Public evidence must contain no token values, identifiers, token-file paths, credentials or raw request bodies. If evidence is unavailable, leave the hypothesis unresolved.
- **Observation windows:** Select a real observation using actual installed expiry, actual pod projection configuration and observed generation metadata. Do not assume a fixed Entra token lifetime, projected TTL, an 80-percent refresh schedule, or that dispatch duration equals client lifetime. Span the actual boundary being claimed and retain service evidence after it. The later plan must set finite per-client, observation-window and cleanup deadlines, check them against measured metadata, and classify a missed boundary as incomplete evidence. A forced callback, shortened real expiry, cache flush or manual token replacement cannot satisfy a natural observation.
- **Existing execution bounds:** [`probe-v2-runtime-limits.json`](probe-v2-runtime-limits.json) bounds producer process time at 1920 seconds, reader time at 840 seconds and batch admission at 14400 seconds. The [scenario workflow](../../.github/workflows/scenario.yml) bounds each applicable job at 360 minutes. V2 capture permits one statistics report per slot. These are short fresh-client protocols, not a lifecycle runner; this prerequisite changes none. If an actual observation exceeds a bound, stop before the live experiment and give Hari the measured metadata, proposed finite bound/reserve and lifecycle design decision. Do not silently extend a limit or dispatch.
- **Controls and completion:** Retain same-run initial successful delivery and exact-marker read controls. Distinguish producer `Poll`, consumer `Consume`, application processing or pause, callback entry, credential return, native installation and service success. Do not infer acceptance from elapsed time or callback count. Each later approved configuration uses five fixed repeat slots with no replacements. Missing observer rows, unavailable generations, lost polling evidence, clock uncertainty, cap exhaustion, missing service evidence, identity mismatch or incomplete cleanup remains explicit incomplete evidence and does not automatically mean a scientific hypothesis is contradicted.
- **Recovery and cleanup:** This capability adds no infrastructure, jobs or recovery operation. A later plan uses workflow-owned bounded collection, Job deletion, ephemeral destroy and dispatch-end AKS stop under ADR-020 and existing governance. A collection, bound or cleanup failure retains diagnostics and prohibits a successful lifecycle claim or replacement run without authorization. Agent sessions never obtain Azure credentials or apply Terraform.

## Observation windows

No executable live window, deadline, duration increase, repeat or dispatch is approved by this prerequisite. The future plan must use actual token expiry and projection metadata to choose its window, reserve the approved workflow cleanup time, and stop before execution if current bounds cannot contain the real observation. Callback or file-generation timestamps on their own cannot select a lifecycle verdict.

## Controls and completion

Future live work must keep delivery and exact-marker readback as service controls and identify the same Kafka session across observations. Preserve the distinction among polling, application work, callback invocation, credential return, native installation and service acceptance. Use finite bounds, five fixed repeat slots per approved configuration, zero replacement repeats, bounded evidence collection and workflow-owned cleanup. Missing, ambiguous or incomplete evidence stays incomplete; it is not converted into a successful observation or a contradicted verdict by default.

## Fault boundary

This prerequisite injects no fault. Entra-unreachable and federated-credential-deletion designs, valid-token/expiry/recovery observations, protected identity/network scope, fault metrics and completion policy, and Event Hubs reauthentication or connection-close behavior remain deferred. The existing initial-versus-refresh local failure behavior and metric tests remain in force. Healthy observations do not settle these questions.
