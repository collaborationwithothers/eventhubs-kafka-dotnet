# Authentication lifecycle observations

These observations prepare the renewal and projected-token rotation experiments. They preserve SDK-owned acquisition and caching and librdkafka-owned scheduling. They do not establish a new Entra exchange, a credential file re-read or broker acceptance.

## Purpose

The library exposes two opt-in diagnostic capabilities for a later approved live plan. A Kafka session can retain a bounded sequence of native callback, credential return, successful installation and sanitized failure observations. A separate observer can sample stable metadata for the configured projected token file. Neither capability starts automatically, changes the authentication path, or decides whether a run is successful.

The session snapshot is local evidence about callback handling. A successful installation means the native client accepted the token-install call; it does not establish that Event Hubs accepted the token or that a later exchange occurred. The file observer reports a stable filesystem generation only. It does not establish JWT rotation, an SDK re-read, or use of that generation by a credential exchange.

## Capture API and bounds

`KafkaAuthenticationFactory.CreateObservedSession` creates a session with capture enabled. Existing `CreateSession` calls remain unobserved. `GetLifecycleSnapshot` returns a defensive read-only copy and never calls the credential, polls a Kafka client, reads a file, or samples a clock.

Ordinary observed sessions retain at most the first 128 callback attempts and at most three events per attempt, for a maximum of 384 events. The test-only capped mode retains the same first 128 attempts and allows up to five events per successful capped attempt, for a maximum of 640 events. Events have increasing one-based sequence and attempt numbers. The phases are `initial` and `refresh`; stages are `callback_started`, `acquisition_returned`, `installation_succeeded`, and `failed`. Acquired expiry is absent before acquisition returns and is retained for later events in that attempt. Installed expiry changes only after the existing token-install operation succeeds. Failure reasons are the existing sanitized values `acquisition`, `token_validation`, and `installation`; exception text and credential material are never included.

When capture is disabled, the snapshot is empty and reports `capture_disabled`. An enabled session with no callback is a complete empty snapshot and does not imply success. Attempt 129 and later set `attempt_limit`, retain existing events, perform no further observation clock calls, and continue the existing authentication path. Observation clock errors leave the related clock fields null and set `clock_unavailable`; the core token-validation clock and error behavior stay independent. `attempt_limit` takes precedence over `clock_unavailable`.

## Separately selected handler refresh-path diagnostic

The handler refresh-path diagnostic is a test-only, default-off addition to the original metadata route. It exercises our OAuth handler with the Identity SDK as a black box. `KafkaAuthenticationFactory.CreateRefreshPathTestSession(identity, 5000, cancellationToken)` is callable only for the fixed 5000 millisecond cap; it creates one observed session for one native client. Production `CreateSession` and `CreateObservedSession` remain uncapped.

On every successful capped callback, the handler first validates the SDK's actual `AccessToken.ExpiresOn` against the current UTC time. After the SDK call returns, it computes the absolute Kafka expiry as `min(actual ExpiresOn, now + 5000 ms)` and passes that absolute Unix time in milliseconds to `OAuthBearerSetToken`. The cap is recomputed for each callback and never extends the SDK expiry. `AcquiredExpiresOn` records the SDK expiry; `EffectiveExpiresOn` records the absolute expiry advertised to Kafka; `CapComputedAt` records the post-SDK time used for the minimum; and `TestExpiryCapMilliseconds` identifies the opt-in. The cap is not a duration sent to Kafka. The pinned [Confluent.Kafka 2.16.0 API](https://github.com/confluentinc/confluent-kafka-dotnet/blob/v2.16.0/src/Confluent.Kafka/ClientExtensions.cs#L39-L91) takes absolute epoch milliseconds. Native eligibility is based on the advertised expiry; the [librdkafka 2.16.0 refresh calculation](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka_sasl_oauthbearer.c#L378-L432) makes 80 percent of the remaining validity eligible. Four seconds from a five-second advertised expiry is derived arithmetic, not a callback-time promise.

The observed Identity SDK seam records `sdk_get_token_invoked` immediately before the existing synchronous `TokenCredential.GetToken` call and `sdk_get_token_returned` immediately after it returns. It returns the same `AccessToken` without reading its value or changing SDK caching. The successful capped event chain is `callback_started`, `sdk_get_token_invoked`, `sdk_get_token_returned`, `acquisition_returned`, `installation_succeeded`. A cached SDK response passes. Invocation and return do not prove a network exchange, cache provenance or assertion use.

The opt-in travels only through the workflow-dispatch boolean `test_handler_refresh_path`, which defaults to false and is valid only with `scenario=probe-batch-2`, `run_kind=smoke`, `items=authentication-controls`, and `capture_authentication_metadata=true`. The frozen phase tuple enables it only for the ordinary F06 C6 seed/loadgen producer and F06 C9 action/enrichment-consumer. The F06 C6 action/probe remains uncapped prerequisite and namespace-role exception evidence. Full smoke, scientific selection, both judges, identities, dependency captures, candidate receipts and scientific judgement retain their existing definitions.

Each ordinary actor keeps its original native client and first captures its ordinary delivery or read through the existing capture path. Within the existing post-terminal 20-second statistics window, two later successful callbacks can enable exactly one extra service operation on that same client. The producer sends a separately labelled synthetic marker. The consumer issues one `Seek` to its original requested location and reads that location again. The consumer read may use native buffering; it does not prove a fresh broker fetch or reauthentication. The worker admits operations only before the 20-second cutoff, recomputes the remaining time after synchronous calls, and records late returns as raw observations that cannot satisfy the later assessment. SDK acquisition, `Consume` and `Seek` are synchronous native paths; a requested 100 millisecond poll slice does not bound their completion time. Per-client cancellation is cooperative and has no latency guarantee. The existing process, Job, cleanup, phase and workflow bounds remain in force.

`KafkaHandlerRefreshProgress` is an immutable volatile count of successful capped installs for which the observed SDK call both entered and returned. It is available without taking the session gate so a blocked credential call does not block worker polling. The worker uses only the count and the retained third successful attempt to decide whether to admit the one diagnostic operation. The count is not evidence completeness or a lifecycle verdict. Lifecycle snapshots are read only after client disposal succeeds.

Handler rows use the existing `PARCHWELL_PROBE_V2_AUTHENTICATION_METADATA` line, one bounded JSON row no larger than 262144 bytes, and the existing IO deadline. Enabled rows use schema version 2 and mode `single-action-v2-handler-refresh-path`; disabled rows keep the schema version 1 metadata shape. The `handler_refresh` object contains raw boundary times, monotonic timestamps, event counts, operation status, bounded delivery/read fields and sanitized error codes. It contains no token, hash, SDK request, semantic `complete`, `exact_match`, pass/fail or verifier field. A row-size fallback clears the handler object. Missing, truncated or malformed rows remain missing evidence.

Offline evidence is split by what its fixture can establish. Native producer background polling and consumer polling against unreachable `127.0.0.1:1` exercise native callback scheduling and token installation with synthetic credentials. The existing local Kafka fixture separately exercises same-client delivery, `Seek` and readback without OAuth. Real ProbeV2 host exports pass producer and consumer fixture bytes through the actual Python collection and immutable transfer helper. None of these offline checks combines authenticated OAuth with a live Event Hubs service.

`KafkaAuthenticationFactory.CreateProjectedTokenFileObserver` constructs an independent observer without reading the configured path. Each explicit `Observe` call takes two independent metadata snapshots. Each snapshot resolves directory and file symlinks component by component before comparing the resolved full path, UTC last-write ticks and file length. Matching snapshots establish a stable generation: the first is generation 1, a later different stable tuple increments it, and an unchanged tuple retains it. A missing/inaccessible target, a non-directory intermediate component, a resolution failure or limit, a mismatch between snapshots, or a clock error returns `unavailable` with no generation while preserving prior stable state.

Each snapshot permits at most 256 component visits and 40 link expansions, with a maximum of 4096 characters in the input and each expanded pending path including its resolved prefix. These are diagnostic policy limits. Exhaustion returns `unavailable` for that sample without retry; only a later explicit call samples again. The resolver's limits are defined in `ProjectedTokenPathResolver`; they bound managed traversal work, not OS-call latency. A `token -> ..data/token` directory-target switch can change the compared path even when length and last-write time remain equal. Two matching snapshots are not an atomic filesystem transaction. Unobserved changes between samples, hard-link changes, or content changes at the same resolved path with equal length and time can remain invisible. Generation does not prove JWT rotation, SDK re-read, exchange provenance or broker acceptance.

On .NET runtime `v10.0.13`, `FileSystemInfo.LinkTarget` exposes raw link text, while `ResolveLinkTarget` resolves the final component; `Path.GetFullPath` removes lexical relative segments but does not resolve directory links. The observer therefore walks components itself and uses refreshed file metadata without opening token contents. Sources: [FileSystemInfo.cs](https://github.com/dotnet/runtime/blob/v10.0.13/src/libraries/System.Private.CoreLib/src/System/IO/FileSystemInfo.cs), [FileSystem.Unix.cs](https://github.com/dotnet/runtime/blob/v10.0.13/src/libraries/System.Private.CoreLib/src/System/IO/FileSystem.Unix.cs), [Path.Unix.cs](https://github.com/dotnet/runtime/blob/v10.0.13/src/libraries/System.Private.CoreLib/src/System/IO/Path.Unix.cs) and [FileInfo.cs](https://github.com/dotnet/runtime/blob/v10.0.13/src/libraries/System.Private.CoreLib/src/System/IO/FileInfo.cs).

The observer serializes calls and performs at most 4096 sample attempts. Attempt 4097 and every later call returns sample 4097 with status `sample_limit`, null clock values and generation, without reading metadata or sampling a clock. These limits bound this diagnostic capability; they are not measured credential lifetimes or rotation rates. Public sample fields are limited to sample number, observation time, monotonic timestamp, timestamp frequency, generation and status. The observer never opens token contents, parses JWTs, persists the comparison tuple, or exposes paths, hashes, file lengths, modification times or exceptions.

## Native client compatibility diagnostic

The native client diagnostic builds a producer with librdkafka's own OIDC code and no refresh handler, beside the custom-handler control. Only `test_native_authentication` selects it, with scenario `probe-batch-2`, run kind `smoke`, items `authentication-controls`, metadata capture on and the handler refresh path off. It adds one F06 C6 Job, `nativejwt` (JWT-bearer), after the C6 judge. It runs five 120000 ms slots under the 900 s reader Job bound; these are planning choices, not measurements. The IMDS stages `nativeimds` and `nativeimdsnode` ran once, in run 41286058152; the chart and worker still accept them, but the phase scripts no longer schedule them. The workflow input's description still says three producers; the workflow is a protected path and is not changed here.

The JWT-bearer settings set `https.ca.location` to `/etc/ssl/certs/ca-certificates.crt`. In librdkafka v2.16.0 that setting names the CA file or directory for verifying the token endpoint ([rdkafka_conf.c L902-L919](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka_conf.c#L902-L919)). Without it, every token request in run 41286058152 failed locally with `error adding trust anchors from file: /etc/pki/tls/certs/ca-bundle.crt`. That this file is missing from the image is inferred, not checked. librdkafka rejects the client at construction if the configured file is missing ([rdkafka_conf.c L4271-L4275](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka_conf.c#L4271-L4275), copied into the error by [rdkafka.c L2600-L2608](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka.c#L2600-L2608) and thrown as `InvalidOperationException` by [SafeKafkaHandle.cs L136-L144](https://github.com/confluentinc/confluent-kafka-dotnet/blob/v2.16.0/src/Confluent.Kafka/Impl/SafeKafkaHandle.cs#L136-L144)).

`ProbeV2NativeAuthentication.Apply` holds the literal settings and is applied outside the authentication factory, so the ordinary baseline and its validator are unchanged.

`ProbeV2NativeAuthentication.Redact`, called inside `ProbeV2Capture`, rewrites every client log line and every client error, `KafkaException` and delivery-report reason. It replaces the token-file path, classifies each `principal=` value as `[workload]`, `[other]` or `[empty]`, and replaces JWT-shaped strings and GUIDs. Recorded settings replace the tenant ID, workload client ID and token-file path. A construction rejection is recorded only as `construction:` and the exception type. No repository code reads token, assertion or token-file contents.

Captures are raw; native Jobs get no judge, candidate or receipt. A native Job that reaches a capture limit or a client cleanup timeout exits 1, so the dispatch can fail while the control passes. A native Job whose stop cannot be confirmed sets the safety stop, so the C9 stages after it are not attempted; the C6 control has already run. The authored assessment reads every slot whatever the dispatch result. A `Failed to acquire SASL OAUTHBEARER token` error without a `Failed to retrieve ... token from` line, and a `SASL authentication error:` continuing `SaslAuthenticateRequest failed:` or `SaslAuthenticateResponse parsing failed:`, are local failures, never Entra, IMDS or broker answers. The rules are in the issue 244 plan.
