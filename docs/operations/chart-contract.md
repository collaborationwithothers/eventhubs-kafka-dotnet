# Parchwell worker chart contract

Each Helm render creates one bounded worker Job in namespace `parchwell`, plus the `loadgen` and `verifier` service accounts. The selected mode determines its image, identity, pool, deadline and fixed environment. The chart accepts explicit deployment identity and destination values; parser, worker and execution limits are fixed from `a01-runtime-limits.json`.

## Inputs

The only top-level inputs are `scenario_id: A01`, `configuration_id: C0|C3`, and the closed `runtime` object. Runtime inputs are `run_id` (lowercase DNS label, 1-29 characters), `phase` (`probe`, `C0`, `C3`), `mode` (`start-line`, `loadgen`, `verify`, `judge`), optional repeat identity (repeat modes require `repeat` 1-5 and `loadgen_job_name`; judge forbids both), lowercase 40-character `source_commit`, digest-pinned `loadgen_image` and `verifier_image`, closed `service_accounts`, `eventhubs`, and `blob` objects, private endpoint IPv4 values `eventhubs_ip` and `blob_ip`, and the runtime-only `application_insights_connection_string`.

`service_accounts` has exactly `loadgen` and `verifier`, each with its fixed role name, nonblank `client_id`, and optional federation `subject` matching `system:serviceaccount:parchwell:<role>`. Terraform's `workload_identity.service_accounts` is the source; the chart selects only these two roles. `eventhubs` is populated from the ephemeral Terraform outputs: namespace name, matching `<namespace>.servicebus.windows.net:9093` bootstrap address, and fixed `document-events`, `document-state`, and `document-events-dlq` topic names. `blob` comes from storage outputs and fixes the account-root HTTPS URL and `ledger`, `verifier`, and `claim-check` containers. The private endpoint addresses come from `private_endpoint_ips`. The Application Insights connection string comes from the persistent output `application_insights_connection_string`; it is runtime-only and must not be committed.

Every ordinary object is closed. The only other runtime input is `bounds`, whose eight sections must equal their complete schema constants: `scenario_parsing`, `loadgen`, `verifier_shared`, `verifier_kafka`, `verifier_start_line`, `verifier_verify`, `verifier_gate`, and `execution`. The first seven copy their complete sections from `docs/operations/a01-runtime-limits.json`. `execution` contains only the four mode deadlines and 30-second termination grace. In particular, `verifier_verify.MaxInputEntries` remains 4,194,304 and `MaxInventoryEntries` remains 186,000.

## Names, environment and deadlines

For a repeat mode, the Job is `<run_id>-<lowercase phase>-r<repeat>-<mode>`, and the checked `loadgen_job_name` is `<run_id>-<lowercase phase>-r<repeat>-loadgen`. The artifact prefix is `<run_id>/<phase>/r<repeat>/`; the producer writes beneath its `producer/` child. A judge Job is `<run_id>-<lowercase phase>-judge` and uses phase prefix `<run_id>/<phase>/`. For example, run `synthetic-c3`, phase `C0`, repeat 1 produces Job `synthetic-c3-c0-r1-loadgen` and prefix `synthetic-c3/C0/r1/`; the judge Job is `synthetic-c3-c0-judge`. The 29-character run ID cap keeps the longest repeat Job name at 49 characters. This chart's DNS-label bound comes from the parent interface; Kubernetes permits a wider DNS-subdomain alphabet for some object names ([Kubernetes object names](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/#dns-subdomain-names), checked against the [official source](https://github.com/kubernetes/website/blob/fe59320b9e3858bc9d41b4ad8d86b1c77568ceb4/content/en/docs/concepts/overview/working-with-objects/names.md#dns-subdomain-names), 2026-10-24).

Every mode receives the source commit and derived Job name as literal environment values; pod name and UID come from the Kubernetes downward API. `Telemetry__ConnectionString`, `Telemetry__ServiceName` (`Parchwell.LoadGen` or `Parchwell.Verifier`), scenario `A01`, and run ID are also supplied as literal values. `Telemetry__ServiceInstanceId` uses the pod name. Loadgen additionally receives all `bounds.loadgen` and `bounds.scenario_parsing` fields as `LoadGen__*`, run/configuration/phase/repeat identities, downward-API pod identities, namespace and ledger storage destination, and the producer artifact prefix. Verifier modes receive `bounds.verifier_shared` as `Verifier__*`, parser values as `Verifier__ScenarioLoadOptions__*`, run/configuration/phase and verifier destination identities, and the verifier client identity from the downward API. Start-line and verify also receive `bounds.verifier_kafka`, namespace/repeat/producer identities and repeat artifact names, plus their respective bound section. Judge receives `bounds.verifier_gate`, phase prefix, candidate output name and both image digests. Boolean strings are lowercase, integer strings are base 10, and TimeSpan strings are copied unchanged. No arbitrary environment map or workload-identity token path is chart input.

The Job deadlines are 840 seconds for loadgen, 150 for start-line, 750 for verify, and 90 for judge, each with 30 seconds termination grace. Process bounds are respectively 11, 2, 12 and 1 minutes. Loadgen has a configured 150-second outer allowance after process and grace; other modes have zero. These values describe configured envelopes, not measured startup or success guarantees. Existing telemetry sampling/export policy stays in CT. C4/C5 implement the declared environment; C4 owns independent finalization/publication-bound changes and any corresponding chart update; C6 proves live interoperability at gate 2. This order follows the adopted #138 decision [6388193638](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/138#issuecomment-6388193638).

## Fixed deployment shape and validation

The Job has one completion, parallelism one, no retries, and `restartPolicy: Never`. Loadgen also sets `podReplacementPolicy: Failed`. Loadgen selects the tainted `loadgen` pool; verifier modes use `workload`. All images are digest-pinned and use `IfNotPresent`. Both accounts disable automatic service-account token mounting while retaining the workload identity label. Pods run as UID/GID/fsGroup 1654, non-root, with RuntimeDefault seccomp, no privilege escalation, read-only root filesystem, and all capabilities dropped. CPU requests/limits are 1/3, memory requests/limits are 2/12 GiB, `/work` is an 8 GiB emptyDir, and `/tmp` is an emptyDir.

`charts/parchwell/tests/check.sh` verifies source-bound projections and the finite render matrix: 21 positive cases and 32 one-mutation negative cases. Each positive case runs Helm lint, Helm template, strict kubeconform for Kubernetes 1.35.0, and structural checks. It checks the rendered Job, service accounts, environment, finite bounds, deadlines, account/pool selection, resources and security settings. Negative cases must fail schema/helper validation cleanly and produce no Job. This is a deployment contract check; worker consumption, receipt membership/hashes, broker coverage and registered-instance enumeration belong to C4/C5.
