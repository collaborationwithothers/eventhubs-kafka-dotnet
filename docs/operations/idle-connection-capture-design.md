# Idle-connection packet observation design

This design selects header-only observation at the producer pod and defines how its packet evidence would be associated with one producer repeat. It cannot identify an unseen component behind the Event Hubs endpoint. Hari has approved the narrow observer capability and experimental interpretation rules; execution still needs a separate checked implementation plan and smoke proof.

## Selected placement and proposed privilege

Place a dedicated observer container in the same pod as exactly one investigation producer. Use a new A07 investigation route with one producer per pod/repeat; do not add an observer to the existing five-producer idle Job. Run five such pods concurrently for a batch configuration, and the two configurations sequentially. The smoke uses the same five-pod concurrency and sequential configurations, with a 5-second idle interval solely to prove instrumentation and scheduling. Keep the producer container's current security context. Give only the observer `NET_RAW`, retaining non-root execution, a read-only root filesystem, `allowPrivilegeEscalation: false`, `RuntimeDefault` seccomp and dropping all other capabilities. Do not grant `NET_ADMIN`, host networking, host PID access, host paths, a privileged container or additional Azure permissions.

The observer placement and exact observer-only `NET_RAW` exception are approved by [Hari's approval of Revision 3](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/334#issuecomment-6615675298). Kubernetes documents that containers in one pod share its network namespace [K1]. Linux's packet-socket creation path requires `CAP_NET_RAW` [L1]. Together these support the selected placement; they do not prove that the configured AKS admission policy, container runtime, seccomp profile or effective capabilities will allow it. The implementation plan must verify those facts before treating this as a working capture method.

A node-level debug pod is not the proposed fallback. Failure of the narrow placement returns for a new decision. No node keepalive timers change.

## Selected header-only collection

Use an `AF_PACKET`/`SOCK_DGRAM` socket on the producer pod's `eth0`, opened with protocol zero and later bound to IPv4. This selected framing delivers network-layer bytes rather than Ethernet header bytes in the pinned `packet_rcv` implementation [L1]; the actual interface and framing still need smoke proof. Before enabling reception, attach and lock the header-only filter.

The declared observation scope is the single Event Hubs private-endpoint IPv4 address supplied by the deployment, TCP port 9093, in both directions. Before producer construction, require that bootstrap-name resolution contains that IPv4 address and no other IPv4 or IPv6 address. Keep the Kafka hostname and resolved Kafka settings unchanged; do not substitute a literal IP or force a different client address-family setting. An unsupported resolution ends that repeat without constructing a producer.

The filter must retain only headers: complete IPv4/TCP headers for unfragmented TCP with either port 9093, and only the IPv4 header for a fragment involving the selected endpoint. Unexpected TCP peers or any such fragment generate a bounded diagnostic with no address or raw bytes and make coverage incomplete. Do not silently discard an unsupported selected-endpoint packet and still claim complete coverage. Other protocols are outside this observation's declared scope. Runtime socket-peer auditing, described below, detects a producer using a different endpoint or address family; that condition ends usable coverage rather than broadening the filter.

The filter must return the parsed network-header length plus parsed TCP-header length, with no Ethernet-length addition for the selected datagram framing. It must validate those lengths before accepting a packet. A fixed snap length does not establish this boundary because TCP header length includes any options and locates the start of data [R1]. Kernel source shows the filter return value limiting `snaplen` before delivery [L1]. Kernel documentation describes attaching and locking a socket filter [L2]. These sources support the proposed mechanism, not its unimplemented bytecode.

Attach and lock the filter before binding or otherwise enabling packet reception. Open with packet reception disabled. No unfiltered startup window is allowed. The future implementation must prove this ordering and its exact framing with synthetic packet tests and a bounded live smoke. Do not enable promiscuous mode or configure offload settings.

Parse only the accepted headers in memory and emit an allowlisted derived record. Do not write a pcap, a packet hex dump, TLS bytes, Kafka bytes, payload strings, addresses or ports to files, stdout, stderr or public artifacts. Raw captures are not an intermediate publication format. The observer does not receive the producer's Azure token or blob credentials through a new grant; its output is a bounded local derived file.

## Selected derived summary

The public packet section contains only flow-local labels, direction, TCP flags and timing, plus the run/configuration/repeat identity needed to associate the observation. A flow label is an ordinal assigned within the repeat, not an address, port or cross-run identifier.

Selected envelope fields: `schema_version`, `run_id`, `source_commit`, `configuration_id`, `repeat`, `capture_started_utc`, `capture_ended_utc`, and `events`. Each event has `flow`, `direction` (`outbound` or `inbound` relative to the pod), `elapsed_ns`, and `flags` (the set of SYN, ACK, FIN, RST, PSH, URG, ECE and CWR present). Elapsed time is the observer's user-space dequeue timestamp measured from its monotonic start; it is not a kernel arrival or wire-transmission timestamp. The common-clock checks below establish correlation eligibility, not a claim of nanosecond precision. No sequence numbers, acknowledgment numbers, payload lengths, raw headers, IP addresses or port numbers are published.

## Selected socket-to-repeat and clock correlation

Each investigation pod contains one process that constructs one native Kafka producer for exactly one configuration/repeat. The observer never opens TCP port 9093 connections. No second producer, AdminClient, verifier, proxy, service-mesh sidecar or other TCP-9093 client is admitted to that pod. Existing authentication and telemetry use their existing destinations, outside the declared capture scope. The pod UID and assigned configuration/repeat therefore identify all its in-scope Kafka flows without guessing which of five concurrent producer instances owns a socket. This is a design invariant to verify in the rendered manifest and worker tests, not a fact established by the current harness.

Before producer construction, the worker registers the run/configuration/repeat/pod UID with the observer through a shared local control file. The observer replies ready only after filter installation, endpoint validation and the clock handshake. The worker constructs its single producer only after that reply. The observer uses the private tuple `(local IPv4, local port, remote IPv4, remote port)` and the outbound SYN's initial sequence number to assign an ordinal flow label. Retransmitted SYNs with the same tuple and sequence number stay in the same generation. A new initial sequence number after an observed reset or completed bidirectional close starts a new generation. Overlapping generations, reuse with an ambiguous sequence number, or a packet with no observed opening SYN leaves that connection mapping incomplete. A FIN alone does not close a bidirectional generation. Header sequence numbers and tuples stay only in bounded memory and never enter output.

All connections from that producer, including bootstrap and broker connections, belong to the repeat. The plan does not claim to identify which encrypted connection carried a particular Kafka request. It correlates the repeat's producer lifecycle and send/idle markers with the set of its observed TCP flows. A per-request causal claim remains unsupported.

The worker audits its own connected TCP socket peers immediately before each produce, at idle start/end, and at least once per second during the observation. It reports only `peer_scope_ok` or a fixed diagnostic code and its monotonic timestamp through one atomically replaced local control slot. Keep aggregate audit count and maximum gap in the final receipt; do not append every audit into the bounded marker file. An unexpected peer, IPv6 peer, failed audit or a missing audit interval makes coverage incomplete. This is a sampled audit, not proof that a short-lived out-of-scope socket never existed between samples; that residual limitation is explicit and prevents claims about all possible client traffic. For the selected Linux design, enumerate only the worker's `/proc/self/fd` symlink targets, retain `socket:[inode]` identifiers in memory, and join them to the inode column in `/proc/self/net/tcp` and `/proc/self/net/tcp6`. Inspect remote port 9093 peers only; sockets for other ports are outside this audit. Source [L4] documents TCP-table endpoint and inode fields; [L5] shows socket-descriptor links with bracketed identifiers. Joining that identifier to the TCP-table inode is inferred from these sources; the required actual-image smoke must verify the join. The TCP-table interface is documented as deprecated, so actual-image compatibility is an explicit smoke check; there is no fallback to a pod-wide table without the ownership join. Bound each audit to 4096 descriptor entries, 65536 bytes per TCP table and 500 milliseconds total; a concurrent descriptor-close race, exceeded limit, malformed row or unreadable entry leaves that audit incomplete. No raw table, fd path or peer address is logged or persisted. No host-PID access is proposed.

Use `CLOCK_MONOTONIC` nanoseconds in the observer and the Linux .NET `Stopwatch` timestamps in the worker. The pinned .NET 10 sources route `Stopwatch.GetTimestamp()` through `SystemNative_GetTimestamp()` to `clock_gettime(CLOCK_MONOTONIC)` on the supported Linux build [D1-D4]. Verify the actual image/runtime path rather than assuming the pinned source is the deployed binary. At startup and shutdown, perform one local handshake: worker records `before`, observer records `sample`, worker records `after`; require `before <= sample <= after` and `after - before <= 100000000` ns. Each control operation has a 5-second timeout and no retry. A failed bracket, different time namespace, unsupported runtime clock or failed handshake leaves correlation incomplete.

Record worker monotonic markers for construction start, first produce start/terminal, idle start/end, second produce start/terminal and disposal completion in the local diagnostic evidence. Both processes measure against the observer start value. UTC start/end are descriptive labels only and are never subtracted to align events. The observer records each header's dequeue timestamp immediately after receive and records its longest receive-loop scheduling gap. A gap above 1000000000 ns makes timing coverage incomplete. Packet order and this timestamp still do not establish exact wire timing; events near a phase boundary can be reported as observed without assigning them to one side of that boundary. The latency and gap thresholds are approved policy values, not measured clock precision.

A public joint result needs its own approved decision rule and verifier implementation under blueprint ADR-019. The publication allowlist remains the packet envelope/events above; private worker markers, socket audits, raw counters, addresses and sequence numbers do not become public packet fields. The verifier may publish an approved incomplete-status reason separately, but this design does not authorize extending an existing candidate or publishing unchecked capture data.

## Proposed completeness and interpretation

These experimental completeness and interpretation rules were adopted by [Hari's approval of Revision 3](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/334#issuecomment-6615675298); no verdict word was selected:

1. A capture is usable for an absence statement only when collection began before producer connection establishment and continued through the second-send observation and final producer shutdown; identity, the single-producer mapping and the specified peer audits, flow-generation mapping, clock handshakes and receive-loop bounds are satisfied; and capture/drop counters, parser diagnostics and completion receipts show no missing interval. Missing or unavailable evidence is an incomplete observation, never zero packet loss.
2. An observed inbound FIN or RST establishes only that the packet reached the producer pod observation point. An observed outbound FIN or RST establishes only its direction at that point. Neither identifies which hidden service or network component originated the cause.
3. No observed FIN or RST establishes only absence from the declared capture interval under the completeness condition. It does not prove a silent network drop, assign a responsible component or show that the remote connection remained open.
4. A gap, unsupported packet shape, buffer drop, exhausted bound, failed completion or unproven correlation leaves the affected observation incomplete. Do not substitute an outcome or modify the existing idle-connection verdicts.

A later verifier plan must enumerate every enforced predicate and its tests. No existing expected outcome, evaluator, verdict word or result changes in this design PR.

## Selected resource and capture bounds

These are design budgets, not measurements. The current cluster file defines one loadgen node with autoscaling disabled; the existing idle worker requests one CPU in its pod. See [cluster configuration](../../infra/cluster/aks.tf) and [the current idle template](../../charts/parchwell/templates/_idle-observation.tpl). The new single-producer route must use the following explicit resources rather than copying the existing request five times.

| Per-pod container | CPU request / limit | Memory request / limit |
|---|---|---|
| Single-producer worker | 100m / 500m | 512 MiB / 1024 MiB |
| Observer | 50m / 250m | 64 MiB / 256 MiB |

For five pods the script-computed total is 750m requested CPU, 3750m CPU limit, 2880 MiB requested memory and 6400 MiB memory limit. These totals do not prove schedulability or adequate performance; allocatable capacity, other workloads and observer perturbation need the smoke evidence. No node addition, autoscaling change, larger SKU or silent sequential fallback is authorized. If all five pods cannot start within the group bound, record the incomplete group and stop the batch. These new resource limits and separate process/pod lifetimes mean the observation is not a reproduction of the old shared-pod performance measurements.

| Bound | Selected literal and approved evidence consequence |
|---|---|
| Observer lifetime | 1320 seconds from observer process entry; exit after the final bounded drain and receipt, or at the deadline |
| Ready/filter/clock startup | 20 seconds within worker execution; no producer construction after a failed or late readiness reply |
| Final capture drain | 20 seconds after producer disposal; then take final packet statistics and close the socket |
| Kernel receive buffer | Request 262144 bytes; require effective `SO_RCVBUF` no greater than 1048576 bytes; otherwise fail startup |
| Header receive buffer | 120 bytes for the supported IPv4-plus-TCP headers; any observed truncation or invalid header length makes coverage incomplete |
| In-memory event queue | 256 entries, at most 256 serialized bytes each; saturation stops usable capture |
| Flow generations | 64 per repeat; ambiguous or excess generations stop usable capture |
| Public derived event count | 65536 per repeat; no sampling or oldest-event eviction |
| Event encoding | At most 256 bytes per event, plus one separator byte; serialization overflow stops usable capture |
| Derived file | 20971520 bytes per repeat including envelope; stream to disk rather than retaining all events in memory |
| Local control/diagnostic files | 65536 bytes each for worker markers and observer receipt; bounded diagnostic codes, no packet contents |
| Shared work volume | Disk-backed `emptyDir`, 134217728-byte size limit; no raw capture files or payload buffers written |
| Worker native-statistics capture | 67108864 bytes for the single producer, with the existing per-report/error/setting limits retained |
| Packet-counter sampling | Once per second and once after final drain; accumulate every `PACKET_STATISTICS` read in unsigned 64-bit totals |
| Control handshake timeout | 5 seconds per operation, no retries; clock bracket limit 100000000 ns |
| Socket peer-audit work | At most 4096 descriptors and 65536 bytes per TCP table within 500 milliseconds; no retry or unbounded scan |
| Socket peer-audit / receive-loop gap | Audit at least once per second; missing audit or receive-loop gap over 1000000000 ns makes coverage incomplete |

The event and envelope upper bound is `65536 * 257 + 65536 = 16908288` bytes, below the 20971520-byte file cap. Across a full batch the derived-file ceiling is `10 * 20971520 = 209715200` bytes; it is not an expected artifact size. The implementation must check every append before writing, atomically finalize a derived file, and never turn a partial file into a complete receipt. Kernel source resets packet statistics on each read [L1], so reading only the last sample or treating a failed read as zero is prohibited by the approved completeness rule. The packet-statistics fields and direction constant are defined in [L3].

On any capture count, byte, queue, memory, time, parser, flow or clock bound failure, stop producing usable capture, preserve only permitted bounded diagnostics and perform cleanup. The affected observation is incomplete under the approved rules; it is not evidence that no close occurred. No automatic retry, event thinning, wider filter, resource increase or fallback privilege is proposed. An OOM kill or forced termination may prevent a receipt; missing completion is incomplete evidence.

## Selected bounded execution

No Azure run is part of this PR. The adopted execution design allows planning for one smoke dispatch and, only after its complete smoke evidence and the separate implementation plan's approval, one observational batch dispatch. The smoke runs five single-producer pods concurrently for keepalive off, then five concurrently for keepalive on, using a 5-second idle interval. This checks the intended scheduling/resource shape and observer startup/disposal without claiming to test idle disconnection. The batch uses the same concurrency with the full 420-second idle interval. Each dispatch has ten distinct pod/repeat observations; the smoke's ten are not published experimental repeats. Across the smoke and batch the cap is twenty producer pods. No reruns are included.

Resolve each configuration from the existing A02 scenario and shared baseline at the dispatch source commit: C0 supplies `socket.keepalive.enable=false`; C1 retains the baseline value. Both retain `metadata.max.age.ms=900000`, `topic.metadata.refresh.interval.ms=900000`, the existing `connections.max.idle.ms`, authentication, timeout and retry settings, `idle_seconds=420`, the 15000-millisecond statistics interval and 80-report cap. Retain the existing record shape, two-produce sequence, 330000-millisecond action windows, 20-second post-terminal statistics period and 10-second client-disposal bound. For the batch change only the documented one-producer-per-pod execution, container resource budgets and observer instrumentation, with a unique `client.id` per pod/repeat. For the smoke additionally replace only the idle interval with 5 seconds; this smoke schedule is never used for experimental conclusions. Verify the resolved settings and omissions against the source configuration before publication. Do not relabel this A07 observation as new A02 result evidence or alter A02's existing judgement. No shortened node keepalive timer is tested.

Selected worker bound, computed from the current worst-case client schedule: 30 seconds registration + 20 observer readiness + 1110.4 client observation/disposal + 20 observer drain + 60 upload + 10 host cleanup + 30 completion = 1280.4 seconds. Use a 1320-second worker process limit and a 1380-second Job active deadline with 30-second termination grace. Observer deadlines are independent, so a failed worker cannot leave it collecting indefinitely. The marker/control operations must fit inside the named phase budgets, not add uncapped time outside them.

Reserve 2400 seconds for each configuration group: five bounded apply commands at 60 seconds each, one whole-group wait at 1470 seconds, five collection commands at 60 seconds each, five deletion commands at 30 seconds each, 30 seconds for aggregate deletion confirmation, and 50 seconds command/control reserve. The accounted total is 2300 seconds, leaving 100 seconds inside the reservation. Smoke groups use the same five-pod reservation ceiling; their shorter idle interval is not used to increase the number of groups or retries. All waits are bounded wall-clock operations; a per-pod timeout does not restart the whole-group wait. Delete partial groups on every exit. Check actual resource requests and all desired pods' scheduling inside that reservation rather than extending it.

After the two groups, reserve 1255 seconds for the new investigation judge and collection, matching the existing judge transport reservation as an initial policy budget, not proof the new judge fits. Use a 720-second judge Job deadline, 660-second judge process limit and 810-second whole-Job wait; the remaining reservation is 60 apply + 210 collect + 120 delete + 30 confirm + 25 command reserve. The later implementation plan must test the new bounded streaming reader against the maximum input sizes.

The script-computed planned work is `2 * 2400 + 1255 = 6055` seconds within the existing 14400-second batch admission window. Before starting each group, require its full 2400-second reservation plus the 1255-second judge reservation to remain. The judge starts only with its full reservation remaining. This leaves 8345 seconds relative to that window, but does not establish the lifecycle setup duration or prove that a live dispatch will finish. Keep the existing 360-minute workflow-job ceiling and all existing infrastructure cleanup reservations and environment approvals; no timeout extension is requested.

The existing orchestration admits only A02, A03 and A04; it does not already admit A07. A future capability PR must add a distinct default-off A07 route, freeze this selection and keep the existing idle route unchanged. Exhaustion action for the proposed dispatch/sample caps: `record the gap and continue`, meaning end observation, preserve only permitted diagnostics and return for assessment without automatic rerun or a causal conclusion. No Azure run is authorized by this design PR.

Dispatch ownership remains with the session coordinating the active verdict work until explicitly handed over. Follow the investigation decision and repository workflow rules for concurrency, environment approval and dispatch refs. A later capability PR must preserve cleanup on every exit and the existing private network/identity boundaries.
