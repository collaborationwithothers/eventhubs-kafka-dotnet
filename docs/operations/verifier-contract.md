# Verifier contract

The production C5 worker has three modes: `start-line`, `verify`, and `judge`. A successful object write alone never authorizes outcome counts or a successful process exit. Each mode publishes a bounded receipt after its work and cleanup complete.

## C5 phase, blob and receipt contract

The run ID `U` is 1-29 lowercase ASCII alphanumerics/hyphens with alphanumeric ends. Phase is exactly `probe`, `C0`, or `C3`; configuration is respectively `C0`, `C0`, or `C3`. Repeat is 1-5. Blob paths retain original phase case while Kubernetes Job names lowercase it. For example, `synthetic-c5`, `C0`, repeat 1 uses Job `synthetic-c5-c0-r1-loadgen` and blob repeat prefix `synthetic-c5/C0/r1/`. Every producer result's `run_id` remains `U`; phase and repeat are separate fields. Authority: [approved C5 plan, revision 4](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/162#issuecomment-6388329508), [adopted probe usability decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/138#issuecomment-6384660536), and [adopted Job-case and bounds decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/162#issuecomment-6388194126).

The six-field producer identity records the actual registered instance, expected instance and Kafka client ID. `instance_id` equals `expected_instance_id`; it does not have to equal the observed pod name. Producer Job and pod details are separately bound by a closed registration receipt. Start-line identity uses the expected LoadGen Job in all three instance/client fields; it does not claim to know the producer pod. Verification checks the captured start-line identity independently from the registered actual producer identity.

| Container | Fixed path | Content |
| --- | --- | --- |
| verifier | `U/phase/rN/start-line.json` | Schema-one start-line note |
| verifier | `U/phase/rN/broker-inventory.json` | Independent start-time broker metadata |
| verifier | `U/phase/rN/start-line-completion.json` | Final start-line receipt |
| ledger | `U/phase/rN/producer/<instance>/registration.json` | Producer registration before Kafka creation |
| ledger | `U/phase/rN/producer/<instance>/publication/{index.json,ledger.jsonl,manifest.json,statistics.jsonl,request-lifecycle.jsonl,capabilities.json}` | Closed six-object publication |
| ledger | `U/phase/rN/producer/<instance>/completion.json` | Successful producer cleanup receipt |
| ledger | `U/phase/rN/producer/<instance>/diagnostics/<fixed-name>` | Bounded diagnostic payloads; never a success index |
| verifier | `U/phase/rN/result.json` | Schema-one verifier result |
| verifier | `U/phase/rN/verify-completion.json` | Final verifier receipt and accepted-publication snapshot |
| verifier | `U/phase/candidate.json` | One phase aggregation candidate |
| verifier | `U/phase/judge-completion.json` | Final judge receipt |

Registration and completion are outside `publication/`; they do not add members to its closed six-name set. Their strict schema-one JSON uses exact fields, duplicate/unknown-field rejection and 65536-byte maximum size. Artifact references contain only a fixed container, fixed path, nonnegative length and lowercase SHA-256 of exact bytes. Reads verify both length and digest. They are not caller-provided URLs or destinations.

Blob listings request pages of 64 and fail closed after 16 pages, 1024 entries or 1048576 UTF-8 bytes of names. The worker never treats a capped listing as a complete singleton. A completed listing must expose exactly one valid registration for the repeat. Judge lists producer markers again, so a later second marker invalidates J5 even if an earlier verify receipt exists. Registration identity binds A01, phase configuration, U, repeat-derived producer Job, actual instance, pod name/UID and 40-character lowercase source commit.

Receipts are strict, bounded projections with `schema_version`, mode, scenario/configuration/run/phase/repeat, Job/pod, nullable identity, source commit, exit code, cleanup flag, UTC round-trip start/completion, artifact references, publication acceptance, and repeat-check states. Only judge has null repeat and identity. Start-line references note then inventory. Verify references result. Judge references candidate. A normal verify result may return exit 1 and still retain a receipt; exceptions, cancellation, cleanup failure, or failed final publication do not. The final receipt is written after host disposal as the worker's final external write; an uncertain create-only upload is not retried.

Verify independently checks the completed producer listing, exactly one registration marker, its actual identity/Job/source binding, successful producer cleanup receipt, start-line completion and referenced bytes, inventory identity/source, exactly the six publication members, every indexed fixed descriptor, exact byte lengths and SHA-256, fixed completion flags, manifest and index identity, and configured per-object/aggregate byte caps. Publication references are recorded in read order: index, ledger, manifest, statistics, lifecycle, capabilities. Only complete acceptance appears as a non-null `publication_acceptance` snapshot in the verify receipt. A rejected but readable publication remains diagnostic evidence and cannot establish J2 or authorize phase counts.

Judge uses five fixed ordinals and never replaces or averages slots. J1 establishes the exact five repeat slots with no foreign or duplicate phase directory. J2 requires a verifier receipt carrying independently accepted publication. J3 validates the verifier final receipt and referenced result bytes/hash. J4 checks derived producer Job binding. J5 requires a completed singleton registration listing. J6 requires available independent broker inventory coverage from the verifier's check-24 assessment. J7 sums all six outcome totals only when every repeat is `complete_valid`, every J1-J6 passes, and checked Int64 addition succeeds. J8 is a separate probe decision: every repeat must satisfy J1-J6 plus usable probe evidence; any qualifying maximum above 20000 ms gives `pass`, five usable nonqualifying repeats give `untestable_at_build_scale`, and any unavailable/unusable repeat gives `inconclusive`. J9 validates the candidate's closed privacy projection and rejects unrecognized raw/private/cost fields; it is a serialization guard, not a scientific verdict. Workload telemetry is not a validity oracle.

Probe usability requires evaluated/pass checks 3, 27, and every check 17-26, plus a complete accepted publication, current producer registration/binding, and independent broker inventory coverage. It does not require a positive throttle sample. A usable repeat with no observed positive sample remains usable and nonqualifying; a positive sample with maximum zero retains observed zero. Thresholds 19999, 20000 and 20001 ms qualify false, false and true. Missing check-24 inventory coverage makes the repeat unusable for J8 even if message validity is unaffected.

The phase candidate is a bounded privacy projection. `versions` records the verifier version and only workload generator, Confluent.Kafka, librdkafka and .NET versions common to accepted results; unavailable or inconsistent versions are null with `version_unavailable`. Image digests come from the validated immutable deployment image references and are deployment inputs, not a cryptographic image-source attestation. Timings begin at the earliest trusted start-line receipt and end at candidate serialization; missing timing is null with `timing_unavailable`.

Each repeat carries its accepted fixed-profile `workload_observation` when available. Candidate diagnostics aggregate only the existing safe A01 projections: error codes, maximum throttle, request-timeout increment, disconnect increment and RTT p99. A missing observation stays null; measured zero stays zero. Counts appear only when J7 authorizes them. The candidate excludes private environment, raw workload payloads, broker hostnames, arbitrary diagnostics, object URLs and cost/costs fields. Workload summaries are descriptive only: they do not determine validity, J2, J7 or J8.

The current implementation validation receipt is at the end of this document. It records blocked checks and does not claim cloud ingestion or a live experiment.

Schema names match case-sensitively using ordinal comparison. Harness JSON is strict UTF-8 and one JSON object per document, or one JSON object per LF-terminated JSONL row. The parser rejects invalid JSON, multiple roots, comments, trailing commas, duplicate properties, unknown harness properties, wrong JSON kinds, unsupported schema versions and out-of-representation integers. It does not coerce numeric strings or booleans. The pinned [.NET 10 JSON reader](https://github.com/dotnet/runtime/blob/6aa72daa24f66c01c3d7b6a32519e9d21396deec/src/libraries/System.Text.Json/src/System/Text/Json/Reader/Utf8JsonReader.TryGet.cs#L14-L48) can reject malformed escaped UTF-16 when a string is decoded; the verifier maps that failure to its existing `malformed_json` route in [StrictJson](../../src/Parchwell.Verifier/Common/Serialization/StrictJson.cs). This keeps decoding failures on each artifact's existing owner path without adding a check. Configured byte, row, entry and depth ceilings are execution limits: exceeding one is an execution failure with zero output calls before publication, not malformed evidence attributed to a check. Failures after upload follow the output section below. There is no silent truncation of input evidence or default-zero substitution. These rules follow the [approved wire catalogue](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245697297).

The wire type notation is: `s` string, `b` boolean, `i32` signed Int32 JSON integer, `i64` signed Int64 JSON integer, `f64` finite JSON number representable as `Double`, `T?` a nullable value, `[T]` an array, and `{s:T}` a string-keyed map. For strict harness objects, all declared properties are required exactly once unless marked optional. Under the O4 answer, strings may be empty; timestamp and digest fields are strings without lexical validation; integers are bounded by their CLR representation, with no extra range rule. The only closed string value sets are the harness fields that numbered checks branch on:

- `completion_source`: `callback`, emitted by the [pinned LoadGen callback path](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Execution/RunExecutor.cs#L464-L467), or `synchronous_rejection`, emitted by the [pinned rejection path](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Execution/RunExecutor.cs#L181-L182).
- `persistence_provenance`: `native_callback`, `missing`, or `pre_enqueue`, emitted by the [pinned LoadGen executor](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Execution/RunExecutor.cs#L181-L182) and its callback path [in the same source](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Execution/RunExecutor.cs#L447-L467).
- `manifest.worker_status`: `complete`, `incomplete`, or `failed`, emitted by the [pinned LoadGen executor](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Execution/RunExecutor.cs#L512-L515).
- `index.worker_status`: `complete` only, emitted by the [pinned index writer](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Publication/BlobRunArtifactPublisher.cs#L319-L330); a missing, malformed or non-complete index is an execution failure with no numbered-check attribution. Under P12, PR 3's reader test asserts that explicit execution-failure outcome for missing and malformed indexes; handler no-output behavior is tested with the first real `verify` handler in PR 5.

Values outside the applicable writer set are structural problems for their owning ledger or manifest check; the index has no numbered check and fails as an execution failure. Native statistics `source` and `state` remain free strings. Lifecycle event discriminator values select their exact structural variants as recorded by the [pinned evidence writer](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Evidence/RunEvidenceSession.cs#L467-L500).

Nested records are passive data. Readers do not import LoadGen or Kafka parsers, compare unrelated files, reconcile the manifest against the ledger, validate digests, or use producer-side semantic validation as an extra gate. Structural parsing retains missing, explicit null and value distinctly where the approved contract names those states. A present wrong-kind native broker field routes to check 20; an absent selected broker field routes to check 21.

## Modes and startup options

The production executable binds the `Verifier` section and accepts exactly `start-line`, `verify`, and `judge`. Mode matching is case-sensitive; unknown or missing modes fail startup before I/O. The selected mode determines its service graph. `probe-gate` remains an offline test/development compatibility mode and is not used by the production chart or phase candidate.

| Mode | Production inputs and outputs | Execution boundary |
| --- | --- | --- |
| `start-line` | Validated A01 phase/repeat identity, derived LoadGen and start-line Jobs, repeat prefix, Blob destinations and workload identity; publishes the fixed start note, broker inventory and final Blob receipt | Token, metadata, watermark, Blob I/O, cleanup and process lifetime use required positive configured bounds. |
| `verify` | Validated A01 phase/repeat identity, derived verify Job and repeat prefix, discovered producer registration, packaged scenario/profile, Blob destinations and workload identity; publishes one result and final Blob receipt | Token, metadata, watermark, local I/O, Blob I/O, cleanup, safety stop and process lifetime use required positive configured bounds. Producer client ID comes only from registration. |
| `judge` | Validated A01 phase identity, derived judge Job and candidate path, immutable LoadGen/verifier image references, Blob destinations and workload identity; publishes one phase candidate and final Blob receipt | Judge reads fixed five-repeat slots with fixed parser/input bounds and per-operation `IoTimeout`; it constructs no Kafka client. |

Shared output and diagnostic limits, Blob connection identity, source commit, process lifetime and cleanup bounds are validated before I/O. Unused mode options are rejected where they could override derived identity or paths. The chart supplies `RepeatPrefix` for start-line/verify workers; phase and candidate prefixes are derived from run ID and original-case phase. The chart also supplies `ScenarioLoadOptions` for verifier Jobs. Judge parsing uses its fixed `JudgeLimits` profile. Local `probe-gate` option behavior is described below only for test/development compatibility.

The two consumed-stream limits are positive Int64 values required only in verify; they have no defaults and are ignored in other modes. They do not enter the duration sum.

`MaxInventoryEntries` bounds the number of attempts in the manifest inventory. The separate, required positive Int64 `MaxInputEntries` bounds structural entries within each parsed JSON document or JSONL row and entries charged to the shared input budget across artifacts, including ledger rows, inventory attempts and supporting metadata. Property names and array elements count as structural entries, so an inventory attempt uses more parser capacity than one entry. The [A01 deployment limits](a01-runtime-limits.json) supply these independent execution ceilings; reaching either ceiling is permitted, exceeding it remains an execution failure with no result publication. Existing byte, row, depth and broker limits still apply.

Budget requirements are mode-specific. Unused budgets are optional and ignored if supplied. `IoTimeout` bounds local scenario/input/output I/O, including scenario loading in `verify`; `BlobIoTimeout` bounds remote Blob I/O. `ProcessLifetime` must be strictly greater than the sum shown for its mode; equality or checked-sum overflow fails startup validation. The sum is a configuration sanity check, not a worst-case execution bound: Blob I/O and polls may repeat, and the process watchdog is the backstop. All required durations and limits must be positive and representable. Validation checks required resource text and output destination form, but does not read files, create directories, resolve DNS, acquire a token or contact a service. `SafetyStop` has no code default; the approved runner value is 600000 ms. Other production deadline values are supplied by the runner and are not chosen by this PR.

The intended probe-gate expected identity list contains five A01/C0 identities, but a different expected-list cardinality does not fail startup. Startup also preserves actual repeat paths with zero, four, five, six, duplicate or foreign inputs; check 32 owns both cardinalities and attribution. The probe-gate graph requires no Kafka, Azure or workload-identity inputs. The output container differs from the ledger container when both apply; probe-gate output is a local destination.

## Failure routing

Parsers return a structural problem with artifact, row, field, code and bounded snippet, or preserve a successfully parsed fragment. They do not classify a run as `invalid`, `incomplete`, or `complete_valid`, aggregate statuses, calculate failed-check lists or authorize exit 0. The owning check handles evidence shape. Infrastructure I/O faults, cancellation, option/startup failures, execution faults, output failures and exceeded resource bounds are execution failures.

| Input or condition | Owner and route |
| --- | --- |
| Missing, malformed, unsupported-version or truncated ledger | Check 1 |
| Same failures in sealed manifest | Check 2 |
| Run identity mismatch in index, manifest, ledger, statistics, lifecycle or capabilities, or an inventory/ledger/consumed instance mismatch | Check 3; recorded-input judgement |
| Attempt inventory, count, row, key or sequence mismatch | Check 4; duplicate attempt rows are check 5 |
| Consumed-message headers, missing ledger row or key/sequence mismatch | Check 6; message parser follows the Kafka window section below |
| Missing/malformed start-line note | Check 7 |
| Partition boundary, start offset or end-line rules | Checks 8-9 |
| Verify safety stop or token, metadata or watermark deadline | Check 10 or 11 as applicable; see output behavior below |
| Ledger delivery/persistence, guard observations, native counters or lifecycle errors | Checks 12-16 |
| Missing/faulted captured evidence or missing completion/boundary | Checks 17-19 |
| Native raw JSON syntax, selected field representation, or report diagnostic | Check 20 |
| Absent required native broker name/field/window child | Check 21 |
| Native generation, counter reset, broker coverage, post-drain sample or broker-set stability | Checks 22-26 |
| Selected producer settings or recorded broker count | Checks 27-28 |
| Recorded A01 evidence and probe usability/observation/aggregation | Checks 29-32; these are not run-validity checks |
| Missing/malformed index, infrastructure read fault, any configured resource limit, cancellation, other execution/output fault | Execution failure; nonzero, with zero output calls before publication; see the output section for failures after upload. For an index, `ArtifactIndexReader` returns an explicit execution-failure outcome rather than a numbered check; PR 3 tests the reader outcome. The assertion that a handler makes no output calls and writes no result file is paired with the first real `verify` handler in PR 5 under P12. |

The native statistics object is an open librdkafka object, not a closed harness envelope. PR 3 selects top-level `ts`, `age` and `brokers`; `name`, `client_id`, `type`, `time` and other top-level properties are optional. Unknown native properties are accepted. Broker dictionary keys and broker `name` are retained independently. Check 21 owns absent required broker fields (`name`, `nodeid`, `source`, `state`, `req_timeouts`, `txretries`, `txerrs`, `rxerrs`, `disconnects`, `throttle.cnt`, `throttle.max`, `rtt.cnt`, `rtt.p99`); a present field with the wrong kind routes to check 20. Native node IDs are Int64. `source` and `state` are strings. Native units and selected fields follow [librdkafka 2.16.0 statistics documentation](https://github.com/confluentinc/librdkafka/blob/v2.16.0/STATISTICS.md); the verifier does not compare native clocks with host time. The independent readers preserve native fields; the Recorded-input judgement section owns checks 22-26.

## Recorded-input judgement

The [approved PR 4 plan, revision 2](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6258450821), implements checks 1-6 and 12-28 over recorded inputs. Check 28 is a derived measurement, not another rejection predicate. The judgement functions perform no I/O or client construction; PR 5 supplies independently resolved producer configuration, consumed records already limited to the run window, and assessments for checks 7-11.

| Owner under `VerifyRun/Judgement` | Checks or responsibility |
| --- | --- |
| `BookkeepingChecks.Evaluate` | 1-6: ledger/manifest structure, run and instance identity, inventory reconciliation, duplicate attempt IDs and consumed-record association |
| `LateWriteChecks.Evaluate` | 12-16: callback delivery/persistence, guard observations, native guard counters and native error callbacks |
| `StatisticsChecks.Evaluate` | 17-26: captured evidence, completion, native report structure, generation, counter history, broker coverage and sampled set stability |
| `ConfigurationFidelityCheck.Evaluate` | 27: independently selected producer settings and the decided override attribution |
| `BrokerCountRecorder.Record` | 28: sampled connection-count lower bound |
| `OutcomeClassifier.Classify` | Four attempt classes, duplicates and reorders |
| `RunJudgement.Evaluate` | Compose assessments, select status, authorize counts and retain diagnostics |

Each assessment is `Evaluated` with `Pass`, or `Evaluated` with `Fail` and its invalid/incomplete classification, or `NotEvaluated` with neither disposition nor classification. Missing prerequisites never pass. Within each check, an observed violation wins; otherwise unavailable evidence needed to establish the predicate gives `NotEvaluated`; otherwise the check passes. Independent sources are inspected even when another source fails. Missing input retains its reader's owning structural problem; a present empty collection is not missing input.

Malformed ledgers and captured envelopes discard their whole parsed value under the existing readers; judgement does not recover earlier rows. A native report can instead have both a value and check-21 problems, so its independently readable fields still contribute observations. A missing/malformed index or an input-limit exception remains an execution failure, with no additional numbered check. Handler execution acceptance follows [Kafka window and storage execution](#kafka-window-and-storage-execution).

`RunJudgement` retains every failed check number, sorted and distinct. Any witnessed invalid failure takes precedence over incomplete failures, and both remain in the failed-check list. An incomplete failure without an invalid failure gives `Incomplete`. Only evaluated passes for every validity check 1-27, including explicitly supplied checks 7-11, authorize `CompleteValid` and the six outcome counts. If there is no witnessed failure but a required assessment is unavailable, the internal status and counts are null. This aggregate cannot be published and adds no fourth wire status. Output assembly follows [Kafka window and storage execution](#kafka-window-and-storage-execution).

### Bookkeeping and late-write guard

Check 3 compares all six `RunIdentity` fields ordinally with the runner's identity for every parsed identity-bearing artifact: index, manifest, ledger rows, statistics envelopes, lifecycle events and capabilities. It also compares inventory, ledger and consumed instance IDs with the expected instance. Statistics role/client labels do not participate. Check 4 reconciles the manifest's actual attempt count, inventory membership and ledger membership exactly, once per attempt, with matching key and sequence. `PlannedAttemptCount` does not limit retries; unrelated event, provenance and timing metadata is not another equality gate. Check 5 detects repeated bare attempt IDs ordinally, including IDs reused under different instances. Check 6 requires unambiguous instance/attempt headers, decoded key/sequence, exactly one matching ledger row and matching key/sequence. An unjoinable record is invalid, rather than a phantom; repeated identical records are not themselves malformed.

Check 12 fails any callback row with `Delivered=false`, regardless of error code. Synchronous rejections do not fail it. Check 13 fails a readable callback with null persistence status or `PossiblyPersisted`, whose pinned [enum value is 1](https://github.com/confluentinc/confluent-kafka-dotnet/blob/v2.16.0/src/Confluent.Kafka/PersistenceStatus.cs). It does not reject other representable integers; a synchronous rejection with null status passes. An omitted wire `persistence_status` fails check 1 and leaves check 13 `NotEvaluated`, because the ledger is discarded. A successful DTO containing a missing field is a synthetic state and fails check 13, distinct from that omitted-wire route.

Check 14 requires capabilities `GuardObservationsComplete=true` and permits only `broker_lifecycle_inventory_unproven` and `request_lifecycle_capture_unsupported` in the manifest's guard observations. Neither marker is required, and capabilities observations do not replace manifest observations. Under [ADR-013](../blueprint.md#adr-013-a-run-is-the-window-between-high-watermarks-recorded-before-and-after-the-load-generator) and the [revision-2 amendment to check 15](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6258639724), any non-zero `req_timeouts`, `txretries`, `txerrs` or `rxerrs` fails check 15. This includes negative representable values, every broker source/state, and reports after the first post-drain sample; later zero does not heal an earlier failure. It adds no parser range rule. `disconnects` is not this guard. Check 16 fails only a native error callback with `IsError=true`; fatal flags, error codes, native-log severity and text do not replace that predicate.

### Statistics and configuration

Check 17 owns missing/malformed statistics, lifecycle and capabilities artifacts and faulted capture. Check 18 fails a present statistics artifact with no reports. The entire statistics artifact, in capture order, is one captured-client stream for checks 18-26. Role/client labels neither filter nor partition it and add no label-equality predicate, as the [revision-2 decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6258639724) specifies. Check 15 also scans every report. Check 19 requires a present, complete completion marker and a present, non-null drain boundary; zero is a present boundary. The schema-one omitted-boundary case remains parseable and fails check 19.

Check 20 owns envelope diagnostics and native parse problems assigned to it. The raw native report governs; typed snapshots, optional native fields and disagreements add no checks. Check 21 owns absent required broker fields, including native `name`; present wrong-kind fields belong to check 20. Empty broker maps do not by themselves fail check 21. Check 22 requires strictly increasing capture-order `ts` and exact, stable `ts - age`, using `Int128` subtraction. Reports are never sorted or matched by timestamp, and missing values are not replaced with zero or compared with host clocks.

Broker identity for checks 23-26 and 28 is the ordinal `brokers` dictionary key. Native `name` remains required by check 21 but is not a pairing or lookup key; a different key/name pair is not rejected. The [revision-2 decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6258639724) adopts this rule with the pinned [librdkafka dictionary writer](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka.c#L1943-L1993). Check 23 compares each of the four guard counters and `disconnects` with that key's last readable observation, including across intervening reports where the key is absent. Equal native names under distinct keys stay separate. Missing required fields still belong to check 21 and cannot establish a pass for a missing comparison.

Check 24 requires every independently expected dictionary key to occur in some report and to be absent from completion `MissingBrokers`. Expected names are not derived from observed reports or capabilities. Extra observed keys are allowed, and `MissingBrokers` entries outside the expected list do not fail check 24. Check 25 selects the first capture-order report with `ts >= drain boundary`; a missing qualifying report fails it. That report must include every learned/configured/logical dictionary key observed anywhere in the complete capture. A missing boundary leaves check 25 `NotEvaluated` while check 19 fails. Check 26 compares the learned/configured/logical key sets, independent of state or native name, from the first report through that selected report inclusive. Later churn alone does not fail check 26, but a later new key can still fail check 25's whole-capture coverage rule.

Check 27 compares the exact setting-key set and ordinal setting values with the independently resolved baseline plus scenario selection. For each setting, captured override presence (`Presence == Value`) must equal selected override presence (`Override != null`); when both exist, only `ScenarioId` and `ConfigurationId` are compared ordinally. Override location path/line/column, baseline metadata and omissions are excluded. Wire `override:null` means no override; an omitted required `override` makes capabilities malformed under check 17 and leaves check 27 `NotEvaluated`. Likewise, omitted wire `resolved_configuration` fails check 17 and leaves check 27 `NotEvaluated`, while explicit null reaches check 27 and fails there. A successfully constructed DTO with a missing resolved configuration is synthetic and fails check 27. These routes and the comparison subset come from the [revision-2 decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6258639724); LoadGen's wider metadata validator is not imported.

Check 28 records counts only when checks 18-26 all pass. For each report it counts dictionary entries whose source is exactly `learned`, `configured` or `logical` and state is exactly `UP`; internal/unknown sources and other states are excluded. It records the maximum over all reports and the count in the selected first post-drain report, without deduplicating native names or node IDs. The measurement is published under `LoadGenProducer` and the runner's producer `ClientId`, regardless of statistics labels. A measured zero is allowed, while unavailable counts remain absent. The [approved sampled-count definition](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6235834239) is a lower bound: a connection opened and closed between reports may be unseen. This is the approved oracle criterion, not proof of physical-server counts or every broker lifetime; the native source/state fields are documented in [librdkafka v2.16.0 statistics](https://github.com/confluentinc/librdkafka/blob/v2.16.0/STATISTICS.md).

### Outcome counts and diagnostics

The classifier joins ordinal `(InstanceId, AttemptId)` pairs. Each ledger attempt contributes once: delivered/seen is `ok`, delivered/unseen is `loss`, failed/seen is `phantom`, and failed/unseen is `reported_failure`. Distinct retries sharing a key and sequence remain separate attempts. These counts are authoritative only after the aggregate passes every validity/completion prerequisite; an incomplete window cannot turn unread records into loss.

Duplicate counting groups consumed records globally by ordinal key and sequence and counts excess records: three equal records give two duplicates. Reorder counting groups by topic, partition and key, orders by offset, and counts each sequence below the maximum preceding sequence. An equal-to-maximum sequence does not reorder; an equal-to-an-earlier sequence below the maximum does. Thus synthetic sequences `3,1,2` give two reorders, `1,2,1` gives one duplicate and one reorder, and `1,1` gives one duplicate and no reorder. A key in different partitions does not share a reorder maximum. Negative representable sequences acquire no extra range rule. These conventions follow [Q5](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6236696194) and its [clarification](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245100268).

Diagnostic retention never changes an assessment or the failed-check set. Judgement retains the first configured per-check maximum in source order and truncates only snippets to the longest prefix of complete Unicode scalar values fitting `MaxDiagnosticBytes` in UTF-8. Parser problems preserve their original code, artifact path, row, field and snippet through the owning assessment. Semantic failures use `check_<number>_failed`; they do not replace parser problem codes. The embedded check-27 fidelity assessment consumes a per-check slot, so it has no redundant root diagnostic. Setting differences are bounded by the same per-check maximum in ordinal setting-name order after the full comparison has been assessed. Whole captured files are not retained by this pure judgement layer.

The [carried diagnostic correction](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6265036994) fixes checks 7-11 at their assessment sources. Semantic rows and snippets are null; parser metadata remains original. Checks 7-9 are invalid failures, and checks 10-11 are incomplete failures, with existing status precedence and failed-check numbers preserved.

## Outputs and process outcomes

The start-line note and result projection follow the PR 3 [schema and codec plan](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245697297) and Hari's [later corrections](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245827595), with literal codec cases R1-R9. Start-line notes and verify results use schema version 1 and explicit snake_case projections. Diagnostic snippets are subject to the configured retention limit; if shortened during retention, that does not alter the failed-check list. Result codecs reject output projections whose byte, per-check record or snippet-byte bounds are exceeded; they do not truncate the encoded result. Readers report malformed result shape without assigning a run check. The codecs copy supplied fields and do not compute verdicts, counts, configuration differences, hashes or probe predicates.

MaxDiagnosticBytes bounds diagnostic snippets only. Diagnostic code, artifact and field strings remain subject to whole-result and input limits. An assessment with evaluation not_evaluated has neither disposition nor classification; writing that state with either value is a codec error, and reading it is a malformed result. See the [carried diagnostic-byte correction](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6249810186) and [assessment-consistency decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6249832717). PR 4 proves codec rejection; probe-gate classifies an unreadable result under [Local probe gate](#local-probe-gate).

Result provenance separates producer and verifier versions. Schema 1 permits omitted `generator_version` and `runtime_versions`; the handler omits both only when the manifest is missing or unreadable under check 2. With a readable manifest it copies both unchanged. Empty strings/maps and verifier versions never substitute for unavailable producer data. `verifier_commit`, `verifier_confluent_kafka_version` and `verifier_librdkafka_version` record the verifier itself. Present producer properties retain strict string/map parsing; JSON null is not the absent representation.

`status` is exactly `complete_valid`, `invalid`, or `incomplete` and is copied without aggregation. The six top-level outcome keys (`ok`, `loss`, `phantom`, `reported_failure`, `duplicate`, `reorder`) appear only for `complete_valid`, where counts are required. They are absent for `invalid` and `incomplete`, never null or zero. There is no global `check_assessments` property: the supplied fidelity assessment is nested at `configuration_fidelity.assessment`. Failed check numbers and diagnostic records are separate; diagnostic retention cannot alter the failed-check list. Every diagnostic emits all six keys `check`, `code`, `artifact`, `row`, `field`, and `snippet`; nullable artifact, row, field, and snippet values are JSON null rather than omitted. These required nullable diagnostic keys are distinct from optional measurement properties, which are omitted when unavailable.

Absent boundaries are omitted; an observed empty start/end array remains `[]`. Durations are JSON integer milliseconds, truncated toward zero. `drain_time` and `drain_elapsed_at_stop` are mutually exclusive. A lower-bound stop duration uses the sibling `drain_elapsed_at_stop_lower_bound: true`; absent duration means no duration or lower-bound keys. Optional measurement values are omitted when unavailable, not synthesized as zero. Explicit nullable members in the accepted output projection are emitted as JSON null where specified by the output interface.

| --- | --- | --- |
| `start-line` | Successful note publication and process completion | Execution, publication or cleanup failure |
| `verify` | Successfully published `complete_valid` result and process completion | Published `invalid`/`incomplete` result, or execution/publication/cleanup failure |
| `judge` | Successfully published a `complete_valid` candidate, including a separate non-passing or inconclusive probe gate | Published invalid/incomplete candidate, or execution/publication/cleanup failure |

The process watchdog alone exits 124. A successful output write alone does not establish process success.

In verify, safety expiry is check 10 and token, metadata or watermark failure/expiry is check 11; these permit an incomplete result unless an independent invalid failure takes precedence. Counts remain absent. All execution failures before publication make zero output calls, including input/output limits and local/Blob input or handler cleanup failures. All handler-owned input and Kafka cleanup completes under the handler's cleanup budget before any upload. Failure at or after upload, including uncertain remote commit and later host shutdown failure, exits 1 without delete, overwrite or retry. The watchdog remains armed through final host cleanup and exits 124 on process-lifetime expiry. Runner integration must reject output from these failed processes; no physical-absence guarantee applies after a possibly committed upload.

The watchdog tests run child processes and retain the prepublication no-output proof. PR 5 additionally covers operation budgets, handler cleanup before publication, and late host failures; a watchdog after publication may leave an object but cannot yield successful exit. Test-only blocking/injection does not introduce a production watchdog bypass.

The prescribed `Common/` layout is populated in PR 3 for passive contracts, strict JSON support, and window/result codecs shared by future modes. Captured-input DTOs remain under `VerifyRun/Input`, following the repository's [folder namespace rule](../engineering/dotnet.md#vertical-slices). Populating `Common/` in this PR is an accepted, specific exception to the general rule that it is populated only when two slices need shared behavior. ## A01 recorded evidence and probe usability

The pure [A01 recorder](../../src/Parchwell.Verifier/VerifyRun/A01/A01EvidenceRecorder.cs) supplies checks 29-31 for every A01/C0 verify repeat. The runner's independently expected identities select probe repeats; there is no phase option. For A01/C3, the handler calls the separate `RecordC3` entry point: it emits the same diagnostic `a01_recorded_evidence` projection with the prerequisites below and omits `probe_observation`. The legacy `Record` method remains C0-only, including when called directly with C3. Other scenario/configuration selections omit both projections. The recorder adds no validity assessment and does not change run status, failed checks or authorization of the six outcome counts.

Check 29 records `delivery_error_codes` as distinct non-zero ledger codes in ascending order. A readable ledger with no non-zero codes writes `[]`; a missing or malformed ledger omits the property. Statistics `windows` are present only when every assessment 17-26 is evaluated/pass. Otherwise that collection is omitted, with no partial entries or `statistics_complete` flag. Ledger codes and statistics windows are independently available. Both collections are optional in schema 1: omitted decodes as absent, while present `[]` stays empty; explicit null is not a collection value.

For complete statistics, windows follow original report order and ordinal broker dictionary-key order within each report. Each window requires `broker`, `report_index` (zero-based report line index) and `native_timestamp` (native `ts`). It can carry `request_timeouts_increment`, `disconnects_increment`, `throttle_maximum_ms` and `round_trip_p99_us`. No envelope role/client label, optional native name/type/time, native source/state or post-drain cutoff filters these entries. Each counter's first increment is its cumulative value minus zero; later increments compare that dictionary key's last observation, including across an intervening absence. Checked Int64 subtraction overflow omits only that increment and retains a record-only diagnostic: check 29, code `increment_overflow`, artifact `statistics.jsonl`, row `report_index + 1`, field `brokers.<key>.req_timeouts` or `brokers.<key>.disconnects`, snippet null. The previous counter value advances even after overflow; the independent counter remains recordable. Retain the first `MaxDiagnosticsPerCheck` such diagnostics in traversal order without changing validity or truncating windows.

The pinned [librdkafka v2.16.0 statistics contract](https://github.com/confluentinc/librdkafka/blob/v2.16.0/STATISTICS.md) defines `ts` in monotonic microseconds, `req_timeouts` and `disconnects` as integer counters, `cnt` as sampled-value count, `max` as largest window value and `p99` as the 99th percentile. RTT is microseconds; throttle time is milliseconds. Each summary is available only when its own `cnt > 0`; negative or zero counts omit it. A positive count with value zero retains an observed zero. No average of p99 values or request-level timing is inferred.

Check 30's usable predicate is exactly evaluated/pass assessments 3, 27 and every assessment 17-26. Missing or not-evaluated assessments do not pass. Run status and checks 1, 2 and 4-16 add no prerequisite, so late-write failures 12-16 alone do not make an otherwise usable repeat unusable. Check 31 qualifies a usable repeat when some nonempty throttle window has `max > 20000` ms. Maxima 19999, 20000 and 20001 therefore give false, false and true; an absent positive sample remains usable and nonqualifying, while an observed zero remains measured zero. No throttle window is required.

`probe_observation` always carries `usable` and `qualifying`. For a usable repeat, select the nonempty window with the highest maximum, breaking ties by lowest `report_index`, then ordinal broker key. Copy its `broker`, `report_index`, `window_count` and `window_maximum`, even when it does not qualify. An unusable observation has both flags false and omits all optional references. In both result projections, `report_index` replaces the unpublished `report_timestamp` key; schema remains 1, no timestamp parsing is added, and the old key is rejected even alongside the new one. The passive codec copies values and flags without recomputing these predicates. [Recorder tests](../../tests/Parchwell.Verifier.Tests/A01/A01EvidenceRecorderTests.cs) and [published-output tests](../../tests/Parchwell.Verifier.Tests/Host/VerifyRunHandlerTests.cs) cover absence, observed zero, threshold boundaries, references and invalid-but-usable repeats.

## Local probe gate

The local [probe-gate slice](../../src/Parchwell.Verifier/ProbeGate/ProbeGateHandler.cs) implements check 32. It loads the actual A01 definition through `ScenarioLoader` and `FileSystemScenarioSource`, using the configured scenario limits. The supported gate is C0, measurement `stats.broker.throttle.max`, role `LoadGenProducer`, operator `GreaterThan`, threshold 20000 ms, repeats 5 and full configurations `[C0,C3]`. There is no generic aggregation engine and no read of `expected.yaml` or LoadGen's evaluator. An unsupported or missing gate is an execution failure: exit 1 with no output. The selected DI graph contains only local dependencies, with no Kafka, Azure or workload-identity registration or requirement. The A01 declaration and expected outcome follow [approved revision 4](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/14#issuecomment-6229628298).

The runner supplies expected six-field run identities independently of path-ordered actual results: `scenario_id`, `configuration_id`, `run_id`, `instance_id`, `expected_instance_id` and `client_id`. Match identity strings ordinally. Exactly five expected entries and five actual paths are required, with unique expected run IDs and each expected A01/C0 identity matched once. Never choose five of six. Before opening any result, evaluate every root condition and append each applicable reason once in this exact order:

1. `expected_repeat_count`: expected count differs from five.
2. `actual_repeat_count`: actual path count differs from five.
3. `duplicate_expected_run`: an expected six-field identity or run ID repeats.
4. `foreign_expected_run`: an expected scenario is not A01 or configuration is not C0.

Any root reason produces `inconclusive`, the complete ordered root list and `repeats: []`, with zero repeat-file reads. Root checks inspect expected identities only and do not allocate a rejected record per entry. With no root reason, retain all five repeat records in input order, assigning one reason by this precedence: `missing_result`, `unreadable_result`, `foreign_identity`, `duplicate_identity`, `unusable_repeat`, `usable`. A foreign result does not match one expected six-field identity or is not A01/C0; foreign takes precedence over duplication. Duplicate detection uses the decoded identity/run-ID inventory. Absent probe observations and `usable:false` are unusable, including `qualifying:true, usable:false`.

After strict shape and attribution checks, the gate trusts supplied `usable` and `qualifying` flags. It does not recompute them from run status, failed checks, windows or reference consistency. Exactly five correctly matched usable repeats give `pass` when any qualifies, otherwise `untestable_at_build_scale`. Any missing, unreadable, foreign, duplicate or unusable repeat gives `inconclusive`.

Gate JSON has root `schema_version:1`, `scenario_id:"A01"`, `outcome`, `reasons`, `repeats` and `verifier_commit`. Each repeat has `path`, nullable six-field `identity`, `usable`, `qualifying`, `reason`, and an optional `observation` copying the decoded probe projection. It has no run `status`, verdict or six outcome totals. Root reasons and repeat records have fixed cardinality; retain full reason, path, identity and observation/reference values without truncation. `MaxDiagnosticsPerCheck` and `MaxDiagnosticBytes` retain their result-decoder diagnostic meaning and do not limit gate reasons. Encode and check the complete gate JSON against `MaxOutputBytes` before creating output; overflow is an execution failure, with no shortened successful outcome.

Inputs use bounded streaming reads with `MaxArtifactBytes` per file and one aggregate `MaxTotalInputBytes` budget charged as bytes are read, including bytes read before a malformed result or read exception. Do not charge the same bytes again in the codec. Decoder depth maps to `MaxInputDepth`; diagnostic limits map directly. The decoder's `MaxEntries` and `MaxRowsPerArtifact` derive from `MaxTotalInputBytes`, and its unused row-byte ceiling is Int32.MaxValue: each counted JSON property/array-entry token occupies at least one byte, so the derived entry ceiling adds no rejection within the byte budget. Scenario/profile parsing keeps its separate scenario limits.

A missing file gives `missing_result`; per-repeat `UnauthorizedAccessException`, other read `IOException` or structurally unreadable result gives `unreadable_result`. Input-size/depth/total-byte/diagnostic limit excess, cancellation, deadlines and cleanup failures remain execution failures, never inconclusive results. Catch only the per-repeat read exceptions for unreadable classification; an input disposal failure is a cleanup failure. `IoTimeout` covers scenario loading, input reads and publication, checking cancellation and elapsed time after synchronous completions too. All handler-owned inputs are disposed under `CleanupTimeout` before output is opened. Encode the bounded result, then open with `FileMode.CreateNew`, `FileAccess.Write`; do not create parent directories, overwrite, delete or retry. An existing destination remains byte-for-byte unchanged. A failure after creation may leave a partial file: exit 1 and leave it untouched. The host watchdog remains the final process boundary. Successful publication of every gate outcome follows the [exit table](#outputs-and-process-outcomes).

## Kafka window and storage execution

Start-line and verify use the shared authenticated byte-array consumer, pump token installation before metadata/watermark calls, and query high watermarks for document-events. They never subscribe, commit offsets or reset an out-of-range start. Verify fixes the end once, filters records to each half-open start/end interval before decoding, and uses consumer positions for completion. End-only partitions begin at zero; a lost start partition fails check 8.

Under the PR 5 Q4 decision, empty/duplicate start partitions, negative start offsets and a foreign topic fail check 7. An end high below start fails check 9 before assignment, with both durations absent. Successful metadata with no partitions is check 11/incomplete in verify and execution failure/no note in start-line. Completion observed at or before safety expiry passes; a pending window at expiry fails check 10. A token/query failure before a fixed end remains check 11 even at safety expiry, with both durations absent. Duplicate sequence headers and sequence text outside canonical invariant Int64 decimal fail check 6, alongside the existing identity-header checks. No other range or header check is added.

Only in-window records consume MaxConsumedRecords and MaxConsumedBytes. Bytes include raw key/value plus every header key in UTF-8 and every header value, including duplicates/unknown headers; null byte arrays add zero. Checked accounting occurs before retention, and excess or arithmetic overflow is execution failure with no publication. This is not a numbered run check.

Input names are ArtifactPrefix plus the fixed index and five payload suffixes; note/result names come directly from StartLineInputName, StartLineOutputName and ResultOutputName. No identity-derived name or name-equality check exists. Ledger storage is read-only. Note/result uploads are create-only, with no application retry, overwrite, delete or container creation. judged_file_hashes preserves matching fixed-payload declarations in index order, duplicates included; absent declarations are omitted and unrelated names are ignored. Digests are copied without reconciliation and never select arbitrary reads.

These execution rules follow the [PR 5 Q1-Q6 decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6259492117) and the [existing item checks](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6235834239). The pinned APIs are [Confluent.Kafka 2.16.0 consumer callback](https://github.com/confluentinc/confluent-kafka-dotnet/blob/v2.16.0/src/Confluent.Kafka/ConsumerBuilder.cs#L249-L265), [watermark queries](https://github.com/confluentinc/confluent-kafka-dotnet/blob/v2.16.0/src/Confluent.Kafka/IConsumer.cs#L648-L666), [Blob create-only upload](https://github.com/Azure/azure-sdk-for-net/blob/Azure.Storage.Blobs_12.30.1/sdk/storage/Azure.Storage.Blobs/src/BlobClient.cs#L854-L899), and [explicit workload identity](https://github.com/Azure/azure-sdk-for-net/blob/Azure.Core_1.60.0/sdk/core/Azure.Core/src/Identity/Credentials/WorkloadIdentityCredential.cs). Local fixture proofs use [the approved upstream-timeout recipe](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6260300496) for reported failure and [the approved restore-after-retry recipe](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6260447919) for native duplicates.
