# Verifier contract

This document records the PR 3 foundation contract. It describes independent schema-one readers and output codecs, validated mode options, and failure routing. PR 3 does not judge a run: its three mode handlers are unavailable and each mode exits nonzero without writing an artifact. The verifier's only authority for run validity is the closed list of 32 checks approved for issue #80; these foundation types do not add checks or calculate a verdict. See [ADR-019](../blueprint.md#adr-019-the-verifier-is-the-only-authoritative-judge-of-a-live-runs-captured-evidence-its-checks-come-from-the-items-decision-rules-only-checked-evidence-is-published), the [approved check list](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6235834239), and the [PR 3 plan with later answers](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245697297).

## Authority and boundaries

Read authorities in this order; each later source corrects earlier sources where they differ: [approved revision 4](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6235834239), [implementation plan](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6235974011), [Q2-Q10 answers](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6236696194), [confirmation](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245100268), [PR 3 implementation-grade plan](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245697297), [O1-O4 answers](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245737973), and [PR 3 review fixes](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245827595). The checked-in [golden fixture](../../tests/fixtures/verifier-v1/README.md) records producer bytes and is independently parsed by the verifier; the serializer paths are in [LoadGen evidence code](../../src/Parchwell.LoadGen/Run/Evidence/RunEvidenceSession.cs), [ledger row](../../src/Parchwell.LoadGen/Run/Contracts/LedgerRow.cs), [run manifest](../../src/Parchwell.LoadGen/Run/Contracts/RunManifest.cs), and [index publication](../../src/Parchwell.LoadGen/Run/Publication/BlobRunArtifactPublisher.cs). Producer validation is not the verifier's acceptance oracle. ADR-019 keeps LoadGen's bookkeeping and publication checks in LoadGen and assigns the verifier the separately approved check list.

Schema names match case-sensitively using ordinal comparison. Harness JSON is strict UTF-8 and one JSON object per document, or one JSON object per LF-terminated JSONL row. The parser rejects invalid JSON, multiple roots, comments, trailing commas, duplicate properties, unknown harness properties, wrong JSON kinds, unsupported schema versions and out-of-representation integers. It does not coerce numeric strings or booleans. Configured byte, row, entry and depth ceilings are execution limits: exceeding one is an execution failure with no result file, not malformed evidence attributed to a check. There is no silent truncation of input evidence or default-zero substitution. These rules follow the [approved wire catalogue](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245697297).

The wire type notation is: `s` string, `b` boolean, `i32` signed Int32 JSON integer, `i64` signed Int64 JSON integer, `f64` finite JSON number representable as `Double`, `T?` a nullable value, `[T]` an array, and `{s:T}` a string-keyed map. For strict harness objects, all declared properties are required exactly once unless marked optional. Under the O4 answer, strings may be empty; timestamp and digest fields are strings without lexical validation; integers are bounded by their CLR representation, with no extra range rule. The only closed string value sets are the harness fields that numbered checks branch on:

- `completion_source`: `callback`, emitted by the [pinned LoadGen callback path](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Execution/RunExecutor.cs#L464-L467), or `synchronous_rejection`, emitted by the [pinned rejection path](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Execution/RunExecutor.cs#L181-L182).
- `persistence_provenance`: `native_callback`, `missing`, or `pre_enqueue`, emitted by the [pinned LoadGen executor](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Execution/RunExecutor.cs#L181-L182) and its callback path [in the same source](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Execution/RunExecutor.cs#L447-L467).
- `manifest.worker_status`: `complete`, `incomplete`, or `failed`, emitted by the [pinned LoadGen executor](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Execution/RunExecutor.cs#L512-L515).
- `index.worker_status`: `complete` only, emitted by the [pinned index writer](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Publication/BlobRunArtifactPublisher.cs#L319-L330); a malformed or non-complete index is an execution failure.

Values outside the applicable writer set are structural problems for their owning ledger or manifest check; the index has no numbered check and fails as an execution failure. Native statistics `source` and `state` remain free strings. Lifecycle event discriminator values select their exact structural variants as recorded by the [pinned evidence writer](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/92018747b80150386790af707f18aa5ccf2c3bd3/src/Parchwell.LoadGen/Run/Evidence/RunEvidenceSession.cs#L467-L500).

Nested records are passive data. Readers do not import LoadGen or Kafka parsers, compare unrelated files, reconcile the manifest against the ledger, validate digests, or use producer-side semantic validation as an extra gate. Structural parsing retains missing, explicit null and value distinctly where the approved contract names those states. In particular, a callback row with null persistence status remains readable for check 13, and missing or null `statistics_completion` or its drain boundary remains readable for check 19. A present wrong-kind native broker field routes to check 20; an absent selected broker field routes to check 21.

## Modes and startup options

The executable binds the `Verifier` section, including environment variables such as `Verifier__Mode`. Mode matching is exact and case-sensitive: only `start-line`, `verify`, and `probe-gate` are accepted. Missing, empty, differently cased or unknown values fail startup before I/O. Options stay nullable until validation, have no production defaults, and distinguish omitted from explicitly supplied zero or empty collections. The selected mode alone determines its DI graph. These behaviors and the property names are frozen in the [approved plan](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245697297) and Hari's [latest corrections](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245827595).

| Mode | Required inputs beyond shared fields | Required budgets and process-lifetime sum |
| --- | --- | --- |
| All modes | `Mode`, `ScenarioId`, `VerifierCommit`, `ProcessLifetime`, `CleanupTimeout`, `MaxOutputBytes`, `MaxDiagnosticsPerCheck`, `MaxDiagnosticBytes`, and the selected mode's output destination | `ProcessLifetime` and `CleanupTimeout`; `IoTimeout` is required in `verify` and `probe-gate`; `IoTimeout + CleanupTimeout` is the strict sum only for `probe-gate` |
| `start-line` | Run/configuration/instance/expected-instance/producer client identities; verifier client identity; namespace, Blob service URI and verifier container; `StartLineOutputName`; `MaxPartitions`, `MaxInputDepth`; runtime workload-identity inputs `TenantId`, `WorkloadIdentityClientId`, `FederatedTokenFilePath` | `TokenTimeout`, `MetadataTimeout`, `WatermarkTimeout`, `PollSlice`, `BlobIoTimeout`, `CleanupTimeout`, `ProcessLifetime`; sum is token + metadata + watermark + Blob I/O + cleanup, excluding `PollSlice`; `IoTimeout` is optional and ignored |
| `verify` | The same run, client, namespace, Blob and workload-identity inputs; `LedgerContainer`, `ArtifactPrefix`, `StartLineInputName`, `ResultOutputName`, `ScenarioRoot`, `ExpectedBrokerNames`, `SafetyStop`; `MaxArtifactBytes`, `MaxTotalInputBytes`, `MaxRowBytes`, `MaxRowsPerArtifact`, `MaxInventoryEntries`, `MaxInputDepth`, `MaxNativeReportBytes`, `MaxBrokerEntries`, `MaxPartitions`; scenario limits `MaxDocumentCharacters`, `MaxNestingDepth`, `MaxScalarCharacters`, `MaxParserEvents` | Token, metadata, watermark, `PollSlice`, `IoTimeout`, Blob I/O, cleanup, `SafetyStop`, and `ProcessLifetime`; sum is token + metadata + watermark + local I/O + Blob I/O + cleanup + safety stop, excluding `PollSlice` |
| `probe-gate` | `IoTimeout`, `GateOutputPath`, `ScenarioRoot`, the same four scenario limits, runner-expected repeat identities, actual `RepeatResultPaths`, and `MaxArtifactBytes`, `MaxTotalInputBytes`, `MaxInputDepth` | `IoTimeout`, `CleanupTimeout`, and `ProcessLifetime`; sum is I/O + cleanup |

Budget requirements are mode-specific. Unused budgets are optional and ignored if supplied. `IoTimeout` bounds local scenario/input/output I/O, including scenario loading in `verify`; `BlobIoTimeout` bounds remote Blob I/O. `ProcessLifetime` must be strictly greater than the sum shown for its mode; equality or checked-sum overflow fails startup validation. The sum is a configuration sanity check, not a worst-case execution bound: Blob I/O and polls may repeat, and the process watchdog is the backstop. All required durations and limits must be positive and representable. Validation checks required resource text and output destination form, but does not read files, create directories, resolve DNS, acquire a token or contact a service. `SafetyStop` has no code default; the approved runner value is 600000 ms. Other production deadline values are supplied by the runner and are not chosen by this PR.

The intended probe-gate expected identity list contains five A01/C0 identities, but a different expected-list cardinality does not fail startup. Startup also preserves actual repeat paths with zero, four, five, six, duplicate or foreign inputs; check 32 owns both cardinalities and attribution. The probe-gate graph requires no Kafka, Azure or workload-identity inputs. The output container differs from the ledger container when both apply; probe-gate output is a local destination.

## Failure routing

Parsers return a structural problem with artifact, row, field, code and bounded snippet, or preserve a successfully parsed fragment. They do not classify a run as `invalid`, `incomplete`, or `complete_valid`, aggregate statuses, calculate failed-check lists or authorize exit 0. The owning check handles evidence shape. Infrastructure I/O faults, cancellation, option/startup failures, execution faults, output failures and exceeded resource bounds are execution failures.

| Input or condition | Owner and route |
| --- | --- |
| Missing, malformed, unsupported-version or truncated ledger | Check 1 |
| Same failures in sealed manifest | Check 2 |
| Identity mismatch across manifest, ledger or consumed message | Check 3; comparison is later judgement |
| Attempt inventory, count, row, key or sequence mismatch | Check 4; duplicate attempt rows are check 5 |
| Consumed-message headers, missing ledger row or key/sequence mismatch | Check 6; message parser lands in PR 5 |
| Missing/malformed start-line note | Check 7 |
| Partition boundary, start offset or end-line rules | Checks 8-9 |
| Verify safety stop or token, metadata or watermark deadline | Check 10 or 11 as applicable; see output behavior below |
| Ledger delivery/persistence, guard observations, native counters or lifecycle errors | Checks 12-16 |
| Missing/faulted captured evidence or missing completion/boundary | Checks 17-19 |
| Native raw JSON syntax, selected field representation, or report diagnostic | Check 20 |
| Absent required native broker name/field/window child | Check 21 |
| Native generation, counter reset, broker coverage, post-drain sample or broker-set stability | Checks 22-26 |
| Selected producer settings or recorded broker count | Checks 27-28 |
| Recorded A01 evidence and probe usability/observation/aggregation | Checks 29-32; these are not run-validity checks |
| Missing/malformed index, infrastructure read fault, any configured resource limit, cancellation, other execution/output fault | Execution failure; nonzero, no result file |

The native statistics object is an open librdkafka object, not a closed harness envelope. PR 3 selects top-level `ts`, `age` and `brokers`; `name`, `client_id`, `type`, `time` and other top-level properties are optional. Unknown native properties are accepted. Broker dictionary keys and broker `name` are retained independently. Check 21 owns absent required broker fields (`name`, `nodeid`, `source`, `state`, `req_timeouts`, `txretries`, `txerrs`, `rxerrs`, `disconnects`, `throttle.cnt`, `throttle.max`, `rtt.cnt`, `rtt.p99`); a present field with the wrong kind routes to check 20. Native node IDs are Int64. `source` and `state` are strings. Native units and selected fields follow [librdkafka 2.16.0 statistics documentation](https://github.com/confluentinc/librdkafka/blob/v2.16.0/STATISTICS.md); the verifier does not compare native clocks with host time or apply check 22-26 semantics in PR 3.

## Outputs and process outcomes

The start-line note and result projection follows the PR 3 [schema and codec plan](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245697297) and Hari's [later corrections](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245827595), with literal codec cases R1-R9. Start-line notes and verify results use schema version 1 and explicit snake_case projections. Diagnostic snippets are subject to the configured retention limit; if shortened during retention, that does not alter the failed-check list. Result codecs reject output projections whose byte, per-check record or snippet-byte bounds are exceeded; they do not truncate the encoded result. Readers report malformed result shape without assigning a run check. The codecs copy supplied fields and do not compute verdicts, counts, configuration differences, hashes or probe predicates.

Result provenance separates the producer under test from the verifier. `generator_version` and `runtime_versions` are copied unchanged from the producer manifest. `verifier_commit`, `verifier_confluent_kafka_version`, and `verifier_librdkafka_version` describe the verifier itself. The producer's Confluent.Kafka and librdkafka versions are in the copied `runtime_versions` map, not substituted with the verifier's versions. The start-line note separately records verifier commit and verifier client versions.

`status` is exactly `complete_valid`, `invalid`, or `incomplete` and is copied without aggregation. The six top-level outcome keys (`ok`, `loss`, `phantom`, `reported_failure`, `duplicate`, `reorder`) appear only for `complete_valid`, where counts are required. They are absent for `invalid` and `incomplete`, never null or zero. There is no global `check_assessments` property: the supplied fidelity assessment is nested at `configuration_fidelity.assessment`. Failed check numbers and diagnostic records are separate; diagnostic retention cannot alter the failed-check list.

Absent boundaries are omitted; an observed empty start/end array remains `[]`. Durations are JSON integer milliseconds, truncated toward zero. `drain_time` and `drain_elapsed_at_stop` are mutually exclusive. A lower-bound stop duration uses the sibling `drain_elapsed_at_stop_lower_bound: true`; absent duration means no duration or lower-bound keys. Optional measurement values are omitted when unavailable, not synthesized as zero. Explicit nullable members in the accepted output projection are emitted as JSON null where specified by the output interface.

Exit codes are 0 for success, 1 for any other ordinary outcome, and 124 only for the process watchdog. In PR 3, all three configured mode handlers are unavailable, so every mode fails nonzero without output. When future handlers land, `start-line` succeeds only after its note is written; `verify` succeeds only for `complete_valid` after successful execution; `probe-gate` succeeds after writing `pass`, `untestable_at_build_scale`, or `inconclusive`. Invalid or incomplete verify results exit 1.

Budget expiry follows Hari's O1 correction. In `verify`, safety stop is check 10 and token, metadata or watermark deadline is check 11: these write an `incomplete` result, include the owning failed check, preserve `drain_elapsed_at_stop` when applicable, omit outcome counts, and exit 1. Every other budget expiry is an execution failure with no result file and a nonzero exit, including Blob I/O, cleanup, process lifetime, and any expiry in `start-line` or `probe-gate`. Process-lifetime expiry is the watchdog and exits 124. A result codec may round-trip a lower-bound duration as projection data; that does not permit publishing a result after another execution failure.

The H7 watchdog proof is a child-process test: the test executable re-invokes itself, blocks work or cleanup under a test-only marker, advances a synthetic `TimeProvider`, and asserts child exit 124 with no output artifact. It is process-level verification outside the unit layer's no-I/O rule; it does not terminate the test runner and adds no production watchdog bypass. H8 was removed from PR 3 because none of the operation-budget handlers exists yet; budget-expiry tests, including O1's incomplete-result versus execution-failure cases, belong with PR 5. PR 3 keeps H1-H7 and H9, including the strict options-sum case H3.

The prescribed `Common/` layout is populated in PR 3 for passive contracts, strict JSON support, and window/result codecs shared by future modes. Captured-input DTOs remain under `VerifyRun/Input`, following the repository's [folder namespace rule](../engineering/dotnet.md#vertical-slices). Populating `Common/` in this PR is an accepted, specific exception to the general rule that it is populated only when two slices need shared behavior. The exception is explicit in the [approved package plan](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245827595); no other speculative shared service is introduced.

## Ownership and deferred work

PR 3 owns foundation contracts, parsers, codecs, host/options validation and watchdog, plus the Stryker tool/config. PR 4 owns checks 1-6 and 12-28. PR 5 owns Kafka and storage operations, start-line and verify handlers, and checks 7-11. PR 6 owns probe-gate and checks 29-32.

O1-O4 are answered in Hari's [correction](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245737973), and the later review fixes are in [issue comment 6245827595](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/80#issuecomment-6245827595). No PR 3 contract question remains open. Non-safety production budgets remain runner inputs; PR 6 owns the final mutation break threshold decision from measured scores; a new adapter requires its own exact pinned approval. Azure permissions, live behavior and handler acceptance remain outside this foundation contract.
