Unreachable cases:
- `ItemStatus` on an empty set returns `complete_valid` (`All` over nothing is true). The handler cannot reach it: each item has two or three configurations and `JudgeConfigurationAsync` always returns a result, so the set is never empty. The theory still pins the value.
- In the phase module's gap reason, `judge_<outcome>` and `judge_exit_<code>` are mutually exclusive (the first needs an outcome other than `complete`, the second needs `complete`), so swapping those two branches is an equivalent mutant and no test can tell them apart. The other two swaps of the three branches were tried by hand against the tests and each made them fail.
- `last <= first` (the guard in `Windows`) cannot be reached through `JudgeRepeat`. Once the 20000 ms start slack, the 20000 ms end slack and the 420000 ms span hold, the last idle report is at least 380000 ms after the first, so `last > first` for any non-decreasing series. The clause is a safety guard (`reports[-1]` would otherwise be indexed), not a judgement. No test is written for it.
- The plan's "Least sure" notes that `Q` is read up to one 15000 ms interval before the disconnect, so a close just after traffic sent since the earlier report can still count as `idle_timed`. No test can show otherwise without real reports.

## Departures from the plan text

1. `values.schema.json` gained a `capture_pods` string property (minLength 1), because the runtime object has `additionalProperties: false`.
2. Phase state entries record `{item, configuration: "judge", accepted, transport_valid, candidate, judge_completion}`, because `Phase.report()` reads those keys. Gap files are named `{item}-judge-gap.json`.
3. `capture_complete` also requires `metadata.uid` to match `[0-9A-Za-z._-]+`, so a uid with `:` or `,` cannot break the judge's `CapturePods` option.
4. `IdleObservation.values()` is split into `values()` and a shared `runtime()`, so `judge_values()` works when A04 is not selected. `idle_observation.py` carries its own strict JSON reader, because it cannot import `phase.single_action_json`.
5. The judge resolves settings for the expected client id `<pod>-r<ordinal>`, not `repeat.ClientId`; a mismatched captured id already makes the repeat `invalid` with `idle_identity`. Read failures map to `idle_wire`, then `idle_capture_limit`, then `idle_capture_missing` in that priority. The plan does not give that order. The telemetry `ScenarioId` is the literal `idle-observation`.
6. `tests/Parchwell.Verifier.Tests/IdleObservation/IdleFixture.cs` is a test helper that the plan does not name as a file.
7. Not run here: the full `verify-dotnet.sh` beyond `Parchwell.Kafka.Tests`, the Docker-dependent tests, and the live judge Job. The batch dispatch and the hosted mutation campaign follow the merge under the #301 override decision.
