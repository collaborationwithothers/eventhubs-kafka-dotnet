# Archive readiness smoke

The archive smoke prepares live evidence for the proposed persistent evidence archive. It transfers a small synthetic Blob fixture between the real ephemeral and persistent storage accounts, checks create-only conflict behavior and verifies the destination bytes. It does not run Kafka workers or establish scientific results.

The [preparation decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/494#issuecomment-6894417226) authorizes code, offline tests and a reviewable prerequisite PR. It grants no deployment, spending, persistent apply or workflow dispatch. The [product specification R3](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/f96eab914d00c06484431ff67a1808fb331c7e13/items/494/plan-observability-evidence.md), read with that decision's receipt correction, was subsequently [approved for implementation](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/494#issuecomment-6899146479) with named live risks accepted as unverified. Its feature-activation and publication checks remain required.

Hari subsequently [accepted the dated smoke cost estimate](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/494#issuecomment-6897041922). After the first smoke failed at source creation, he [authorized the diagnostic follow-up](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/494#issuecomment-6897941549) to retain enough evidence for the next controlled attempt and fix confirmed faults. That work keeps the original transfer and completion checks.

## Before deployment

Hari reviews and merges the protected changes, approves a dated cost estimate and plans/applies `infra/persistent`. Only Hari executes that root. Replace the private `PARCHWELL_PERSISTENT_OUTPUTS` environment secret with the new Terraform output JSON, keeping its IDs and exporter configuration out of public artifacts.

The new `evidence_archive` output has exactly `storage_account_id`, `account_name`, `blob_service_uri`, `container_name`, `container_id` and `retention_days`. A separate sensitive `workflow_principal_id` output exposes the existing workflow principal to the ephemeral root through its private remote-state reference. It is not an agent identity or a new credential. The workflow identity also needs its existing backend, resource-management and role-assignment permissions; a mock plan cannot establish effective access.

The runner operator must supply Azure CLI 2.92.0 with its own Python environment containing `azure-storage-blob` 12.29.0b1. The probe verifies both versions and the interpreter path, and fails closed on a mismatch rather than installing or upgrading them. The pins follow the [CLI release](https://github.com/Azure/azure-cli/releases/tag/azure-cli-2.92.0), its [Linux dependency](https://github.com/Azure/azure-cli/blob/azure-cli-2.92.0/src/azure-cli/requirements.py3.Linux.txt#L91) and [Python-location formatter](https://github.com/Azure/azure-cli/blob/azure-cli-2.92.0/src/azure-cli-core/azure/cli/core/util.py#L442).

Persistent archive capacity, its private endpoint and transactions are paid resources. The smoke's existing ephemeral Terraform root also creates a Premium Event Hubs namespace and other normal ephemeral resources, although no Kafka workload runs. Price those resources and expected execution/retention time before authorizing a dispatch. The dated retail illustration in the product specification is an estimate, not a spending approval or measured invoice.

## Authorized execution

After those prerequisites, Hari or a separately authorized successor may dispatch [Archive smoke](../../.github/workflows/archive-smoke.yml) on `main`. It has no other trigger or user-controlled workload selection. Use one controlled dispatch, one phase and one positive/negative fixture pair; retain failure evidence rather than automatically rerunning it.

The workflow shares the existing ephemeral concurrency group and environment-bound OIDC identity. It prepares private inputs, enables the serialized renewable Azure CLI wrapper and runs version/configuration preflight before ephemeral provisioning. It then uses the existing lifecycle init, plan and apply commands, followed immediately by the existing private DNS check and storage-readiness wait. It does not apply persistent Terraform or start AKS.

Only this workflow enables `TF_VAR_archive_smoke_enabled=true`. Its temporary `archive-smoke-source` container gives the existing workflow principal Blob Data Contributor on that container, allowing a synthetic fixture to be seeded without an account-wide grant. The archive grant is limited to `run-evidence`. Ordinary scenarios retain the default `false`; they do not create the source container or consume its new principal output. A default-config sweeper destroy still removes the smoke resources recorded in ephemeral state.

The probe commands are fixed:

```sh
python3 infra/scripts/archive/smoke.py preflight
python3 infra/scripts/archive/smoke.py run
```

These are live workflow operations, not agent-session verification commands. They read the private prepared `phase.json`, `persistent-output.json` and, for `run`, the applied `ephemeral-output.json`. Account endpoints and container identities come from those validated files. No connection string, access key, SAS URL or agent service principal is accepted.

The fixture is synthetic and bounded to 8192 bytes by the preparation scope. The probe verifies its source ETag, length and SHA256; conditionally creates the destination; independently reads it back; deliberately attempts another create; checks the expected conflict; and verifies unchanged content. A failed negative check is not success merely because a CLI command failed. Fresh CLI processes exercise new connections; evidence must identify actual execution conditions rather than treating an offline fixture as a deployed observation.

## Controls and public evidence

The product archive manifest, completion-marker and public-receipt contracts are pinned in the linked specification and adopted correction. The canonical manifest has `completion:null`; its readiness describes data verification. A separately verified completion marker and matching true receipt are also required before the probe reports complete retained evidence.

A false receipt has `completion:null` and an approved gap. It can reference independently verified canonical bytes whether their `archive_complete` is true or false. Failure after canonical verification never rewrites those immutable bytes or permits publication. The smoke identifies `run_kind=smoke`, `purpose=archive-readiness` and `scientific_admissible=false`.

Private spooling remains outside artifact staging. GitHub receives only these fixed small files, with the existing 90-day artifact policy:

- `archive/archive-smoke.json`: checks, observed byte count, duration and gaps.
- `archive/archive-manifest.json`: canonical bytes when available.
- `archive/archive-receipt.json`: verified control references or an explicit incomplete state.

The original synthetic destination fixture and remote controls remain under the run-scoped archive prefix for lifecycle processing. Source fixture cleanup is part of destroying the complete ephemeral layer. No production event body, claim-check body, backend configuration or CLI error dump is uploaded.

An archive command has a 600-second monotonic deadline, including SDK requests/backoff and hashing. A subprocess also has the existing 60-second invocation bound and a child file-size limit of 256 MiB. There is one helper pass, without an outer transfer retry. The intentional negative probe is a distinct bounded check. Native retries are still enabled in the [pinned SDK policy](https://github.com/Azure/azure-sdk-for-python/blob/azure-storage-blob_12.29.0b1/sdk/storage/azure-storage-blob/azure/storage/blob/_shared/policies.py#L593-L635); one CLI call is not one HTTP request.

The persistent Hot/LRS account disables public access, shared keys, versioning and Blob/container soft delete. Its `run-evidence` creation-age deletion policy is 90 days, as supported by the [pinned AVM inputs](https://github.com/Azure/terraform-azurerm-avm-res-storage-storageaccount/blob/5695e5ec21744a3765051677d9e82bfba16b5d98/variables.management_policy.tf). Azure processes lifecycle actions periodically; this is not a promise of deletion at the exact 90-day instant ([official lifecycle behavior](https://learn.microsoft.com/en-us/azure/storage/blobs/lifecycle-management-overview)).

## Failure and continuation

### Diagnose the failed operation

Read `archive-smoke.json` first. Its additive `diagnostics` array records the ordered CLI operations against `source` and `archive`, distinguishing the fixture, manifest and completion objects. Each entry carries its UTC start, elapsed time, outcome, return code, category, recognized terminal exception/service code, last recognized HTTP status and request ID when available. Unknown fields remain null. `expected_negative` labels only the pre-create not-found and deliberate create-conflict results that the protocol actually accepted. An unexpected source conflict remains a failure. Wrapper stage observations distinguish lock, token request, login, account selection and real-command execution. The archive job opts into these stage observations with `PARCHWELL_AZ_SESSION_DIAGNOSTICS=true`; other workflow jobs retain their existing selection behavior.

The CLI debug stream is bounded and parsed privately in memory. Public evidence contains fixed diagnostic labels and validated numeric/request-ID fields, never raw command output, messages, stack traces, tokens, URLs or private paths. Quiet authentication commands also drain their error output without publishing it; recognized AADSTS labels and stage exit status are retained. The accepted upload options and their SDK forwarding are defined by the pinned CLI's [argument registration](https://github.com/Azure/azure-cli/blob/azure-cli-2.92.0/src/azure-cli/azure/cli/command_modules/storage/_params.py) and [upload implementation](https://github.com/Azure/azure-cli/blob/azure-cli-2.92.0/src/azure-cli/azure/cli/command_modules/storage/operations/blob.py#L644-L716).

Debug commands use `--debug` without `--only-show-errors`. The CLI's pinned Knack 0.14.0 [verbosity validator](https://github.com/microsoft/knack/blob/v0.14.0/knack/log.py#L135-L148) rejects that combination before command execution. The probe classifies this local option conflict as `arguments`; absent Storage logs are not needed to identify it.

After a failed transfer's control-publication attempt, `sdk_diagnostic` and `network_diagnostic` record separate observations for both validated targets, prioritizing the failed target. They run within the existing global deadline and explicitly report unavailable, interrupted, timeout or skipped observations. They do not retry a write or change the original failure's completeness.

The SDK observation obtains a token through the existing serialized CLI session and passes the token and its actual expiry to the CLI's Python interpreter through standard input. It performs a container-properties read with retries disabled and bounded connection/read timeouts. It retains recognized exception chains, including `inner_exception`, errno, service code, HTTP status and request ID. Sources: the pinned CLI's [token output](https://github.com/Azure/azure-cli/blob/azure-cli-2.92.0/src/azure-cli/azure/cli/command_modules/profile/custom.py), the pinned Blob SDK's [client and transport construction](https://github.com/Azure/azure-sdk-for-python/blob/azure-storage-blob_12.29.0b1/sdk/storage/azure-storage-blob/azure/storage/blob/_shared/base_client.py) and [retry policy](https://github.com/Azure/azure-sdk-for-python/blob/azure-storage-blob_12.29.0b1/sdk/storage/azure-storage-blob/azure/storage/blob/_shared/policies.py), and the CLI's [dependency pins](https://github.com/Azure/azure-cli/blob/azure-cli-2.92.0/src/azure-cli/requirements.py3.Linux.txt).

The network observation performs DNS resolution, then TCP and TLS checks against the first returned address, publishing outcomes and errno without addresses. TLS failures retain a recognized failure kind/reason and bounded certificate verification code, without certificate contents or exception messages. It sends no HTTP request. A successful supplemental read or connection does not establish the path or authorization of the earlier upload. A missing request ID or an empty `StorageBlobLogs` query does not prove that Storage received no request.

Correlate an original operation's UTC timing and request ID with existing service logs when available, using the recorded wrapper and client stages to investigate failures before a service response. The [first failed attempt](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/494#issuecomment-6897893730) retained only `transport / source create`; its root cause remains unknown. A later diagnostic observation must not be presented as a recovered error from that attempt.

### Preserve evidence and cleanup

The probe returns 0 for verified completion, 1 for an incomplete transfer/evidence check and 2 for unsupported or invalid configuration. Available failure evidence remains explicit. Ephemeral destroy and the independent dispatch-end AKS stop still run after failures where the runner survives. The sweeper recognizes this workflow's active runs and completion time; runner loss is not proof that cleanup executed.

Before claiming readiness, inspect source/destination access, private DNS/routing, deployed CLI/SDK/interpreter versions, exact observed bytes and timings, the classified conflict, independent hashes and both cleanup outcomes. Record whether connections were fresh or already open and whether the system was idle or under load. A tiny synthetic transfer does not establish feasibility at the product archive's maximum volume, metadata capture, Kafka telemetry reception or backend metric limits.

If a prerequisite is missing or the one dispatch fails, preserve diagnostics and hand off the specific finding. No automatic replacement dispatch, broader role, public endpoint, timeout increase or scientific rerun is authorized. The future archive, telemetry and inline duplicate-reporting PRs remain separate work. Agent Azure identities stay in [the separate identity issue](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/496).


## Phase evidence retention

The first product entry in the approved specification adds bounded phase retention to the existing scenario workflow. Before worker deletion and ephemeral destruction, each prepared workload invokes:

```sh
bash infra/scripts/phase/phase.sh archive
```

The zero-argument command reads the archive destination frozen from validated persistent outputs and sources frozen from lifecycle outputs. It uses the existing serialized workflow CLI session. No agent identity, access key, SAS URL or arbitrary destination is accepted. The raw spool is `PARCHWELL_ARCHIVE_DIRECTORY` under the private phase directory; only the canonical manifest and public receipt are staged under `PARCHWELL_ARCHIVE_MANIFEST_DIRECTORY`. Never upload the private spool as pod evidence.

Batch manifests use the frozen aggregate phase name as their string configuration identifier; each capture and published source keeps its own actual scenario/configuration binding. Pod diagnostics retain an allowlist of pod name/UID, phase, finite conditions and container termination outcomes; environment values, annotations, volumes and exception messages are excluded.

Inventory comes from the selected run/phase and published registration/index/reference contracts. An absent expected publication or capture is an explicit gap; a listing of the available files cannot establish completeness. Unselected or genuinely unstarted units remain distinguishable from required missing evidence. Retain producer bookkeeping and raw statistics, verifier per-repeat/phase evidence, distinct consumed-metadata captures and the bounded approved runner diagnostics. Exclude claim-check and explicit message-value bodies, backend configuration files and credential material. The diagnostic-text exception below retains the accepted residual risk in free-text messages.

The [metadata-only retention amendment](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/494#issuecomment-6900154350) applies to legacy single-action captures and V2 structured stdout that contain message bodies. Retain a distinct `source_metadata_projection` envelope with the original source identity, byte count and SHA256, plus the permitted metadata. Body values become null/length/hash metadata; ordered header values and native statistics remain intact. Verify the original source before projection and independently verify the projected archive bytes. Required malformed, missing or truncated sources remain gaps. Original body-bearing bytes stay out of the archive and public staging; existing scientific publications and readers retain their contracts. The [candidate extension](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/494#issuecomment-6914458649) applies the same archive-only rule to V2 candidates containing `repeats[*].read_observation.record.value_base64`, using projection format `probe_v2_candidate`. Its original source length/hash and judge-receipt hash are verified before projection; the distinct `.metadata.json` copy has independent length/hash/readback verification. Scientific candidate bytes and readers remain unchanged. A missing required reference or malformed candidate remains a gap with no raw-body fallback. The source-size bound follows the existing [candidate runtime limit](probe-v2-runtime-limits.json).

The [later diagnostic-retention decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/494#issuecomment-6913599161) keeps free-text native/client log messages, diagnostics and error reasons. Do not replace them with hashes alone. Hari accepted that unlabelled text may contain sensitive content; no production leak was established, and assignment-pattern checks do not prove every message safe. Existing producer redaction and recognized sensitive-assignment checks remain. This exception does not admit malformed source formats, incomplete collection or explicit message-value bodies, and does not authorize collecting credentials or publishing raw diagnostic payloads in public issue comments.

The fixed limits and exact wire schemas are owned by the [approved specification](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/f96eab914d00c06484431ff67a1808fb331c7e13/items/494/plan-observability-evidence.md#resource-and-work-bounds). A transfer has one helper pass under the aggregate deadline; native SDK retries consume the same process/global deadlines. Source and destination downloads are ETag-conditional and bounded, uploads are create-only, and destination acceptance requires independent length/SHA256 readback. Existing matching destinations still require readback; conflicting bytes are never overwritten. No outer helper retry or mutable latest pointer is added.

The canonical manifest always has `completion:null`. Its `archive_complete` describes the expected data/capture inventory. A true public receipt additionally requires verified canonical and completion-marker references. A false receipt has an approved gap and `completion:null`; it may reference independently verified canonical bytes whose `archive_complete` is true or false. A failed marker never rewrites those immutable canonical bytes. No successful publication follows from a marker's existence alone.

Before preparing a future evidence pack, derive its expected contributing run contexts independently from the pack's selected executions, including the source commit, candidate scenario/configuration and image digests. Recover each contribution's manifest, marker and receipt bytes. Pass the expected contexts and supplied controls to `infra/scripts/phase/archive_pack.py`'s `verify_pack`, using `archive.verify_controls` as the control verifier. Require its `complete` result and retain the reported missing, extra, duplicate and invalid contributions. Internally consistent controls from another run cannot satisfy the pack's expected context. This check does not change an existing result, verdict or scientific eligibility.

Archive and public-upload failures remain visible separately from the original scientific/cleanup report. The original blocking report and job-result gates retain their previous scientific meaning; archive failure does not suppress an otherwise authorized later scientific phase. Both reports run after unconditional cleanup. A false/missing completion receipt still blocks the future complete-retained-evidence claim even where science completed successfully.

Consumed metadata is one bounded JSONL row per in-window record. It retains null/empty/binary keys and ordered headers, coordinates, timestamp type/value, decoded identity problems and payload SHA256/length without retaining the payload. Each actual drain has its own monotonically indexed capture ID, including the legacy sweep's original/late windows. Empty completed windows emit an explicit capture manifest. A partial drain, row/byte/write/upload failure or interruption retains available sealed chunks and a sticky gap; missing capture publication is a gap rather than zero observations. This capture overhead is part of the measured system.

The [successful prerequisite smoke](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/actions/runs/43744609382) covers a synthetic 49-byte transfer and both cleanup outcomes. It does not establish full-volume capture/transfer feasibility, unknown load conditions or telemetry backend behavior. The [named-risk acceptance](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/494#issuecomment-6899146479) permits implementation while leaving the specified acceptance work in force. No new paid dispatch, persistent apply, protected merge or scientific publication is implied.
