# A01 runner contract

This is the operational contract for the synthetic A01 deployment. The [approved Revision 2 plan](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/114#issuecomment-6321098789), [adopted ten checks](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/109#issuecomment-6313658165) and [persistent storage/recovery decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/114#issuecomment-6332413257) authorize this implementation. [Blueprint section 9](../blueprint.md#9-security-and-identity) owns trust boundaries; [Kubernetes worker standards](../engineering/dotnet.md#kubernetes-workers) own image/chart policy. Offline fixtures establish local contracts, not Azure readiness or live findings. No output here is a verdict publication.

## Commands and inputs

Run the Release executable built at the approved full source SHA. Commands use explicit path arguments, never shell-generated command strings:

```sh
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll generate --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll phase --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll gate --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll export --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll destroy --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll sweep --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll rehearse --fixtures <wire-fixture-directory> --output <directory>
```

`generate` resolves only the A01 declaration/profile, never `expected.yaml`. It emits the unmodified version-1 verifier-context document, separate LoadGen/verifier comparison files and a runtime-only envelope. Runtime cannot override `contract_version`, `scenario_id`, `configuration_id`, `profile` or `kafka`. The [scenario contract](scenario-contract.md) and existing generator remain authoritative.

The runtime envelope projects only the LoadGen and Verifier service accounts from Terraform's workload-identity output. The enrichment-consumer account remains outside this chart. Each worker's generated-values path binds through its validated host options before the worker compares the document against its resolved scenario.

Runtime JSON has `schema_version:1`, `source_commit` (approved full SHA), `phase` (`probe`, `C0`, `C3`), deterministic phase/run identity, `ephemeral_outputs`/`persistent_outputs` matching [the Terraform output contract](terraform.md#output-contract), `images.loadgen`/`images.verifier` each with matching `source_commit` and immutable `digest`, `limits_file`, `service_tags_file`, `cost_file`, `backend_config`, `tfvars_file`, `readiness_file`, `ephemeral_root` (only `infra/ephemeral`), `scenario_root`, `chart_directory`, `helm_archive_file`, `helm_binary_file`, `kql_parameters_file`, `kql_source_file`, optional `actual_cost_file`, `environment_run_id`, `verifier_executable`/optional `verifier_arguments`, and explicit `initialize_ledger`. Deployment generation additionally uses `run_id`, `producer_pod_name`, mode (`loadgen`, `start-line`, `verify`) and independent `expected_broker_names`. `environment_run_id` is a DNS-safe identifier of at most 29 characters, leaving room for the fixed repeat suffix. Actual producer identity replaces the pre-admission placeholder before release. Prior phase receipts and gate inputs remain private. All real identifiers and credential inputs are supplied privately; examples/fixtures use documentation addresses and `example.invalid` only.

The committed [limits file](a01-runtime-limits.json) has schema version 1. `scenario_parsing`, `loadgen`, `verifier_shared`, `verifier_kafka`, `verifier_start_line`, `verifier_verify` and `verifier_gate` contain PascalCase worker option names; `execution` contains runner bounds. These are design ceilings, not measured capacity or new scientific thresholds. All applicable writable worker properties must be supplied by generated runtime or an explicit limit; unknown/missing properties fail coverage. TimeSpan values use invariant `hh:mm:ss[.fff]`. No test fixture provides a production fallback.

## Ten runner checks

1. **Deployment fidelity.** Resolve both workers independently and retain exact generated bytes/hashes, packaged definition/profile hashes, full source tag and resolved image digest. LoadGen uses the admitted producer name for every declared role. Verifier uses that producer name for LoadGenProducer and `<run-id>-verifier` for VerifierConsumer. Verify each worker's complete profile/Kafka equality before native construction. C0 request/socket/message timeouts are `60000/60000/300000`; C3 is `60000/20000/300000`.
2. **One independently admitted producer.** Establish list/watch at its returned resourceVersion before Job creation. Record all matching Pod names/UIDs through export; exactly one UID permits release. Lost/expired watch, replacement UID or a second nonproducing Pod invalidates the repeat. The worker waits before host construction for a matching bounded permit; no started/interrupted repeat is replaced.
3. **Independent brokers.** Start-line publishes metadata-derived inventory after native cleanup. Sort by ID and reject empty/duplicate/malformed inventories or more than 64 brokers. Both workers receive identical native broker names; statistics never supply a fallback. See [the verifier contract](verifier-contract.md#optional-deployment-inventory-and-completion).
4. **Explicit inputs/bounds.** Require every mode's options, identity/storage inputs and finite positive budgets from the limits/runtime files. Verifier workload-identity environment enters existing options only. Parser limits apply to every scenario caller. RequireStatisticsEvidence is true and RequireRequestEvidence false, derived from actual measures. Bounds stop execution and mark incomplete evidence; they never clip counts.
5. **Start-line and LoadGen completion.** Fix identity, complete start-line and release admission in that order. Actual LoadGen exit 0, normal completion receipt and all six original index-last publication objects are prerequisites for verify. Existing LoadGen bookkeeping remains the publication authority; see [its contract](loadgen-contract.md#optional-deployment-boundary).
6. **Verifier outcome and cleanup.** Actual exit, completion receipt and result identity/status must agree. Complete-valid/0/receipt permits counts. Invalid or incomplete/1/receipt retains diagnostics with counts absent. A result with exit 124, signal/OOM, failed cleanup, missing receipt or disagreement is unaccepted diagnostic evidence. A stored result never overrides a failed process.
7. **Probe gate.** Execute the actual built verifier locally in `probe-gate` mode with the five downloaded real results and independent admitted identities. Only `outcome=pass` plus exit 0 and normal receipt permits full C0 then C3. Inconclusive and untestable outcomes block them despite exit 0. Never select five of six or read expected outcomes.
8. **Cumulative cost reservation.** Compute decimal GBP spend from the persistent ledger, reserve phase estimate plus teardown allowance durably and read back before apply. Cumulative total `<=15` permits; `>15` blocks. Scheduled dispatch grants no new allowance. Unknown actual cost preserves the full reservation; unused headroom grants no repeats.
9. **Evidence before teardown.** Export original bytes privately, verify readback hash/size and publish immutable manifest last. Export failure still attempts guarded destroy and prevents a complete pack. Public candidates use an explicit allowlist, stable safe reason codes and subscription redaction; raw state, plans, identifiers, exception/query/log text and runtime files remain private.
10. **One environment and finite lifecycle.** Only the ephemeral root executes, in three phases with five repeats each and zero replacements. Shared workflow concurrency, existing backend locking and prior destruction receipts serialize mutators. A failed or unresolved cleanup prevents the next phase. No new Blob lease is introduced.

## Bounds and lifecycle

The exact literals live in [a01-runtime-limits.json](a01-runtime-limits.json). LoadGen/start-line/verify/gate execution watchdogs are respectively 660/120/720/60 seconds; Job deadlines are 840/150/750/90 seconds. Admission is 180 seconds; a repeat is at most 1500 seconds. The 9600-second phase includes up to five repeats, 900-second apply, 300-second export and 900-second destroy reserve. Phase workflow jobs allow 180 minutes and sweep jobs 30 minutes. These workflow caps do not extend Runner's bounds.

CLI/API calls allow 60 seconds and bounded output; read-only operations allow at most three attempts with delays 1/2 seconds inside that bound. Mutations have no retry. Store operations allow 180 seconds total. A watch allows 10000 events; each event/JSON document is at most 16 MiB. Evidence allows 8 GiB per phase, 256 MiB per downloaded producer artifact, 1 GiB per-repeat input and 16 MiB per container log. Ledger/manifest allow 1048576 bytes, with at most 256 manifest entries. KQL allows 10000 rows/16 MiB, at most three reads spaced 30 seconds within export. Over-limit data is visibly incomplete, never silently successful truncation.

Persist reservation, apply-started timestamp/expiry, repeat-started, worker outcomes, export and destruction receipts before advancing. Expiry is apply-started plus four hours; sweeper eligibility is strictly `now > expires-at`. A process killed after apply-started is recovered by workflow fallback and sweeper; `finally` is not a SIGKILL guarantee.

Normal cleanup and sweep capture exact run-id/expiry and state serial/lineage, export that generation, reread before destroy, create a saved destroy plan, inspect its prior-state tags and apply only that plan for the same generation. Any generation/state change blocks mutation, including A-cleaned/B-applied races. Missing/ambiguous tags fail closed. Empty state is idempotent already-destroyed, never permission to assume ledger ownership. Terraform locking stays enabled; never force unlock or target persistent resources.

Sweep collects fresh Terraform state and outputs, available scoped Kubernetes snapshots and logs, and the known worker Blob objects from that generation. Collection and private export share the existing export deadline. A fresh recovery directory prevents stale files from entering the snapshot. Recovery uses read-only cluster access and never creates Jobs, admission permits or namespaces. Kubeconfig remains outside the exported directory. The verified recovery manifest has a separate immutable path linked from the cleanup receipt; it never replaces the original phase manifest. Missing historical watch continuity remains explicit, with no accepted counts or replacement repeats. Failed collection or export still leads to a guarded cleanup attempt.

On a normal repeat failure, collect available worker originals before final private export and guarded teardown, including artifacts published before host cleanup or receipt writing failed. Preserve partial transfers and unavailable reasons as diagnostics. Artifact collection and corroboration each use an existing CLI/API deadline within the shared export budget, leaving time to upload available files. These records authorize no verification, accepted counts or replacement repeat. Downloaded originals use their canonical repeat paths so repeated local copies do not consume the phase manifest budget.

## Durable ledger and private export

Persistent `run_storage` is separate from both the external Terraform backend and ephemeral worker storage. Its authoritative state is `ledger/A01/state.json`, schema 1, fixed item/currency/source/baseline and nonnegative Int64 revision. Exactly three phase keys (`probe`, `C0`, `C3`) each retain five fixed repeat ordinals. Reservation IDs are `A01/<phase>`; repeat IDs are `<environment_run_id>-r<1..5>`. Unknown phase/repeat keys fail. Phase states are `not_started`, `reserved`, `apply_started`, `running`, `exported`, `destroyed`, `interrupted`; repeat states are `not_started`, `started`, `completed`, `interrupted`. A nullable actual cost never means zero.

Private cost input contains currency/item, immutable `baseline_spend_gbp`/`baseline_sources`, three `phase_estimates` each with phase and teardown allowances, a separate `persistent_estimate_gbp`, and sourced price lines (URL/retrieved time/unit/quantity/GBP unit price). Only explicit `initialize_ledger:true`, probe, absent blob, empty ephemeral state and sourced nonnegative baseline permit bootstrap. Create with `If-None-Match:*`; duplicate bootstrap is idempotent only for identical initialization. Changed source/baseline, absent state without bootstrap or unknown prior cost blocks apply. Started/completed phases never restart; a reservation without apply marker is interrupted conservatively, retained without apply or budget release. Reconciliation accepts only a received sourced actual GBP record scoped through settled teardown; it changes costs, never repeat eligibility.

Before reconciliation, preserve the received actual-cost file's original bytes at a verified content-addressed private path. Normalized ledger fields do not replace that source record.

Actual-cost records must cover both the primary phase resource group (`resource_scope`) and the separate AKS node resource group (`node_resource_scope`) in their combined `cost_gbp`. The node group contains the node VMs, networking and storage, as the [official AKS FAQ](https://github.com/MicrosoftDocs/azure-aks-docs/blob/6901de76c108a545a6b17fee61a39ca9e9e001d1/articles/aks/faq.yml#L110-L117) describes. After apply, retain the original `terraform show -json` bytes privately at `terraform/state.private.json`. Reconciliation verifies this file and the phase output against the immutable private manifest, matches the cluster ID, and derives the node group from the pinned module's exported `nodeResourceGroup` property; see its [resource output](https://github.com/Azure/terraform-azurerm-avm-res-containerservice-managedcluster/blob/4bc0128b057d10d5ed146a53d8c77933fd00ead8/main.tf#L12-L26) and [node-group outputs](https://github.com/Azure/terraform-azurerm-avm-res-containerservice-managedcluster/blob/4bc0128b057d10d5ed146a53d8c77933fd00ead8/outputs.tf#L98-L109). Missing, ambiguous or mismatched scope evidence leaves the full reservation in place. A primary-group-only record cannot settle phase costs.

Before phase execution, snapshot the exact runtime input and original sourced cost JSON into `private-provenance/` under the phase output. The cost snapshot includes price lines and the separate persistent estimate; reservation reads those same bytes. Runtime `private_provenance_directory` points to the workflow output containing the fixed named image and tool receipts accepted by `PrivateProvenanceCollector`. Probe retains its original image publication log. C0/C3 retain their image-reference readback log and receipts while reusing the probe image digests. The [pinned Azure CLI repository show registration](https://github.com/Azure/azure-cli/blob/da4c0548a2725ea3d08b1d94b8e7fa1b0b07256e/src/azure-cli/azure/cli/command_modules/acr/commands.py#L225-L230), [image argument](https://github.com/Azure/azure-cli/blob/da4c0548a2725ea3d08b1d94b8e7fa1b0b07256e/src/azure-cli/azure/cli/command_modules/acr/_params.py#L187-L190) and [read operation](https://github.com/Azure/azure-cli/blob/da4c0548a2725ea3d08b1d94b8e7fa1b0b07256e/src/azure-cli/azure/cli/command_modules/acr/repository.py#L259-L277) define that readback.

Runtime and cost documents use the existing 1 MiB document ceiling; named receipts use 16 MiB. The immutable phase manifest includes these private snapshots. Fallback export preserves available originals, records missing or invalid inputs in `private-provenance/status.json`, and records an incomplete receipt when provenance is incomplete. An already complete private phase export remains immutable. Process death before export can leave staged workflow provenance unavailable to a later sweeper; that recovery stays explicitly incomplete.

Production uses the existing workflow OIDC login and `az storage blob ... --auth-mode login`; no SAS/key lookup or fallback identity. Read properties/ETag, conditionally download, update with `--overwrite true --if-match`, bootstrap with `--if-none-match '*'`. Read back exact revision/bytes/hash before advancing. Conflict stops advancement without merge/retry. Uncertain write allows at most three bounded reads to establish identical intended bytes, otherwise preserve unresolved reservation. [Pinned Azure CLI option definitions](https://github.com/Azure/azure-cli/blob/da4c0548a2725ea3d08b1d94b8e7fa1b0b07256e/src/azure-cli/azure/cli/command_modules/storage/_params.py#L284-L289) support these preconditions; capture actual runner CLI version/help and test the options before deployment. Unsupported flags block use.

Export to persistent `evidence/A01/<environment_run_id>/...`, preserving paths/original bytes. Create files once, download/read back SHA-256 and size, then create manifest last. Existing objects are acceptable only on exact-byte equality. Record manifest path/hash and verified count/bytes in ledger; upload separate cleanup receipt after destroy, never rewrite the prior manifest. Failed export still destroys matching generation and records incomplete export. Raw private bytes are never GitHub artifacts. Only `candidate.json` can be uploaded; publication into `results/` belongs to a later verdict PR. Missing actual cost remains unavailable and prevents a complete verdict pack.

## Corroborating KQL

Retain [the original query](kql/a01-runtime.kql), its private parameter JSON (explicit start/end UTC and exact ephemeral Event Hubs namespace resource ID), bound query and original CLI JSON output privately. Typed datetime literals and a JSON-escaped resource ID are bound by code through subprocess argument lists, outside shell interpolation. Query `AZMSKafkaUserErrorLogs` and `AZMSDiagnosticErrorLogs` using [official table/column definitions](https://learn.microsoft.com/en-us/azure/event-hubs/monitor-event-hubs-reference). Kafka details use `Message`; diagnostic details use `ErrorMessage`/`ErrorCount`. [Kafka columns](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/azmskafkausererrorlogs#columns) and [diagnostic columns](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/azmsdiagnosticerrorlogs#columns) were checked on 2026-10-22. Missing tables are unavailable; absent/delayed rows are incomplete with a reason. Empty results never establish no errors. Captured worker statistics remain primary; no telemetry exporter is added.

## Binding the applied AKS cluster

Before any Kubernetes request, read the fresh Terraform `aks.id`/`aks.name` output, validate the managed-cluster ARM segments and matching name, and fetch non-admin credentials for that exact subscription/resource group/name into a fresh explicitly supplied private kubeconfig. The file is in a dedicated private sibling directory outside the export tree; it is never an evidence artifact. Every kubectl request and kubelogin conversion receives only that explicit `KUBECONFIG` overlay; inherited default contexts cannot select another cluster. Create/apply the explicit `parchwell` Namespace before the first producer list/watch, then establish watch before creating any worker.

`az aks get-credentials --file ... --overwrite-existing --format exec` uses the existing workflow login; [the pinned Azure CLI options](https://github.com/Azure/azure-cli/blob/da4c0548a2725ea3d08b1d94b8e7fa1b0b07256e/src/azure-cli/azure/cli/command_modules/acs/_params.py#L1096-L1103) define its explicit file/format and non-admin default. `kubelogin convert-kubeconfig -l azurecli --subscription ...` then binds token acquisition to that subscription. [The pinned kubelogin documentation](https://github.com/Azure/kubelogin/blob/bdf0e79b5a0ea6fe9fd3b7ada771378c344ad760/docs/book/src/concepts/login-modes/azurecli.md) states that this mode uses the existing Azure CLI login and manages no separate token cache; no new identity, credential provider or grant is introduced. An installed compatible kubelogin is a deployment prerequisite, with only its exact version/help receipts copied into private evidence (the kubeconfig and its directory are never copied) and unsupported flags failing before Kubernetes use. Adding this provisioned tool remains an approval-only prerequisite for Hari; the workflow introduces no floating installation.
