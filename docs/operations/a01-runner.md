# A01 runner contract

This is the operational contract for the synthetic A01 deployment. The [approved Revision 2 plan](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/114#issuecomment-6321098789), [adopted ten checks](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/109#issuecomment-6313658165) and [persistent storage/recovery decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/114#issuecomment-6332413257) authorize this implementation. [Blueprint section 9](../blueprint.md#9-security-and-identity) owns trust boundaries; [Kubernetes worker standards](../engineering/dotnet.md#kubernetes-workers) own image/chart policy. Offline fixtures establish local contracts, not Azure readiness or live findings. No output here is a verdict publication.

## Commands and inputs

For the live commands (`phase`, `gate`, `export`, `destroy`, `sweep`), run the Release executable built from the `main` head the workflow checked out; `generate` and `rehearse` run locally under Offline acceptance. Commands use explicit path arguments, never shell-generated command strings:

Staged Runner operations write a stderr line in the form `runner_execution_failed <stage> <Type> <reason-code>`, with the reason included only when the complete message contains only lowercase ASCII letters, underscores or colons; an optional safe inner chain follows on that same line. The stages `apply`, `repeat`, `export`, `destroy` and `sweep` identify operations. Unrecognized or absent-command failures retain the unscoped form `runner_execution_failed <Type> <reason-code>`. Consumed exceptions also report diagnostics; a safe diagnostic alone does not change a recovered path's result. Set the GitHub environment variable `PARCHWELL_DEBUG_FAILURES` to exactly `true` only for a diagnostic window, then remove it: this also prints the unredacted exception and the last 50 lines of captured stdout and stderr attached at failed command boundaries, using staged headers `runner_debug_exception <stage>` and `runner_debug_command <stage> <tool> <stream>`, and the scenario and sweeper workflows print the whole redirected Runner log on failure. Workflows mask only the three Azure IDs, so debug output can expose other identifiers, paths and command output; ordinary failure forwarding prints only lines beginning `runner_execution_failed`.

Cancellation during the apply sequence adds `terraform_command=init|plan|apply`, `cancellation=caller_cancellation|apply_deadline|command_deadline|cancellation_unknown`, and `cancellation_evidence=saved|unavailable` to that safe line. Caller cancellation takes precedence when the caller and shared apply deadline are both observed as cancelled. The Runner saves `terraform-apply-cancellation.private.json` under the phase export directory, containing scenario/run identity, the command, reason and partial stdout/stderr already read within the existing process output bounds. `capture_available=false` means the process boundary supplied no capture; empty streams then establish no absence of Terraform output. The capture uses an independent finite local-write deadline and is exported through the existing private evidence path, including when debug is disabled. A failed write leaves cancellation in force and reports evidence as unavailable. This diagnoses interruption; it does not establish which Azure operation stalled or release a state lock.

```sh
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll generate --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll phase --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll gate --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll export --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll destroy --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll sweep --input <private-runtime.json> --output <private-directory>
dotnet src/Parchwell.Runner/bin/Release/net10.0/Parchwell.Runner.dll rehearse --fixtures <wire-fixture-directory> --output <directory>
```

`generate` resolves only the A01 declaration/profile, never `expected.yaml`. It emits the unmodified version-1 verifier-context document, separate LoadGen/verifier comparison files and a runtime-only envelope. Runtime cannot override `contract_version`, `scenario_id`, `configuration_id`, `profile` or `kafka`. The [scenario contract](scenario-contract.md) and existing generator remain authoritative.

The runtime envelope projects only the LoadGen and Verifier service accounts from Terraform's workload-identity output. The enrichment-consumer account remains outside this chart. Each worker's generated-values path binds through its validated host options before the worker compares the document against its resolved scenario.

The [A01 network rule](../engineering/dotnet.md#kubernetes-workers) applies to this chart. The generated runtime retains `eventhubs_ip` and `blob_ip` as deployment data. The [scenario workflow](workflows/scenario.yml.txt) and its installed file change together in one pull request (AGENTS.md hard safety rule 8).

Runtime JSON has `schema_version:1`, `source_commit` (the `main` head when the run started, written by the workflow), `phase` (`probe`, `C0`, `C3`), deterministic phase/run identity, `ephemeral_outputs`/`persistent_outputs` matching [the Terraform output contract](terraform.md#output-contract), `images.loadgen`/`images.verifier` each with matching `source_commit` and immutable `digest`, `limits_file`, `cost_file`, `backend_config`, `tfvars_file`, `readiness_file`, `ephemeral_root` (only `infra/ephemeral`), `scenario_root`, `chart_directory`, `helm_archive_file`, `helm_binary_file`, `kql_parameters_file`, `kql_source_file`, optional `actual_cost_file`, `environment_run_id`, `verifier_executable`/optional `verifier_arguments`, and explicit `initialize_ledger`. Phase execution also requires private `subscription_guid` in GUID D format for public redaction; the workflow sets it from `AZURE_SUBSCRIPTION_ID`, and Runner validates it before production transports are constructed. Deployment generation additionally uses `run_id`, `producer_pod_name`, mode (`loadgen`, `start-line`, `verify`) and independent `expected_broker_names`. `environment_run_id` is a DNS-safe identifier of at most 29 characters, leaving room for the fixed repeat suffix. Actual producer identity replaces the pre-admission placeholder before release. Prior phase receipts and gate inputs remain private. All real identifiers and credential inputs are supplied privately; examples/fixtures use documentation addresses and `example.invalid` only.

The committed [limits file](a01-runtime-limits.json) has schema version 1. `scenario_parsing`, `loadgen`, `verifier_shared`, `verifier_kafka`, `verifier_start_line`, `verifier_verify` and `verifier_gate` contain PascalCase worker option names; `execution` contains runner bounds. These are design ceilings, not measured capacity or new scientific thresholds. All applicable writable worker properties must be supplied by generated runtime or an explicit limit; unknown/missing properties fail coverage. TimeSpan values use invariant `hh:mm:ss[.fff]`. No test fixture provides a production fallback.

## Ten runner checks

1. **Deployment fidelity.** Resolve both workers independently and retain exact generated bytes/hashes, packaged definition/profile hashes, full source tag and resolved image digest. LoadGen uses the admitted producer name for every declared role. Verifier uses that producer name for LoadGenProducer and `<run-id>-verifier` for VerifierConsumer. Verify each worker's complete profile/Kafka equality before native construction. C0 request/socket/message timeouts are `60000/60000/300000`; C3 is `60000/20000/300000`.
2. **One independently admitted producer.** Establish list/watch at its returned resourceVersion before Job creation. Record all matching Pod names/UIDs through export; exactly one UID permits release. Lost/expired watch, replacement UID or a second nonproducing Pod invalidates the repeat. The worker waits before host construction for a matching bounded permit; no started/interrupted repeat is replaced.
3. **Independent brokers.** Start-line publishes metadata-derived inventory after native cleanup. Sort by ID and reject empty/duplicate/malformed inventories or more than 64 brokers. Both workers receive identical native broker names; statistics never supply a fallback. See [the verifier contract](verifier-contract.md#optional-deployment-inventory-and-completion).
4. **Explicit inputs/bounds.** Require every mode's options, identity/storage inputs and finite positive budgets from the limits/runtime files. Verifier workload-identity environment enters existing options only. Parser limits apply to every scenario caller. RequireStatisticsEvidence is true and RequireRequestEvidence false, derived from actual measures. Bounds stop execution and mark incomplete evidence; they never clip counts.
5. **Start-line and LoadGen completion.** Fix identity, complete start-line and release admission in that order. Actual LoadGen exit 0, normal completion receipt and all six original index-last publication objects are prerequisites for verify. Existing LoadGen bookkeeping remains the publication authority; see [its publication and storage contract](loadgen-contract.md#publication-and-storage-paths).
6. **Verifier outcome and cleanup.** Actual exit, completion receipt and result identity/status must agree. Complete-valid/0/receipt permits counts. Invalid or incomplete/1/receipt retains diagnostics with counts absent. A result with exit 124, signal/OOM, failed cleanup, missing receipt or disagreement is unaccepted diagnostic evidence. A stored result never overrides a failed process.
7. **Probe gate.** Execute the actual built verifier locally in `probe-gate` mode with the five downloaded real results and independent admitted identities. Only `outcome=pass` plus exit 0 and normal receipt permits full C0 then C3. Inconclusive and untestable outcomes block them despite exit 0. Never select five of six or read expected outcomes.
8. **Cumulative cost reservation.** Compute decimal GBP spend from the persistent ledger, reserve phase estimate plus teardown allowance durably and read back before apply. Cumulative total `<=15` permits; `>15` blocks. Scheduled dispatch grants no new allowance. Unknown actual cost preserves the full reservation; unused headroom grants no repeats.
9. **Evidence before teardown.** Export original bytes privately, verify readback hash/size and publish immutable manifest last. Export failure still attempts guarded destroy and prevents a complete pack. Public candidates use an explicit allowlist, stable safe reason codes and subscription redaction; raw state, plans, identifiers, exception/query/log text and runtime files remain private.
10. **One environment and finite lifecycle.** Only the ephemeral root executes, in three phases with five repeats each and zero replacements. Shared workflow concurrency, existing backend locking and prior destruction receipts serialize mutators. A failed or unresolved cleanup prevents the next phase. No new Blob lease is introduced.

## Bounds and lifecycle

The producer mounts its comparison document and admission file from one per-run
ConfigMap volume. After start-line, Runner patches the release JSON and both
final worker comparison documents in one request. Later start-line/verify chart
applications leave that admission ConfigMap untouched. After the atomic patch,
Runner updates an annotation on the independently observed producer Pod to
request immediate projection refresh. Kubernetes documents eventual mounted
ConfigMap updates and this annotation refresh mechanism in its
[pinned 1.35 source](https://github.com/kubernetes/website/blob/8817d358864b70a9710c5ad34f78df6a239be33d/content/en/docs/tasks/configure-pod-container/configure-pod-configmap.md#L743-L758).
This is not a network timing guarantee: the unchanged worker identity/hash checks
must pass before host construction, and delayed or mismatched release still
fails closed at its existing deadline.

One Runner admission deadline also spans producer creation, identity observation,
comparison generation, start-line and release/refresh. It is not reset between
those steps. Producer execution then uses the enclosing repeat deadline; neither
the annotation request nor a slow start-line extends the worker's admission
window or permits another repeat.

The exact literals live in [a01-runtime-limits.json](a01-runtime-limits.json). LoadGen/start-line/verify/gate execution watchdogs are respectively 900/120/720/60 seconds; Job deadlines are 1140/150/750/90 seconds. Admission is 180 seconds; a repeat is at most 1500 seconds. The 9750-second phase includes up to five repeats, 900-second apply, 300-second export and 1050-second destroy reserve. The phase work allowance remains 8400 seconds. The destroy allowance is 60 seconds above the 990-second teardown reported by Hari in [#140](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/140), a budget choice rather than a guarantee of future teardown duration. Phase workflow jobs allow 240 minutes and sweep jobs allow 60 minutes. [Scripted arithmetic](evidence/issue-140/raw/budget-arithmetic.txt) over the final workflow wrappers gives:

| Job | Shell wrappers | Python subprocess wrappers | Total | Job cap | Remainder |
|---|---:|---:|---:|---:|---:|
| probe | 12930 s | 1380 s | 14310 s | 14400 s | 90 s |
| full-C0 | 12840 s | 120 s | 12960 s | 14400 s | 1440 s |
| full-C3 | 12840 s | 120 s | 12960 s | 14400 s | 1440 s |
| sweep | 3090 s | 0 s | 3090 s | 3600 s | 510 s |

The probe's Python wrappers allow registry login 60 seconds and, per worker, publish 600 seconds plus digest read 60 seconds. Each full phase adds two 60-second registry readbacks. Unwrapped checkout, SDK setup, login, upload and other setup work shares the remainder, including Helm's existing 60-second `--max-time` download in scenario jobs. The probe's 90-second remainder is tight, not a guarantee that setup finishes within the job cap. The sweeper's kubelogin install remains non-fatal so a slow or failed download degrades only recovery export.

Open problem, not solved by these workflows: Entra issues the federated Azure CLI access token with a default lifetime that "is assigned a random value ranging between 60-90 minutes" ([Configurable token lifetimes](https://learn.microsoft.com/en-us/entra/identity-platform/configurable-token-lifetimes), "Access tokens", read 2026-10-22), and an Azure CLI maintainer states on [issue 28708](https://github.com/Azure/azure-cli/issues/28708#issuecomment-2047256166) that "An ID token lasts for 5 minutes on GitHub Actions and 10 minutes on Azure DevOps, but an access token lasts for 60 minutes", and the issue reports that the CLI cannot request new per-resource access tokens once the stored ID token has expired. Inferred from those two sources: the Runner requests Storage, AKS and Log Analytics tokens on demand, and in the probe job image publication (bounded at 1380 s) runs between login and the phase, so the first such request can fail at the start of the phase, not only in a long one. Applying the Entra default to this client is also an inference; the source says the lifetime varies by client and resource. The fix is [#124](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/124) and precedes the first live run. These workflow caps do not extend Runner's bounds.

CLI/API calls allow 60 seconds and bounded output; read-only operations allow at most three attempts with delays 1/2 seconds inside that bound. Runner does not reinvoke mutations. The [durable-store retry amendment](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/114#issuecomment-6336034219) permits the required Azure CLI's pinned SDK to retry conditional requests internally within the existing 60-second CLI and 180-second store-operation deadlines. A watch allows 10000 events; each event/JSON document is at most 16 MiB. Evidence allows 8 GiB per phase, 256 MiB per downloaded producer artifact, 1 GiB per-repeat input and 16 MiB per container log. Ledger/manifest allow 1048576 bytes, with at most 256 manifest entries. KQL allows 10000 rows/16 MiB, at most three reads spaced 30 seconds within export. Over-limit data is visibly incomplete, never silently successful truncation.

Before each original Blob transfer, normal, failed and recovery collection check its advertised length against both the individual ceiling and remaining repeat input space. Earlier start-line, inventory and publication originals consume that same space before later results. Configured byte budgets can lower these ceilings; they cannot raise them. The publication listing must contain the exact unique canonical members before any transfer. Zero-length originals remain valid at an exactly exhausted byte budget.

Persist reservation, apply-started timestamp/expiry, repeat-started, worker outcomes, export and destruction receipts before advancing. Expiry is apply-started plus four hours; sweeper eligibility is strictly `now > expires-at`. A process killed after apply-started is recovered by workflow fallback and sweeper; `finally` is not a SIGKILL guarantee.

Normal cleanup and sweep capture exact run-id/expiry and state serial/lineage, export that generation, reread before destroy, create a saved destroy plan, inspect its prior-state tags and apply only that plan for the same generation. Any generation/state change blocks mutation, including A-cleaned/B-applied races. Missing/ambiguous tags fail closed. Empty state is idempotent already-destroyed, never permission to assume ledger ownership. Terraform locking stays enabled; Runner cleanup and sweep never force unlock or target persistent resources.

If cleanup receipt persistence failed after teardown, a fresh sweep can finish it from empty state only for one unresolved, registered, applied and aged ledger phase. It rechecks empty state before recording `already_empty` under the existing cleanup budget. It preserves that phase's ownership, repeat outcomes and incomplete export; it neither destroys a new generation nor reconstructs missing evidence.

Sweep collects fresh Terraform state and outputs, available scoped Kubernetes snapshots and logs, and the known worker Blob objects from that generation. Collection and private export share the existing export deadline. A fresh recovery directory prevents stale files from entering the snapshot. Recovery uses read-only cluster access and never creates Jobs, admission permits or namespaces. Kubeconfig remains outside the exported directory. The verified recovery manifest has a separate immutable path linked from the cleanup receipt; it never replaces the original phase manifest. Missing historical watch continuity remains explicit, with no accepted counts or replacement repeats. Failed collection or export still leads to a guarded cleanup attempt.

On a normal repeat failure, collect available worker originals before final private export and guarded teardown, including artifacts published before host cleanup or receipt writing failed. Preserve partial transfers and unavailable reasons as diagnostics. Artifact collection and corroboration each use an existing CLI/API deadline within the shared export budget, leaving time to upload available files. These records authorize no verification, accepted counts or replacement repeat. Downloaded originals use their canonical repeat paths so repeated local copies do not consume the phase manifest budget.

Preserve already observed worker termination, raw pod response and available stdout/stderr even when a later result download or log retrieval fails. Failure retention uses the independent export token and attempts available files separately; a failed diagnostic write does not suppress the Blob collector or private export. An unavailable stdout is recorded as unavailable. Original Terraform output is retained at `terraform/outputs.private.json` before the dependent state read, so that read's failure cannot discard the received output.

## Durable ledger and private export

Persistent `run_storage` is separate from both the external Terraform backend and ephemeral worker storage. Its authoritative state is `ledger/A01/state.json`, schema 1, fixed item/currency/source/baseline and nonnegative Int64 revision. Exactly three phase keys (`probe`, `C0`, `C3`) each retain five fixed repeat ordinals. Reservation IDs are `A01/<phase>`; repeat IDs are `<environment_run_id>-r<1..5>`. Unknown phase/repeat keys fail. Phase states are `not_started`, `reserved`, `apply_started`, `running`, `exported`, `destroyed`, `interrupted`; repeat states are `not_started`, `started`, `completed`, `interrupted`. A nullable actual cost never means zero.

Private cost input contains currency/item, immutable `baseline_spend_gbp`/`baseline_sources`, three `phase_estimates` each with phase and teardown allowances, a separate `persistent_estimate_gbp`, and sourced price lines (URL/retrieved time/unit/quantity/GBP unit price). Only explicit `initialize_ledger:true`, probe, absent blob, empty ephemeral state and sourced nonnegative baseline permit bootstrap. Create with `If-None-Match:*`; duplicate bootstrap is idempotent only for identical initialization. Changed source/baseline, absent state without bootstrap or unknown prior cost blocks apply. Started/completed phases never restart; a reservation without apply marker is interrupted conservatively, retained without apply or budget release. Reconciliation accepts only a received sourced actual GBP record scoped through settled teardown; it changes costs, never repeat eligibility.

Before reconciliation, preserve the received actual-cost file's original bytes at a verified content-addressed private path. Normalized ledger fields do not replace that source record.

Actual-cost records must cover both the primary phase resource group (`resource_scope`) and the separate AKS node resource group (`node_resource_scope`) in their combined `cost_gbp`. The node group contains the node VMs, networking and storage, as the [official AKS FAQ](https://github.com/MicrosoftDocs/azure-aks-docs/blob/6901de76c108a545a6b17fee61a39ca9e9e001d1/articles/aks/faq.yml#L110-L117) describes. After apply, retain the original `terraform show -json` bytes privately at `terraform/state.private.json`. Reconciliation verifies this file and the phase output against the immutable private manifest, matches the cluster ID, and derives the node group from the pinned module's exported `nodeResourceGroup` property; see its [resource output](https://github.com/Azure/terraform-azurerm-avm-res-containerservice-managedcluster/blob/4bc0128b057d10d5ed146a53d8c77933fd00ead8/main.tf#L12-L26) and [node-group outputs](https://github.com/Azure/terraform-azurerm-avm-res-containerservice-managedcluster/blob/4bc0128b057d10d5ed146a53d8c77933fd00ead8/outputs.tf#L98-L109). Missing, ambiguous or mismatched scope evidence leaves the full reservation in place. A primary-group-only record cannot settle phase costs.

Before phase execution, snapshot the exact runtime input and original sourced cost JSON into `private-provenance/` under the phase output. The cost snapshot includes price lines and the separate persistent estimate; reservation reads those same bytes. Runtime `private_provenance_directory` points to the workflow output containing the fixed named image and tool receipts accepted by `PrivateProvenanceCollector`. Probe retains its original image publication log. C0/C3 retain their image-reference readback log and receipts while reusing the probe image digests. The [pinned Azure CLI repository show registration](https://github.com/Azure/azure-cli/blob/da4c0548a2725ea3d08b1d94b8e7fa1b0b07256e/src/azure-cli/azure/cli/command_modules/acr/commands.py#L225-L230), [image argument](https://github.com/Azure/azure-cli/blob/da4c0548a2725ea3d08b1d94b8e7fa1b0b07256e/src/azure-cli/azure/cli/command_modules/acr/_params.py#L187-L190) and [read operation](https://github.com/Azure/azure-cli/blob/da4c0548a2725ea3d08b1d94b8e7fa1b0b07256e/src/azure-cli/azure/cli/command_modules/acr/repository.py#L259-L277) define that readback.

Runtime and cost documents use the existing 1 MiB document ceiling; named receipts use 16 MiB. The immutable phase manifest includes these private snapshots. Fallback export preserves available originals, records missing or invalid inputs in `private-provenance/status.json`, and records an incomplete receipt when provenance is incomplete. An already complete private phase export remains immutable. Process death before export can leave staged workflow provenance unavailable to a later sweeper; that recovery stays explicitly incomplete.

Production uses the existing workflow OIDC login and `az storage blob ... --auth-mode login`; no SAS/key lookup or fallback identity. Read properties/ETag, conditionally download, update with `--overwrite true --if-match`, bootstrap with `--if-none-match '*'`. Read back exact revision/bytes/hash before advancing. Under the [approved retry amendment](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/114#issuecomment-6336034219), Runner invokes each write once; the required CLI may retain internal SDK conditional-request retries within the existing 60-second CLI and 180-second store-operation deadlines. For a ledger state transition, a CLI 412/conflict always stops ledger advancement without merging or reinvoking the write, including when an earlier request may have committed. Preserve reservations and available evidence. Other uncertain CLI outcomes allow at most three bounded reads with delays of 1 and 2 seconds to establish identical intended bytes; otherwise preserve the unresolved reservation. The [pinned CLI dependencies](https://github.com/Azure/azure-cli/blob/da4c0548a2725ea3d08b1d94b8e7fa1b0b07256e/src/azure-cli/requirements.py3.Linux.txt#L91) select Blob SDK 12.29.0b1; the [CLI upload path](https://github.com/Azure/azure-cli/blob/da4c0548a2725ea3d08b1d94b8e7fa1b0b07256e/src/azure-cli/azure/cli/command_modules/storage/operations/blob.py#L643-L707) delegates to that SDK, whose [retry policy](https://github.com/Azure/azure-sdk-for-python/blob/5eca695d87ce704eabe665ce42c698440521c289/sdk/storage/azure-storage-blob/azure/storage/blob/_shared/policies.py#L554-L590) can resend requests internally. [Pinned Azure CLI option definitions](https://github.com/Azure/azure-cli/blob/da4c0548a2725ea3d08b1d94b8e7fa1b0b07256e/src/azure-cli/azure/cli/command_modules/storage/_params.py#L284-L289) support these preconditions; capture actual runner CLI version/help and test the options before deployment. Unsupported flags block use.

Export to persistent `evidence/A01/<environment_run_id>/...`, preserving paths/original bytes. Create files once, download/read back SHA-256 and size, then create manifest last. The [original plan's private immutable evidence protocol](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/114#issuecomment-6321098789) remains unchanged by the [retry amendment](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/114#issuecomment-6336034219): a pre-existing evidence object is acceptable only after exact-byte/hash readback, without reuploading or merging after a conflict. Evidence export returns a verified receipt; it does not itself advance the ledger. Recording that receipt is a separate ledger transition subject to the ledger conflict-stop rule. Record manifest path/hash and verified count/bytes in ledger; upload separate cleanup receipt after destroy, never rewrite the prior manifest. Failed export still destroys matching generation and records incomplete export. Raw private bytes are never GitHub artifacts. Only `candidate.json` can be uploaded; publication into `results/` belongs to a later verdict PR. Missing actual cost remains unavailable and prevents a complete verdict pack.

The public candidate includes observed versions, source and image digests, apply-to-cleanup timings, the recorded gate outcome, execution status, stable reasons and available costs. Missing metadata stays null with an unavailable reason. Gate execution refreshes the candidate after both a new decision and a verified replay. The candidate never treats a runtime request or an unverified local result as observed provenance.

Candidate counts are phase totals of the verifier's six authoritative fields only when all five completed repeats have process-accepted `complete_valid` results. Otherwise the count fields stay null. Replay requires the durable accepted outcome and the original result's verified hash, source and identity. Diagnostic numeric fields summarize maxima across the recorded eligible windows; `rtt_p99_ms` converts the recorded microseconds to milliseconds. The `diagnostics_window_maxima` reason distinguishes these summaries from totals. Delivery error codes remain bounded observed codes. Unknown diagnostics stay unavailable; raw windows, broker names and result documents remain private. These summaries add no gate or verdict predicate.

Fresh gate dispatches and later candidate refreshes read result originals through the complete immutable phase export, checking its manifest and each file against the independent ledger hash and repeat identity. Gate inputs are materialized locally only after all originals pass. An existing partial or invalid export never falls back to local result files; unavailable candidate counts remain null.

### Resetting a spent phase

A phase runs once per ledger. [PhaseExecutor](../../src/Parchwell.Runner/Run/Execution/PhaseExecutor.cs) rejects an already started phase with `phase_already_started_recovery_only`; a destroyed phase returns `previous_incomplete` when its repeats or export are incomplete, or `already_completed` when complete. A reserved phase is conservatively interrupted with `reserved_phase_interrupted`. Redispatching the workflow does not make these phases eligible again.

The manual reset requested in [#137](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/137) belongs to Hari, outside Runner and the workflows. Before resetting, finish guarded recovery/teardown, verify the ephemeral Terraform state is empty, and preserve the original ledger and available private evidence. Hari deletes only the blob `A01/state.json` from the persistent run-storage account's `ledger` container, the path declared by [RunLedger.BlobPath](../../src/Parchwell.Runner/Run/Cost/RunLedger.cs). In the Azure portal, open the account's Containers view, select `ledger`, open `A01`, select `state.json` and confirm Delete ([official blob-deletion instructions](https://learn.microsoft.com/en-us/azure/storage/blobs/storage-quickstart-blobs-portal#delete-a-block-blob), read 2026-10-23).

A cancelled destroy can leave the ephemeral Terraform state blob leased, as reported in [#140](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/140). After confirming that no Terraform operation still owns that lock, Hari releases it before retrying with `terraform -chdir=infra/ephemeral force-unlock <LOCK_ID>`, using the same initialized private backend and the lock ID from the failure. Terraform's [pinned force-unlock command](https://github.com/hashicorp/terraform/blob/v1.16.6/internal/command/unlock.go) unlocks the configured state, and its [Azure backend](https://github.com/hashicorp/terraform/blob/v1.16.6/internal/backend/remote-state/azure/client.go) releases the Blob lease. Unlocking does not destroy resources or reset the ledger.

The account's committed baseline disables public network access and provides a Blob private endpoint and private DNS ([persistent storage configuration](../../infra/persistent/storage.tf)). Azure permits private-endpoint traffic while public network access is disabled; firewall network rules control the public endpoint ([private endpoints](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints), read 2026-10-23). For this manual operation, Hari temporarily enables public network access from selected networks and permits his own network, then removes that temporary permission and restores public network access to Disabled immediately afterwards. Adding an IP rule while public network access remains Disabled does not permit the connection ([public network access settings](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security-set-default-access), read 2026-10-23). Preserve prior A01 spend and unresolved reservations in that baseline; deletion grants no new GBP 15 allowance. Before reusing an `environment_run_id`, Hari must preserve the original private evidence and clear the entire `A01/<environment_run_id>/` blob-name prefix from the persistent run-storage account's `evidence` container, or use a fresh `environment_run_id` to preserve that prefix. Deleting the blob `A01/state.json` in the `ledger` container alone leaves those immutable export objects and can cause `private_export_readback_conflict` on reuse. Prefer a fresh run ID. No Runner or workflow reset capability is added.

## Renewable Azure CLI session

The [workflow templates](workflows/scenario.yml.txt) enable the [job-local `az` wrapper](../../scripts/azure-cli-session/az) immediately after the existing OIDC login, before image publication or readback. Runner, independent export/destroy/gate steps and the [sweeper](workflows/sweeper.yml.txt) inherit it through PATH. Nested kubelogin calls reach it through [kubelogin's Azure CLI credential](https://github.com/Azure/kubelogin/blob/b00ca2b4b43bf89bbbf149a67c74d55e63bd3bd5/pkg/internal/token/azureclicredential.go) and the [SDK's inherited process environment](https://github.com/Azure/azure-sdk-for-go/blob/f8bda5eb6b532d596c2b2fa858bae8290c8327e9/sdk/azidentity/developer_credential_util_nonwindows.go).

The wrapper obtains fresh assertions on demand through [GitHub's token-request interface](https://docs.github.com/en/actions/reference/security/oidc#methods-for-requesting-the-oidc-token), using the existing audience `api://AzureADTokenExchange`; the [pinned toolkit](https://github.com/actions/toolkit/blob/0c3a9c332b678ff1e776f93d728a4ad279803abe/packages/core/src/oidc-utils.ts) defines bearer authentication and audience encoding. A refresh performs [federated login and subscription selection](https://github.com/Azure/login/blob/7184910d9eb2b1c5e48f7073824a90609bb9b6d6/src/Cli/AzureCliLogin.ts) before forwarding the requested command once. The first normal invocation refreshes even after azure/login succeeded. Assertion expiry and resource access-token expiry are distinct ([CLI maintainer explanation](https://github.com/Azure/azure-cli/issues/28708#issuecomment-2047256166)). Entra validates the assertion; the helper reads its expiry only to schedule refresh.

The [approved policy](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/124#issuecomment-6351953474) requires login freshness strictly below 120 seconds from assertion-request start and at least 90 seconds of assertion life remaining, rechecked immediately before forwarding. These are helper policy thresholds, not measured token lifetimes. Lock waiting, assertion retrieval, login, subscription selection and forwarding consume the same configured 60-second invocation budget. The [workflow contract test](../../tests/Parchwell.Runner.Tests/Contracts/WorkflowAuthenticationContractTests.cs) guards `execution.api_seconds <= 60` in [runtime limits](a01-runtime-limits.json) against future drift; it does not remove lock/authentication overhead or extend any caller deadline. The [kubelogin timeout option](https://github.com/Azure/kubelogin/blob/b00ca2b4b43bf89bbbf149a67c74d55e63bd3bd5/pkg/internal/token/options.go) defaults to 60 seconds; the [SDK default](https://github.com/Azure/azure-sdk-for-go/blob/f8bda5eb6b532d596c2b2fa858bae8290c8327e9/sdk/azidentity/developer_credential_util.go) is 10 seconds only when the caller supplies no deadline.

An exclusive process-shared lock covers both authentication and the requested CLI process through exit and reaping. This follows the [maintainer's warning that Azure CLI does not support concurrent execution](https://github.com/Azure/azure-cli/issues/28708#issuecomment-2050827230). `PARCHWELL_AZ_SESSION_DIRECTORY` is a private sibling under `RUNNER_TEMP`, outside phase/export trees; it holds only the lock and atomic freshness metadata (`request_started_monotonic`, `assertion_exp`). Never export this directory or CLI credential caches. The wrapper stores no assertion, request bearer token or authentication output in its own files or evidence. Existing CLI credential storage remains in use ([CLI identity persistence](https://github.com/Azure/azure-cli/blob/8198e5e8f42b5e9f7d828b15548271fd83368005/src/azure-cli-core/azure/cli/core/auth/identity.py)).

Authentication failure leaves no freshness stamp and prevents the requested command. Diagnostics are fixed reasons without authentication output or underlying exception text. Under the [helper contract](../../scripts/azure-cli-session/az), timeout exits 124, configuration/authentication/expired-assertion/control rejection exits 1, and SIGINT/SIGTERM exits 130/143 after terminating and reaping the child process group. Forwarded commands preserve their argument boundaries, byte streams and exit status, including the JSON kubelogin consumes. A later independent fallback can attempt fresh authentication without retrying an uncertain earlier mutation. Exact `account clear` invalidates freshness and runs once under the lock without requesting an assertion, supporting [azure/login's PATH-based post-job cleanup](https://github.com/Azure/login/blob/7184910d9eb2b1c5e48f7073824a90609bb9b6d6/src/common/Utils.ts). Top-level `login`/`logout` and `account set`/`cloud set` prefixes are rejected; `acr login` and later literal arguments named `login` remain ordinary commands.

Export and guarded destroy require both prepared input and `steps.azure_session.outcome == 'success'`, using [GitHub's documented step outcomes](https://github.com/github/docs/blob/03d2e24b34bd88c361f1185f0aae1c46062c6510/content/actions/reference/workflows-and-actions/contexts.md#steps-context). Failed, cancelled or skipped setup therefore permits neither fallback workload. Setup precedes publication/readback and phase execution, so this job cannot have applied its generation when setup fails. After successful setup, later failure still permits export unless cancelled and permits guarded destroy even on cancellation. The sweeper retains default success handling. The existing azure/login credential cleanup is separate and may use the original CLI after setup failure.

Terraform's `azurerm` state backend and AzureRM/AzAPI providers have their own GitHub OIDC authentication paths, configured by `ARM_USE_OIDC` and the job's identity and token-request environment. Sources at the repository's [Terraform/provider pins](../../infra/ephemeral/versions.tf) are the backend's [OIDC environment mapping](https://github.com/hashicorp/terraform/blob/7b8f1669b95119ac6021e05c9d10eae7cf75f60b/internal/backend/remote-state/azure/backend.go) and [Storage/ARM authorizers](https://github.com/hashicorp/terraform/blob/7b8f1669b95119ac6021e05c9d10eae7cf75f60b/internal/backend/remote-state/azure/api_client.go), AzureRM's [configuration](https://github.com/hashicorp/terraform-provider-azurerm/blob/5782a75422c68a0d0804ac16d97dcaf3df5ee2fa/internal/provider/provider.go) and [GitHub OIDC guide](https://github.com/hashicorp/terraform-provider-azurerm/blob/5782a75422c68a0d0804ac16d97dcaf3df5ee2fa/website/docs/guides/service_principal_oidc.html.markdown), and AzAPI's [configuration](https://github.com/Azure/terraform-provider-azapi/blob/cf3ecee858fa48c0aca95d0b995a8bfd4950c8ec/internal/provider/provider.go) and [GitHub credential construction](https://github.com/Azure/terraform-provider-azapi/blob/cf3ecee858fa48c0aca95d0b995a8bfd4950c8ec/vendor/github.com/Azure/entrauth/aztfauth/aztfauth.go). The [workflow environment](workflows/scenario.yml.txt) supplies the existing identity references and `ARM_USE_OIDC`; [TerraformEnvironment](../../src/Parchwell.Runner/Run/Execution/TerraformEnvironment.cs) launches Terraform directly through [the process runner](../../src/Parchwell.Runner/Run/Execution/BoundedProcessRunner.cs), inheriting the job environment. Those upstream configurations also support CLI authentication. The wrapper renews Azure CLI sessions; it does not implement Terraform token renewal or establish that apply or destroy will succeed.

Success requires the compatible tool versions and private receipts declared above. CLI serialization and lock contention remain the main operational uncertainty: waiting can exhaust an existing deadline. Offline checks establish neither live session longevity nor Azure access; installation and live validation remain outstanding.
