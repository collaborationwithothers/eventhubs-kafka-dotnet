# D04: 10,000 brokered connections per PU

Event Hubs Premium documents a limit of 10,000 brokered connections per PU (processing unit, the unit of Premium capacity), so a namespace with 4 PUs allows 40,000. This item is traced from documentation because, in the inventory's words, it needs connection counts beyond build scale; the build namespace has 1 PU. The main finding is that the largest per-client broker counts published so far are 17 and 16, and no cited source says that one librdkafka connection counts as one brokered connection.

Sources were read on 2026-10-27. Line numbers refer to the linked commit or tag. "Inference" marks a statement that no cited source makes.

## Claim

The [tier limits page](https://github.com/MicrosoftDocs/azure-docs/blob/6da87e3c59251e962dd0b37dbd99ae364d767150/articles/event-hubs/includes/event-hubs-tier-limits.md) (ms.date 02/05/2026) has the row "Number of brokered connections per namespace" at line 25. For Premium it gives "10,000 per PU" and the example "if the namespace is assigned 4 PUs, the limit is 40,000".

## Why it is traced, not tested

The inventory reason in [docs/blueprint.md](../blueprint.md) section 12 is "D: needs connection counts beyond build scale".

The namespace has 1 PU (`capacity = 1`, [infra/ephemeral/eventhubs.tf](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/39e2cbba73f28855d3d0bbc3511d977294b8ba09/infra/ephemeral/eventhubs.tf) line 9). Inference: the build runs too few clients to approach 10,000 connections.

## Broker counts measured so far

Inventory amendment 1 folds "record the broker count in every evidence pack" into D04 (catalogue K-42, in the [catalogue](../research/kubernetes-kafka-clients.md) line 67 at commit 39e2cbb). The largest published per-client counts are 17 and 16.

- 17 is one consumer on `document-events`, configuration C1 ([C12 result](../../results/C12/2026-10-27.md)).
- 16 is the B04 producer ([B04 result](../../results/B04/2026-10-26.md)).

Both are lower bounds from librdkafka statistics. No cited source says one librdkafka connection is one brokered connection. K-42 lists the Event Hubs broker IDs as unconfirmed. Inference: if it is, 10,000 / 17 gives at most about 588 such consumers per PU (computed by script).

## Trace

- Design: [factory.md](../agents/factory.md) "Evidence pack" requires per-repeat broker connection counts for every Kafka client whose statistics a run captures.
- .NET code: the statistics bridge reads each broker's identity and state ([statistics-bridge.md](../operations/statistics-bridge.md) line 40 at commit 39e2cbb).
- Terraform: `capacity = 1` (eventhubs.tf line 9). The limit grows with PUs (tier limits page, line 25).
- Security: none. The item changes no identity, network or credential setting.
- Symptom: the tier limits page states no error for exceeding the limit, so the symptom is unknown.
- Detection: Inference: sum the per-client broker counts of every client and compare the total with 10,000 times the PU count.
- Runbook: assign more PUs (tier limits page, line 25).
