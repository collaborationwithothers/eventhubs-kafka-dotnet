# K08: VM freeze pauses

Microsoft says a scheduled Freeze event pauses the underlying VM for a few seconds, and librdkafka says a consumer is removed from its group when no heartbeat reaches the broker within the session timeout. This item is traced from documentation and design, not tested, because a platform freeze cannot be triggered. The main finding is that the baseline session timeout of 30000 ms is longer than "a few seconds", so by inference a freeze alone does not cause a rebalance, although no cited source gives a maximum freeze length.

Sources were read on 2026-10-27. Line numbers refer to the linked commit or tag. "Inference" marks a statement that no cited source makes.

## Claim

The AKS [node auto-drain page](https://github.com/MicrosoftDocs/azure-aks-docs/blob/1b2c1f91df475f8cb46f72cbf3ee125241523be8/articles/aks/node-auto-drain.md) (ms.date 03/30/2026) says at line 26 of the Freeze event: "The underlying virtual machine (VM) is scheduled to pause for a few seconds. CPU and network connectivity might be suspended, but there's no impact on memory or open files." Its action for the event is to opt in to "pod eviction on freeze events (preview)".

The inventory text adds that a rebalance follows only if a pause exceeds `session.timeout.ms`. The [librdkafka configuration reference](https://github.com/confluentinc/librdkafka/blob/v2.16.0/CONFIGURATION.md) (tag v2.16.0) supports the broker side of that at line 131: "If no hearts are received by the broker for a group member within the session timeout, the broker will remove the consumer from the group and trigger a rebalance." The quote keeps the source's spelling.

## Why it is traced, not tested

The inventory reason in [docs/blueprint.md](../blueprint.md) section 12 is "a platform freeze cannot be triggered". Nothing in the build can ask Azure for the event.

The Freeze text gives no number of seconds. Inference: a pause long enough to stop heartbeats for 30000 ms would not be called "a few seconds". The source does not state a maximum, so that reading is not confirmed.

## Trace

- Design: the baseline sets `session.timeout.ms` to 30000 ([BaselineSettingsCatalog.cs](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/39e2cbba73f28855d3d0bbc3511d977294b8ba09/src/Parchwell.Kafka/Configuration/BaselineSettingsCatalog.cs) line 147). librdkafka documents that the broker removes a member and triggers a rebalance when no heartbeat reaches it within that time (CONFIGURATION.md line 131).
- .NET code: none. A search of `src/` at the pinned commit for Scheduled Events and the instance metadata address finds nothing, so no code reads the event.
- Terraform: none. Pod eviction on freeze events is not configured.
- Security: none. The item changes no identity, network or credential setting.
- Symptom: Inference: a pause of a few seconds stays under 30000 ms, so heartbeats resume before the session timeout and no rebalance follows. The Freeze text says CPU and network connectivity might be suspended, so Inference: no heartbeat is sent during the pause.
- Detection: Inference: a consumer group rebalance with no pod restart, at the time of a Freeze event on the node.
- Runbook: Inference: keep the session timeout well above the longest pause. The build does not configure the preview option for pod eviction on freeze events (see Terraform above).
