# C16: 5,000 concurrent receive requests per event hub

Event Hubs documents a quota of 5,000 concurrent receive requests per event hub, shared by every consumer group, and says later receive requests are throttled. This item is traced from documentation because the build runs one node per pool and cannot hold that many receivers. The main finding is that no cited source says how a Kafka fetch maps to a receive request, so the quota's effect on a Kafka client is not documented in the sources read.

Sources were read on 2026-10-27. Line numbers refer to the linked commit or tag. "Inference" marks a statement that no cited source makes.

## Claim

The [common limits page](https://github.com/MicrosoftDocs/azure-docs/blob/6da87e3c59251e962dd0b37dbd99ae364d767150/articles/event-hubs/includes/event-hubs-common-limits.md) (ms.date 02/05/2026) has this row at line 30: "Number of concurrent receive requests on a hub/topic | Subsequent receive requests are throttled. This quota applies to the combined number of concurrent receive operations across all consumers/consumer groups | 5000".

## Why it is traced, not tested

The inventory reason in [docs/blueprint.md](../blueprint.md) section 12 is "D: needs client counts beyond build scale".

Each node pool has one node (`count_of = 1`, [infra/cluster/aks.tf](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/39e2cbba73f28855d3d0bbc3511d977294b8ba09/infra/cluster/aks.tf) lines 35, 44 and 51). No cited source says whether one Kafka fetch counts as one receive request. Inference: the mapping may not be one to one, so even a client count above 5,000 would not show that the quota was reached.

## Trace

- Design: the quota is per event hub, across every consumer group (common limits page, line 30).
- .NET code: none. The quota is a service limit and no application code reads or sets it.
- Terraform: none. The quota is a service limit with no setting in `infra/`.
- Security: none. The quota has no identity or network aspect.
- Symptom: "Subsequent receive requests are throttled" (common limits page, line 30). The [troubleshooting guide](https://github.com/MicrosoftDocs/azure-docs/blob/6da87e3c59251e962dd0b37dbd99ae364d767150/articles/event-hubs/apache-kafka-troubleshooting-guide.md) (ms.date 03/06/2025) says at line 18 that when a fetch request's delay exceeds the request timeout, Event Hubs "responds with empty set of records and no error code". Inference: the same response applies when this quota throttles receives; S2 describes it for excessive traffic.
- Detection: librdkafka reports `throttle` per broker, "Broker throttling time in milliseconds" ([STATISTICS.md](https://github.com/confluentinc/librdkafka/blob/v2.16.0/STATISTICS.md) line 115). The bridge exports it as `kafka.broker.throttle.max_ms` ([statistics-bridge.md](../operations/statistics-bridge.md) line 54), the signal H01 names. Inference: quota throttling and throughput throttling look the same there.
- Runbook: Inference, not tested: count receivers across every consumer group of the event hub and compare the total with 5,000.
