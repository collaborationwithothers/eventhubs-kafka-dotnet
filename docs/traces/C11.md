# C11: offset metadata over 1,024 bytes

Microsoft states that the maximum size of `offset.metadata.max.bytes` on Event Hubs for Apache Kafka is 1,024 bytes. This repository does not test the limit, because the pinned Confluent.Kafka client offers no way to attach metadata to an offset commit. The main finding is that the client's managed API and its native conversion carry only the topic, partition, offset and leader epoch, so a .NET client built on it has no commit metadata to measure.

Sources were read on 2026-10-27. Line numbers refer to the linked commit or tag. "Inference" marks a statement that no cited source makes.

## Claim

The [Apache Kafka troubleshooting guide for Event Hubs](https://github.com/MicrosoftDocs/azure-docs/blob/6da87e3c59251e962dd0b37dbd99ae364d767150/articles/event-hubs/apache-kafka-troubleshooting-guide.md) (`ms.date` 03/06/2025) lists, at line 55: "The max size of `offset.metadata.max.bytes` is 1,024 bytes".

## Why it is traced, not tested

The reason in [docs/blueprint.md](../blueprint.md) section 12 is: "the pinned client exposes no commit metadata".

The evidence is in two files of [Confluent.Kafka v2.16.0](https://github.com/confluentinc/confluent-kafka-dotnet/tree/v2.16.0).

- [TopicPartitionOffset.cs](https://github.com/confluentinc/confluent-kafka-dotnet/blob/v2.16.0/src/Confluent.Kafka/TopicPartitionOffset.cs), lines 97 to 112, declares four public properties: `Topic`, `Partition`, `Offset` and `LeaderEpoch`. None of them is metadata.
- [Impl/SafeKafkaHandle.cs](https://github.com/confluentinc/confluent-kafka-dotnet/blob/v2.16.0/src/Confluent.Kafka/Impl/SafeKafkaHandle.cs), lines 1344 to 1376, is the conversion of a list of `TopicPartitionOffset` values to the native partition list. For each entry it adds the topic and partition, writes the offset, and sets the leader epoch when one is present. It writes nothing else.

The native structure does declare `metadata` and `metadata_size` fields (same file, lines 74 and 75). In that file nothing in the conversion fills them.

## Trace

- Design: none. [ADR-005](../blueprint.md) commits offsets by storing each offset after processing and does not use commit metadata.
- .NET code: nothing in the pinned client's managed API or its conversion can set commit metadata (see the two files above).
- Terraform: none. The limit is a service limit with no setting.
- Security: none.
- Symptom: not reachable from the pinned client. No cited source states the reply to metadata longer than 1,024 bytes.
- Detection: not applicable, because the client cannot send metadata.
- Runbook: inference, not tested: a client that calls librdkafka directly can send metadata, because the native structure declares `metadata` and `metadata_size` (SafeKafkaHandle.cs lines 74 and 75). Such a client should keep it at or below 1,024 bytes.
