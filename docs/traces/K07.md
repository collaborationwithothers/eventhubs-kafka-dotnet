# K07: zone spread of consumer group members

Kubernetes documents topology spread constraints as the way to spread Pods across failure domains such as zones. This item is traced from documentation and design, not tested, because a zone outage cannot be induced and the build does not configure zones. The main finding is that the build has no zone setting on any node pool and no spread constraint in the chart, so no cited source or run shows how consumer group members are spread across zones.

Sources were read on 2026-10-27. Line numbers refer to the linked commit or tag. "Inference" marks a statement that no cited source makes.

## Claim

The Kubernetes [topology spread constraints page](https://github.com/kubernetes/website/blob/ed70e311737a/content/en/docs/concepts/scheduling-eviction/topology-spread-constraints.md) (commit ed70e311737a) says at lines 10 to 13 that you can use topology spread constraints to control "how Pods are spread across your cluster among failure-domains such as regions, zones, nodes, and other user-defined topology domains". The quote leaves out the glossary tooltip markup that wraps the word Pods in the source.

At lines 224 to 229 the same page says the registered label keys `topology.kubernetes.io/zone` and `topology.kubernetes.io/region` "are nonetheless recommended rather than the private (unqualified) label keys". The zone key is therefore the key to use for a zone spread.

## Why it is traced, not tested

The inventory reason in [docs/blueprint.md](../blueprint.md) section 12 is "a zone outage cannot be induced". A test of how a consumer group behaves when a zone fails would need that outage.

The build also does not request zones. No node pool in [aks.tf](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/39e2cbba73f28855d3d0bbc3511d977294b8ba09/infra/cluster/aks.tf) sets availability zones (lines 34 to 57). Each pool has one node (`count_of = 1` at lines 35, 44 and 51). Inference: with no zones requested and one node per pool, a consumer group on the `workload` pool runs on a single node and so in a single failure domain.

## Trace

- Design: docs/blueprint.md section 3 "AKS cluster" gives three pools of one node each, with `loadgen` scaling to N for saturation runs; ADR-008 puts every pool on normal capacity.
- .NET code: none. A search of `src/` at the pinned commit for `topology.kubernetes` and `availability zone` finds nothing, so no code reads or sets a zone.
- Terraform: no `zones` setting on any pool in aks.tf lines 34 to 57.
- Kubernetes: the chart sets no topology spread constraint. A search of `charts/` and `infra/` at the pinned commit for `topologySpread`, `topology.kubernetes` and `affinity` finds nothing.
- Security: none. The item changes no identity, network or credential setting.
- Symptom: Inference: a consumer group whose members all run in one zone stops when that zone has an outage, and then rebalances once members run again.
- Detection: Inference: compare the node of each consumer pod with that node's `topology.kubernetes.io/zone` label. Members that share one label value share a failure domain.
- Runbook: Inference, not tested: on a zonal cluster, add a zone spread constraint on `topology.kubernetes.io/zone` to the consumer pods.
