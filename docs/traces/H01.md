# H01: throttling absent from ThrottledRequests

Microsoft says Kafka throttling is mostly not logged as ThrottledRequests, so the response's `throttle_time_ms` is the indicator, and librdkafka reports it as the broker `throttle` statistic. This repository does not test it, because without a throttle event there is nothing to detect. The main finding is that Microsoft marks ThrottledRequests as not exportable through diagnostic settings, so by inference its absence from the workspace is expected even when the namespace throttles, and is not evidence of zero.

Sources were read on 2026-10-27. Line numbers refer to the linked commit or tag. "Inference" marks a statement that no cited source makes.

## Claim

The [troubleshooting guide](https://github.com/MicrosoftDocs/azure-docs/blob/6da87e3c59251e962dd0b37dbd99ae364d767150/articles/event-hubs/apache-kafka-troubleshooting-guide.md) (`ms.date` 03/06/2025) says at line 13: "In most cases, these delayed requests aren't logged as ThrottledRequests metrics on Event Hubs dashboards. Instead, the response's `throttle_time_ms` value should be used as an indicator that throughput has exceeded the provisioned quota."

The [librdkafka statistics reference](https://github.com/confluentinc/librdkafka/blob/v2.16.0/STATISTICS.md) at line 115 describes the per-broker `throttle` field as "Broker throttling time in milliseconds".

## Why it is traced, not tested

The inventory reason in [docs/blueprint.md](../blueprint.md) section 12 is: "without a throttle event there is nothing to detect". It follows [#155 decision 2](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/155#issuecomment-6442094735).

The final A01 probe states "No positive throttle sample was observed" ([A01 result](../../results/A01/2026-10-25.md), line 30 at commit 39e2cbb). [#155 decision 1](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/155#issuecomment-6442094735) (a) parks the throttling family. Inference: no run is planned that would produce a throttle event.

## Metric export finding

The [Event Hubs namespace metrics reference](https://github.com/MicrosoftDocs/azure-monitor-docs/blob/6b3769e284c0234a021a3ff9c86c821414ad3eb0/articles/azure-monitor/reference/supported-metrics/microsoft-eventhub-namespaces-metrics.md) (`ms.date` 07/31/2026) defines the column "DS Export" at line 25 as whether a metric "is exportable to Azure Monitor Logs via Diagnostic Settings". Among the metrics with DS Export `No` are `NamespaceCpuUsage` (line 60), `ServerErrors` (line 68), `ThrottledRequests` (line 73) and `UserErrors` (line 74).

The ephemeral namespace sends `AllMetrics` to Log Analytics through a diagnostic setting ([observability.tf lines 1 to 12](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/39e2cbba73f28855d3d0bbc3511d977294b8ba09/infra/ephemeral/observability.tf)). Inference: those four metrics never reach the workspace. The statement in the [#155](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/155) body, "No ThrottledRequests, ServerErrors or UserErrors metrics exist in the workspace", is therefore expected even when the namespace throttles. It is not evidence of zero throttling.

The #155 body also reports `NamespaceCpuUsage` values from AzureMetrics. The metrics reference says that metric is not exported. Which of the two is right is unknown. `NamespaceCpuUsage` has a `Replica` dimension (line 60).

Inference: ADR-007's KQL join of client throttling with platform metrics (docs/blueprint.md line 273 at commit 39e2cbb) cannot include `ThrottledRequests` from the workspace.

Inference: query Q1 in docs/blueprint.md section 10 (lines 823-838 at commit 39e2cbb), the detection that FM-01 names (line 629), reads ThrottledRequests from AzureMetrics, so its platformThrottled column would stay empty even when the namespace throttles.

## Disconnect signal

The research [catalogue](../research/kubernetes-kafka-clients.md) (row K-38, line 63 at commit 39e2cbb) records that librdkafka silences the disconnect log for disconnects it classifies as idle, and that the statistics `disconnects` counter still counts them. Amendment 1 to the inventory folds K-38 into H01.

The librdkafka statistics reference at line 111 describes `disconnects` as "Number of disconnects (triggered by broker, network, load-balancer, etc.)". The [statistics bridge](../operations/statistics-bridge.md) exports it as `kafka.broker.disconnects` (line 56 at commit 39e2cbb).

## Trace

- Design: ADR-007 sets `statistics.interval.ms = 15000` and reads client throttling from librdkafka statistics. Its context cites the same Microsoft statement as the claim.
- .NET code: the bridge reads each broker's throttle count and maximum, and its `disconnects` counter ([statistics-bridge.md](../operations/statistics-bridge.md) line 40 at commit 39e2cbb). It exports the throttle maximum as `kafka.broker.throttle.max_ms` only when the throttle count is above 0 (line 54).
- Terraform: the `AllMetrics` diagnostic setting ([observability.tf lines 9 to 11](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/39e2cbba73f28855d3d0bbc3511d977294b8ba09/infra/ephemeral/observability.tf)). It carries none of the four metrics named above.
- Security: none. Inference: reading client statistics adds no access to Azure.
- Symptom: delayed acknowledgement of produced messages and delayed delivery of consumed ones, with the delay returned in `throttle_time_ms` (troubleshooting guide line 13).
- Detection: a `throttle` window with a count above 0 (statistics reference line 115; bridge line 54 at commit 39e2cbb). Inference: ThrottledRequests must be read from Azure Monitor metrics, not from the workspace.
- Runbook: treat the client throttle statistics as the indicator (troubleshooting guide line 13).
