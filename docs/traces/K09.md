# K09: LocalDNS prerequisites and effects

AKS LocalDNS runs a DNS proxy on each node, has stated prerequisites, reimages a node pool when its profile changes, and from Kubernetes 1.37 is switched on by default for eligible AKS Standard node pools. It is not tested because, in the words of the inventory, it changes the DNS path for every item. The main finding is that no pool sets a LocalDNS profile at `39e2cbb`, the cluster meets every stated prerequisite (the operating system one by inference), and #225 is the issue that will add `mode = "Disabled"` to all three pools in its own pull request.

Sources were read on 2026-10-27. Line numbers refer to the linked commit or tag. "Inference" marks a statement that no cited source makes. A bare line number refers to the AKS page [localdns-custom.md](https://github.com/MicrosoftDocs/azure-aks-docs/blob/1b2c1f91df475f8cb46f72cbf3ee125241523be8/articles/aks/localdns-custom.md), whose `ms.date` is 09/18/2026.

## Claim

The page describes LocalDNS as "a feature in AKS that improves DNS resolution performance and resiliency for workloads running in your cluster", and says it does this "By running a DNS proxy on each node" (line 24).

It is configured per node pool: "You configure LocalDNS at the node pool level in AKS, so you can tailor behavior by workload and environment." (line 103).

It has prerequisites, which the section "Prerequisites: the cluster meets every stated one" quotes one by one against this repository. Line 97, "This article requires Azure CLI version 2.80.0 and later", is a tooling prerequisite for following the article, not a property of the cluster, so that section leaves it out.

Changing it is disruptive: "Enabling LocalDNS on a node pool initiates a reimage operation on all nodes within that pool." (line 140).

## Why it is traced, not tested

The reason in section 12 of the inventory in [docs/blueprint.md](../blueprint.md) is: "LocalDNS changes the DNS path for every item; to be pinned `Disabled`". The corrected reason follows [#224 decision 3](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/224#issuecomment-6438353573), and the pin follows decision 4 of the same comment.

Pin status: no pool sets a LocalDNS profile at `39e2cbb` (lines 34-57 of [aks.tf](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/39e2cbba73f28855d3d0bbc3511d977294b8ba09/infra/cluster/aks.tf)). [#225](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/225) is the issue that will add `mode = "Disabled"` to all three pools in its own pull request. On 2026-10-27 that pull request does not exist yet. Until it merges, the pin is intended and not in effect.

The inventory row also notes that a separate pool would avoid reimaging existing pools (inference) but adds a node and changes ADR-008. Nothing runs for this item, so no scenario file or expected outcome is added.

## Prerequisites: the cluster meets every stated one

The operating system prerequisite is met by inference, as its bullet says.

- Kubernetes version. Line 96 requires "Kubernetes versions 1.31 and later". The repository's [variables.tf](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/39e2cbba73f28855d3d0bbc3511d977294b8ba09/infra/cluster/variables.tf) lines 65-77 accept only an explicit patch version, and the message on line 76 reads "kubernetes_version: supply an explicit patch version at least 1.35.0." So the floor is met.
- Node size. Line 99 requires "at least 4 vCPUs": "The Virtual Machine (VM) SKU used for your node pool must have at least 4 vCPUs (cores) to support LocalDNS." All three pools use `Standard_D4ds_v5` (aks.tf lines 35, 44 and 51). The [ddsv5-series page](https://github.com/MicrosoftDocs/azure-compute-docs/blob/509cdb5e28e4759acd0c2ef5185e0e71a8c49362/articles/virtual-machines/sizes/general-purpose/ddsv5-series.md) lists that size with 4 vCPUs on line 32. The pools sit exactly at the floor.
- Operating system. Line 98 reads "LocalDNS is only supported on node pools running Azure Linux or Ubuntu 22.04 and newer." aks.tf sets no `os_sku`. The AKS page [node-images.md](https://github.com/MicrosoftDocs/azure-aks-docs/blob/1b2c1f91df475f8cb46f72cbf3ee125241523be8/articles/aks/node-images.md) lines 51-52 give "Ubuntu Linux" as the default OS for OS type "Not Specified" and for "Linux". The AKS page [upgrade-os-version.md](https://github.com/MicrosoftDocs/azure-aks-docs/blob/1b2c1f91df475f8cb46f72cbf3ee125241523be8/articles/aks/upgrade-os-version.md) line 43 says "Ubuntu 24.04 is default for Kubernetes versions 1.35+". Inference: the pools run Ubuntu 24.04, which is newer than 22.04.
- Network plugin and policy. aks.tf line 30 sets the Cilium data plane and Cilium network policy. At `39e2cbb` there is no NetworkPolicy or CiliumNetworkPolicy under `charts/` or `infra/`. The AKS page [azure-cni-powered-by-cilium.md](https://github.com/MicrosoftDocs/azure-aks-docs/blob/1b2c1f91df475f8cb46f72cbf3ee125241523be8/articles/aks/azure-cni-powered-by-cilium.md) lines 349-353 say that "network policies must explicitly allow pod egress to the LocalDNS IP address", so a policy added later must allow that egress. Under `Preferred` mode, line 52 says that a network policy keeps LocalDNS disabled "even if they allow DNS traffic".

## Reimaging

Enabling LocalDNS "initiates a reimage operation on all nodes within that pool" (line 140), and LocalDNS is configured at the node pool level (line 103). Line 130 shows a pool created with a profile: `az aks nodepool add ... --localdns-config ./localdnsconfig.json`. Inference: other pools are untouched when a new pool is added with a profile.

An update to an existing pool also reimages it: "Updating the LocalDNS profile on an existing node pool triggers a node reimage when the resulting profile differs from the current profile. This condition includes changing the mode to `Disabled`." (line 68).

No cited source says whether setting `mode = "Disabled"` on a pool that has no profile counts as a difference from the current profile. That is unknown. It matters for the pull request that adds the pin.

## Kubernetes 1.37 enables it by default

Lines 21 and 22 state both halves of the default: "Starting with Kubernetes 1.37, AKS Standard applies the `Preferred` LocalDNS mode by default to eligible node pools that don't have an explicitly configured LocalDNS profile." and "To prevent LocalDNS from being enabled, explicitly set the LocalDNS mode to `Disabled`." The mode table on line 275 reads, for 1.37 and later under `Preferred`, "LocalDNS installed and enabled when compatibility checks pass". The AKS page [dns-concepts.md](https://github.com/MicrosoftDocs/azure-aks-docs/blob/1b2c1f91df475f8cb46f72cbf3ee125241523be8/articles/aks/dns-concepts.md) lines 23-24 repeat both statements.

Kubernetes 1.37 reaches AKS GA in October 2026 (row for 1.37, line 59 of the AKS page [supported-kubernetes-versions.md](https://github.com/MicrosoftDocs/azure-aks-docs/blob/1b2c1f91df475f8cb46f72cbf3ee125241523be8/articles/aks/supported-kubernetes-versions.md)). The repository sets only a lower bound on the version (variables.tf lines 65-77), so a 1.37 cluster is allowed.

The default applies to AKS Standard. aks.tf line 19 sets the SKU name `Base`. The AKS page [free-standard-pricing-tiers.md](https://github.com/MicrosoftDocs/azure-aks-docs/blob/1b2c1f91df475f8cb46f72cbf3ee125241523be8/articles/aks/free-standard-pricing-tiers.md) line 29 reads "Base SKU clusters can use any of the three pricing tiers: Free, Standard, or Premium." Inference: the cluster is AKS Standard. The `Free` pricing tier on the same line of aks.tf is a separate setting from the cluster type.

The compatibility checks are on lines 44-53. Only line 50, "VM SKU capacity", states no threshold: "The VM SKU has enough CPU and memory for LocalDNS". The other checks would match a pool of this cluster at 1.37 or later: the version (at 1.37), the cluster type (by inference), no profile, the operating system (by inference), a managed CNI (`network_plugin = "azure"`, aks.tf line 29), no network policy, and no `node-local-dns` DaemonSet, for which a search of `charts/` and `infra/` at `39e2cbb` finds nothing (line 53). Inference: a pool built or upgraded at 1.37 without a profile would most likely run LocalDNS.

The page contradicts itself. Line 265 says `Preferred` "**doesn't enable LocalDNS**", while line 275 says it enables LocalDNS on 1.37 and later when the checks pass. Inference: line 265 describes 1.31 through 1.36, as line 274 does. Line 265 also says applying the mode "still triggers a node reimage operation".

## G01 and stale DNS

[geo-replication.md](https://github.com/MicrosoftDocs/azure-docs/blob/6da87e3c59251e962dd0b37dbd99ae364d767150/articles/event-hubs/geo-replication.md) (`ms.date` 07/10/2026) line 259 says that after failover "the private endpoint keeps working without any change". geo-replication.md line 267 says "Each region resolves the namespace name to its local endpoint, regardless of which region is primary." ADR-004 makes the private endpoint the only path. Inference: promotion does not change the DNS answer a pod receives, so a LocalDNS cache has no stale address to serve.

LocalDNS cache limits point the same way. Line 76 says the cache duration "acts as a cap on the DNS record TTL but doesn't increase it". Line 79 says caching "operates on a best effort basis". The G01 note in [docs/blueprint.md](../blueprint.md) records this reasoning, and G01's evidence will record each node pool's LocalDNS mode.

## Trace

- Design: ADR-008 puts every pool on normal capacity and taints the load pool. The inventory row (section 12 of [docs/blueprint.md](../blueprint.md)) explains why LocalDNS is not tested and is to be pinned `Disabled` under #224 decision 4.
- .NET code: none. Clients resolve names through the node's DNS path, so no code in `src/` chooses or observes the resolver.
- Terraform: no pool sets a LocalDNS profile at `39e2cbb` (aks.tf lines 34-57, [aks.tf](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/39e2cbba73f28855d3d0bbc3511d977294b8ba09/infra/cluster/aks.tf)). #225 will add `mode = "Disabled"` to all three pools in its own pull request.
- Security: none. The item changes no identity, network or credential setting.
- Symptom: inference: with LocalDNS on, every lookup goes through a per-node proxy that no evidence pack records, so a DNS effect would be attributed to the wrong layer.
- Detection: line 161 says to run DNS queries from pods in the node pool and inspect the `SERVER` field for `169.254.10.10` or `169.254.10.11`.
- Runbook: lines 62-66 say, before upgrading, to check each pool's profile and to test the change in a non-production pool. Line 66 reads "If the network isn't ready for LocalDNS, explicitly set `mode` to `Disabled` before upgrading".
