# Before opening a pull request

This file holds the rules for work that a pull request will publish: rules 1 to 10 of AGENTS.md "Before opening a pull request" (including the cold-review protocol and budget in rule 8) and the order of the verification gates. Read it in full before you start such work, and before you review such work cold. Rules 11 to 13 of that section bind every session, so they stay in AGENTS.md.

The text moved here unchanged from AGENTS.md in the third governance pull request for issue #264 ([decision](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/264#issuecomment-6570202237)). `/docs/` is a protected path (GOVERNANCE "Merge rule"; `.github/CODEOWNERS` mirrors the list), so a change to this file reaches `main` only through Hari's merge, as a change to AGENTS.md does.

Rule numbers are those of AGENTS.md "Before opening a pull request". A bare rule number means the rule of that number in that section: rules 1 to 10 are here, and rules 11 to 13 are in AGENTS.md. A section name with no file, such as GOVERNANCE "Merge rule" or "Code Review Rules", names a section of AGENTS.md. Where AGENTS.md says that "this file" wins a conflict, this file counts as part of AGENTS.md.

## Rules

Applies to every pull request, documentation included. Authority refreshes follow docs/agents/factory.md "Authority reads".

Apply the current authority, gates, commands, checkpoints and review budget throughout implementation. For verifier work, cover each changed or affected predicate at below, at and above each boundary, empty input and precedence interactions. Explain unreachable cases. Keep unrelated evidence valid so another invalid field cannot mask the predicate under test. The approved plan's test map and the actual tests are the sources for this coverage.

1. Verify every factual claim against its source at the pinned version before committing it. Never write a library or Azure behaviour from memory.
2. Mark a claim confirmed only if every part of it is stated by a cited source. Name any inferred part as inferred. Cite every source a claim depends on, in full.
3. Before every push, including pushes that only contain review fixes, re-read the applicable review scope defined by rule 8 against docs/blueprint.md's ADRs, docs/engineering/ and the merge rule. A fix can break another decision.
4. Compute counts, totals, cross-references and time differences with a script, never by hand.
5. Freeze the review inputs, identify the reviewed revision and wait for complete reports from all reviews started on that revision before editing. Group findings by root cause, audit every affected instance, and consolidate corrections before the next review. When a reviewer finds one error, check every instance of that class, not only the one flagged. For recurring findings, consider automated prevention with an existing tool first. A new check needs explicit supported inputs, failure conditions and regression examples. Add it to the same pull request only when it fits the approved scope; otherwise record the proposal on the issue. A finding does not automatically require a new checker capability. Documentation checks start as advisory; making them blocking requires Hari's approval based on observed usefulness and false positives. The local command and supported checks are in [Documentation checks](../engineering/documentation-checks.md).
6. If two review rounds in a row raise new substantive findings, stop and split the pull request. A substantive finding is a P0 or P1. Moving a finding out of scope into a linked issue counts as a split. The threshold is a governance choice, not a measurement.
7. Keep the description short: what changed, why, what to read first, what you are least sure about. Evidence lives in the repository (ADRs, citations, commit messages); the description links to it. If the change cannot be described in a few lines, split it.
8. Every non-backup push needs applicable cold-review coverage under the protocol below; rule 12 defines backup pushes. A push to a plan branch under docs/agents/factory.md "Item lifecycle" step 3 publishes no pull request; its plan check under that step is its review, and this rule does not apply to it. Before the cold review, run `npm run check:docs`; fix each warning or explain in the pull request why it stands. Warnings in files the pull request does not change take one blanket line in the pull request, not one disposition each, and do not count against a plan's disposition cap. A cold review is a fresh context that applies the repository-owned `repo-review` skill. Give the reviewer directly in its task the frozen review-diff path, mode (comprehensive or focused), input and reviewed revision and applicable comparison revision, and the approved specification or plan revision and links to recognized later decisions. Supply applicable required implementer choices and fixture-change explanations directly in the task so the reviewer can check them before the PR exists; record them in the PR implementation notes. For an existing PR, supply the frozen notes or their source links directly. For directly authorized work without an approved item plan, supply the actual task brief, issue and authorization. For a focused review also supply changes since the previous reviewed revision, unresolved findings and the full PR diff as context. No authored receipt or substitute briefing document is required. Compare implementation against the actual authority sources for missing, partial or incorrect requirements and scope creep, with evidence. Recognize governed plans and later decisions under docs/agents/factory.md "Item lifecycle" step 3. Review all authored repository changes, including code, tests, configuration, workflows, scripts, judgements and prose. Agents commit no program output. Record the final head's CI run and the last cold-review round in the pull request description.

   Record otherwise unavailable facts that affect a decision in the pull request, such as a controlled pre-fix regression comparison, an unresolved cause limiting a claim, an incomplete required check, or required implementer choices and fixture-change explanations. Identify the source revision, command or procedure, outcome and material limits where relevant. Routine successful verification lives in CI; link its runs and reviewed SHAs without copying counts or logs.

   Fix every P0 and P1 the cold review reports, or answer it `Not valid:` with evidence under rule 10, except as the next paragraph allows. For counting under this rule, that exception paragraph applies first. Cold-review rounds do not count toward rule 6. At the first round with no P0 or P1, fix the P2s whose fixes touch only prose in files already in the diff. If those fixes change the diff, run one focused P2-correction review before pushing; that round reports only P0 or P1 and does not repeat. It counts toward the focused-review limit below, including when the initial comprehensive review is clean and no second comprehensive pass is needed. If that round reports a P0 or P1, revert the P2 fixes made after the clean round. Then push the diff that the clean round reviewed, with no further cold-review round. Dispose of each reverted P2 under rule 10. If the P0 or P1 remains after reverting the P2 fixes, use the review-budget handoff below. If no focused round remains for these P2 fixes, use that handoff before making them. Other P2s follow rule 10. Open one follow-up issue for the pull request only for P2s that need new scope.

   Some Code Review Rules flag work that only Hari can approve: changes to expected outcomes, verdicts or `results/`, and new projects, assembly references or NuGet packages. Keep such work only if the approved plan or the verdict step requires it. In that case, push, list the finding in the pull request description, and leave the merge to Hari. A P1 kept this way, including one on a new project, reference, package or tool that the approved plan requires, does not count toward rule 6's review-round stop limit. Revert any other such change before the push. This exception does not relax GOVERNANCE "Verdict integrity".

   **Cold-review protocol and cumulative budget.** Start with one fresh-context comprehensive review of the entire authored PR diff. If corrections are needed, allow one consolidated comprehensive re-review. At most two comprehensive passes run per PR across all sessions. After those passes, allow at most two focused correction-review rounds; the P2-correction exception above may use a focused round after a clean initial pass without requiring another comprehensive pass. These numbers are governance policy choices, not measured token savings. The order of the cold review and the verification gates is set in "Verification gates" below.

   A focused round reviews changes since the last reviewed revision, unresolved findings, and affected surrounding code, callers, tests and contracts. Supply the full PR diff as context, but do not repeat a comprehensive full-PR review. Provide the mode, input and reviewed revisions and comparison revision in the review task and record them in the report. Record complete reports, dispositions and cumulative comprehensive/focused counts in the PR's self-review record; link earlier reports. Reviewed unchanged work retains coverage; every later authored repository change needs applicable coverage. Correcting PR-only metadata, links or explanations requires no Git commit or automatic cold-review round. Such a correction cannot manufacture coverage: missing verification, authorization or valid review coverage still blocks under the existing gates. Changes to repository or governing requirements retain applicable review and approval requirements. Incorrect review task inputs that reveal absent coverage must be resolved within the existing budget; do not reset the counters or claim completion without coverage. Starting a new session, splitting corrections into pushes, or renaming a review does not reset the counters. Cold-review rounds remain excluded from rule 6; that rule's substantive-finding split still applies to the reviews it counts.

   Stop early if substantial changes to design, scope or assumptions make safe focused review impossible. When another required review would exceed the budget, or when focus is unsafe, save unpublished work under rule 12 and hand off to Hari. This is an explicit exception to rule 11's automatic next-session continuation. State the unresolved gate, findings, reviewed revisions, cumulative budget and proposed next action. A third comprehensive pass requires Hari's explicit decision. Never weaken a required gate to fit the budget.

   Publish the tested PR at the earliest authorized review checkpoint. Independent CI and hosted Codex review may run together. Hosted review and GOVERNANCE "Merge rule" final-head requirements remain mandatory and are recorded separately from cold-review counts; avoid duplicate discretionary review requests. Corrections from hosted findings consume the remaining cold-review budget before any non-backup push. If none remains, use the handoff above.
9. Fill in the pull request template, including its collapsed self-review record. Reply to every Codex finding, inside the finding's review thread. When a finding is wrong against its source, start the reply with `Not valid:` and give the evidence. Escapes are not counted by hand; a script will compute them (docs/agents/factory.md, "Measuring the gate", "Escapes").

10. Answer review findings by severity. This applies to Codex code review and the cold review, in every round, subject to rule 8's disposition of P2s at the first clean cold-review round. Codex security review findings are answered under rule 9, and GOVERNANCE "Merge rule" decides whether they block a merge.
    - P0 or P1: fix it, or answer `Not valid:` with evidence (rule 9). Rule 8's third paragraph still applies.
    - P2 that asks for a check, guard or hardening the approved plan does not list: do not fix it. Reply `Out of contract:` and name the plan field or section. If its absence could make a published result wrong, also comment on the issue being implemented so Hari can decide whether the check joins the plan.
    - Any other P2: fix it, or give a one-line reason for leaving it.

    The pull request description links its approved plan. A pull request with no approved plan, such as a governance or documentation change, has no plan checks, so its P2 findings take the last case. The checks a plan lists are its "Enforced checks" field or, for a plan approved before that field existed, the checks its text names. Codex findings are answered in their review thread and cold-review findings in the self-review record. A cold-review P0 or P1 answered `Not valid:` is also listed in the pull request description, so Hari sees the dispute.

    A pull request that cannot clear Codex review uses rule 11, subject to rule 8's review-budget handoff to Hari.

## Verification gates

This section owns the order of the verification gates and what each one is. Other files cite it rather than restating it. Basis: [decision 6847972415](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/440#issuecomment-6847972415) on issue #440, which adopts proposals 1 and 2 of that issue's body, and [decision 6856109826](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/440#issuecomment-6856109826) on the same issue, which sets when the pre-PR local gate runs again. The order is a governance choice; the saving it is expected to produce is not measured.

1. Focused tests. Run the tests that cover the change while the change is still moving. `./scripts/verify-dotnet.sh --tier fast` and `./scripts/verify-dotnet.sh --project <name>` are partial runs for this step, and are cited as partial runs.
2. Cold review, under rule 8.
3. The pre-PR local gate, once, on the source the cold review cleared: `./scripts/verify-dotnet.sh --tier sandbox`, which runs every test except those marked with the xUnit trait `Tier=CGroupV2`. The Docker tests stay in it. Record it as a partial run with that exclusion, never as the full gate.
4. The pre-merge gate: the hosted `.NET verification` check on the pull request's final head, which runs every test, the `Tier=CGroupV2` tests included. GOVERNANCE "Merge rule" is unchanged.

No local gate starts while a review round is open on the same source. A review round is open from the moment its inputs are frozen under rule 5 until its complete report arrives. A change made after step 3 and before the pull request opens is authored work: it needs the coverage rule 8 requires, and step 3 then runs again on the source that coverage cleared. After the pull request opens, a correction, including one from a review finding or a hosted finding, needs the cold-review coverage rule 8 requires, and step 4 on the final head is its verification gate; step 3 need not run again.

Steps 1 and 3 apply to a pull request that changes any file under `src/` or `tests/`, `scripts/verify-dotnet.sh`, any `*.csproj` or `Directory.*.props` file, any `packages*.lock.json` file, or `global.json`. For any other change, rule 13 decides which verification suits it, and rule 8's documentation checks apply as they do to every pull request.
