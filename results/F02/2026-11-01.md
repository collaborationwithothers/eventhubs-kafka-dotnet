# F02: librdkafka's own OAuth code did not deliver under AKS workload identity

In run 41331232103, three producers that used librdkafka's own OAuth code each ran five slots against Event Hubs, and the custom-handler control in the same run delivered all five of its messages. No native producer delivered a message: Entra answered the JWT-bearer grant with HTTP 400 `AADSTS900144`, IMDS answered HTTP 400 `Identity not found` for the workload client ID, and IMDS with no client ID gave a non-workload identity that Event Hubs denied with `Broker: Topic authorization failed`. The run's conclusion is `failure` because the JWT-bearer Job reached the client-error capture limit, which makes those five slots' class a lower bound; the control and the infrastructure did not fail.

Proposed verdict: `confirmed`. Microsoft's [workload identity page for AKS](https://learn.microsoft.com/azure/aks/workload-identity-overview) states that "workload identity uses the Microsoft Entra v2 token endpoint rather than the IMDS `resource` flow used by managed identity" (read 2026-11-01). In this run, librdkafka's built-in `azure_imds` option, which calls IMDS, never obtained the workload identity: with the workload client ID IMDS answered `Identity not found`, and with no client ID the broker saw only a non-workload principal. That page is AKS identity guidance, not Kafka guidance, and does not name librdkafka. A pinned script, not the repository's verifier, classified the native slots; Hari accepted that for this item only in [decision 6562091612](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/307#issuecomment-6562091612) on issue 307, and chose the verdict word in [decision 6562117618](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/307#issuecomment-6562117618).
