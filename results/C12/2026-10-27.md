# C12: group.id is limited to 256 characters on Event Hubs Premium

A consumer with a 256-character group.id was assigned partitions in all five repeats, and a 257-character group.id was rejected by the broker in all five, so the proposed C12 verdict is confirmed. The rejection was broker error 24, which librdkafka names as invalid group.id. The workload is synthetic, and the result covers only the subscribe action on document-events.

Proposed verdict: `confirmed`.

The [approved scenario](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/7b6834c5e8668e89376597bc2b524c0725326daf/scenarios/C12/scenario.yaml) and [expected outcome](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/7b6834c5e8668e89376597bc2b524c0725326daf/scenarios/C12/expected.yaml) are unchanged. Each repeat is one fresh consumer, built from the `EnrichmentConsumer` baseline role and run under the `probe` service account, that subscribes to `document-events`. C1 sets `group.id` to `c12-` followed by 252 `g` characters, and C2 to `c12-` followed by 253; a script measured the two values in the scenario file at 256 and 257 characters. A subscribe succeeds when the partitions-assigned handler fires. The action window is 120000 ms.

## Assessment against expected.yaml

**H1 holds.** C1, 256 characters, was assigned partitions in all five repeats. The troubleshooting guide says "The max length of the `group.id` property is 256 characters" ([troubleshooting guide](https://learn.microsoft.com/en-us/azure/event-hubs/apache-kafka-troubleshooting-guide), read 2026-10-27).

**H2 holds.** C2, 257 characters, errored in all five repeats with origin `broker`. The quotas page lists the Kafka consumer group name size as "Kafka: 256 characters" ([quotas page](https://learn.microsoft.com/en-us/azure/event-hubs/event-hubs-quotas), read 2026-10-27). None of the four Microsoft pages cited in these reports names the error code; code 24 is reported, not judged.

**Verdict.** `confirmed_when: "C1 succeeds and C2 errors with origin broker."` holds, so the proposed verdict is `confirmed`. A script holding these decision rules, transcribed from `expected.yaml` and checked against its pinned SHA-256, derived the same verdict; it equals the verifier's `item_assessment`.

The boundary is measured in characters of ASCII text, where one character is one byte. Whether the limit counts bytes or characters for non-ASCII group IDs is not tested.
