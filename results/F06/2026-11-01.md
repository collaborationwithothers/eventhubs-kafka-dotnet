# F06: identities with narrow event-hub grants send and read inside them and get broker error 29 outside them

Across 60 complete synthetic repeats in 12 deterministic configurations, every positive control succeeded in all five repeats, and the four configurations outside the narrow grants each returned broker error code 29 (`TOPIC_AUTHORIZATION_FAILED`) in all five repeats. The workflow's own permission audit of the two narrow identities listed exactly the four intended grants and nothing else. So H_positive_scope holds, H_negative_surface is recorded only, and the proposed F06 verdict is `undocumented`, for partition 0 of three topics and two narrow identities.

Proposed verdict: `undocumented`.

## What each configuration does

Each repeat is one fresh client with one action on partition 0 of one topic. A producer repeat sends one synthetic message (key and value `F06:<configuration>:<run>:r<repeat>`) with `Produce` to an explicit partition 0 and waits for the delivery report. A fresh `probe` consumer then reads the delivered location independently. A consume configuration assigns partition 0 at the offset of a seed message and reads it. Seeds are written beforehand by an identity that holds the Sender grant on that topic: `loadgen` for `document-events`, and `enrichment-consumer` for `document-state` and `document-events-dlq`. C9, C10 and C11 read the same seed locations as C6, C7 and C8. Every key and value is synthetic. The account, action and topic of each row come from the approved scenario at the run source, and the generator checks each against the capture.

The grants come from [identity.tf at the run source](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/961413f3fc81ec1b58b3fecc7f9e5122a8a21010/infra/ephemeral/identity.tf). `loadgen` has Event Hubs Data Sender on `document-events` ([L6](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/961413f3fc81ec1b58b3fecc7f9e5122a8a21010/infra/ephemeral/identity.tf#L6)). `enrichment-consumer` has Data Receiver on `document-events`, and Data Sender on `document-state` and `document-events-dlq` ([L8-L10](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/961413f3fc81ec1b58b3fecc7f9e5122a8a21010/infra/ephemeral/identity.tf#L8-L10)). `probe` has Data Receiver on `document-events` and, under the explicitly approved test-only exception, Data Sender and Data Receiver on the whole namespace ([L3](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/961413f3fc81ec1b58b3fecc7f9e5122a8a21010/infra/ephemeral/identity.tf#L3), [L16-L18](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/961413f3fc81ec1b58b3fecc7f9e5122a8a21010/infra/ephemeral/identity.tf#L16-L18)). ### Meaning of code 29

In librdkafka v2.16.0, error code 29 is `RD_KAFKA_RESP_ERR_TOPIC_AUTHORIZATION_FAILED`, with the comment "Topic authorization failed" ([rdkafka.h L494-L495](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka.h#L494-L495)), and its description string is "Broker: Topic authorization failed" ([rdkafka.c L578-L579](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka.c#L578-L579)). Confluent.Kafka v2.16.0 names the same value `ErrorCode.TopicAuthorizationFailed = 29` ([ErrorCode.cs L505-L508](https://github.com/confluentinc/confluent-kafka-dotnet/blob/v2.16.0/src/Confluent.Kafka/ErrorCode.cs#L505-L508)). The origin `broker` and the fatal flag false are the candidate's recorded fields. So the client library reports the broker's answer as a topic authorization failure. That does not say which grant, deny or evaluation produced the answer, and the approved rules prescribe no cause. The approved rules do not compare error text (`error_text_compared: false`). ## Assessment against expected.yaml

**H_positive_scope holds.** Its question is whether the exact positive send and read controls succeed under the documented role scopes. All 12 configurations are complete and deterministic. The eight positive controls named by the rule (C0, C1, C3, C5, C6, C7, C8 and C9) all succeeded, and none has a complete observed failure, so the `failed_control` branch does not apply. Each send was acknowledged as persisted on partition 0, and each independent read returned the same topic, partition, offset, key and value.

**H_negative_surface is recorded only.** The rule asks for the native class of each negative observation and forbids a claim of universal scope enforcement. The record is: C2, C4, C10 and C11 each returned error code 29, not fatal, from the broker, in all five repeats. Only C10 and C11 could have shown the approved absence sentence, and they did not.

**Verdict.** The verdict rule requires all configurations complete and deterministic, with no security finding, no incomplete configuration, no unequal classes within a configuration and no construction-origin outcome. If no positive control has a complete observed failure, H_positive_scope is `holds`, H_negative_surface is `recorded_only` and the proposed verdict is `undocumented`. A script holding these rules, transcribed from `expected.yaml` and checked against its pinned SHA-256, derived the same verdict. It equals the verifier's `item_assessment` on C11, and C0 to C10 carry a null assessment, as the rules require for a nonfinal configuration. `undocumented` is the approved classification for these measured classes.
