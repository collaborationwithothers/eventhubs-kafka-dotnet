# C10: a consumer killed while holding an unprocessed message left no message marked done that nobody processed; some messages were processed twice

In run 45074268881 on Event Hubs Premium, a consumer in a two-member group was killed while it held a message it had not processed, and the other member took over its partitions; in all five repeats that stored each offset only after processing the message, and in all five that used librdkafka's default of storing it when the message is handed to the application, no message was marked done without being processed. In every repeat some messages were processed twice (2 to 4 per repeat when storing after processing, 1 to 5 with the default), which the librdkafka sources explain: after the crash the surviving member redoes the work done since the last periodic commit. Storing after processing lost nothing, so the proposed verdict is `confirmed`; the zero under the default store does not show that the default is safe, and the workload is synthetic.

Proposed verdict: `confirmed`.

## In plain words

**The production event.** A consumer has been running in a group and committing its progress. It is killed while it holds a message it has not processed yet, and another member of the group takes over its partitions. The question is whether that crash leaves any message marked done that nobody processed. "Marked done" means the group's committed offset for the partition has moved past the message, so no member will read it again.

**The two settings.** With the first setting (C0, the baseline), the application stores a message's offset only after it has processed the message. With the second (C1), librdkafka's default `enable.auto.offset.store` stores the offset as soon as the message is handed to the application, before the application has processed it. Only the killed consumer changes setting; the member that takes over runs the baseline in both. In both, librdkafka commits the stored offsets in the background every 5000 ms.

**What was measured.** In every repeat of both settings, zero messages were marked done without being processed. Some messages were processed twice: 2 to 4 per repeat when storing after processing, and 1 to 5 per repeat with the default.

**What the verdict means.** Storing after processing lost nothing, so the prediction is confirmed. The zero under the default store does not show that the default is safe. At this kill point a message can be marked done without being processed only if librdkafka commits in the short time between handing the message over and the kill, which is unlikely.

**Why some messages were processed twice.** Both settings showed it. It is the cost of committing periodically, called at-least-once delivery: after a crash, the surviving member starts from the last committed offset and redoes the work done since that commit. The run counted these messages; that they come from this cause is an inference from the librdkafka sources listed under Sources, not a measurement.

**What this result does not cover.** A consumer that dies before its first commit is a different failure with a different cause. It is tested under C01 (#513), not here.

## What was tested

Each repeat ran two consumers in one group: a subject that carried the fault and a witness that ran the baseline consumer and received the subject's partitions. The verifier counted 240 delivered synthetic events per repeat, in five repeats per configuration. C0 runs the baseline, which stores an offset after processing. C1 sets `enable.auto.offset.store` to `true` on the subject and changes nothing else; the witness runs the baseline in both configurations.

Kill point (from the expected outcome):

> The subject sends SIGKILL to itself when Consume returns its 110th message, before processing it (ADR-022). The witness runs the baseline.

Commit precondition (from the expected outcome):

> A repeat counts only when, in the archived consumer records, every partition assigned to the subject at the start line whose start offset is below its end offset has a successful subject commit entry for it with a row sequence below the subject's kill-intent row. Otherwise the witness starts that partition at the latest offset, and a loss there is not an offset-store effect. A repeat that fails it is reported, not counted.

No repeat failed the commit precondition: in all ten, every qualifying partition had a successful subject commit before the kill.

## Hypotheses

- H1, storing after processing loses nothing (C0): holds. All five repeats counted, and in each no message was committed without being processed.
- H2, the default automatic store can pass an unprocessed message (C1), published on its own line and not part of the verdict: inconclusive. All five repeats counted, and none had a message committed without being processed; a zero count does not contradict a possibility.
  Under this kill point a commit can pass an unprocessed message only if an auto-commit lands between Consume returning the 110th message and the kill, so loss under the automatic store is unlikely. A zero count does not show that the automatic store is safe.
- Processed again, recorded only and published on its own line: 2 to 4 messages per repeat in C0 and 1 to 5 in C1.

## Commit evidence

After each repeat the verifier read the group's committed offsets from Event Hubs without joining the group (`offset_read`, outcome `success` in all ten repeats). A repeat is complete and valid only when every committed offset it read matches an offset the members' own commit records report, and only when, on every partition that received messages during the run, the committed offset reached the run's end line. So "committed" here is observed from the broker, not only reported by the consumers.
