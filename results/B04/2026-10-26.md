# B04: idempotent producer confirmed on Event Hubs Premium

The final B04 run produced to the Event Hubs Premium namespace with `enable.idempotence: true` and `max.in.flight: 5` in five valid repeats, with no fatal client error and no reorder, so the proposed verdict is confirmed. Each configuration recorded 930000 ok outcomes and zero loss, phantom, reported failure and duplicate outcomes across these synthetic repeats. This result does not test whether Event Hubs discards a duplicate batch that an idempotent producer resends, and it changes no baseline setting.

Proposed verdict: `confirmed`.

## Assessment against expected.yaml

**C1.H1 holds.** The question in `expected.yaml` is "whether a Confluent.Kafka 2.16.0 producer with enable.idempotence true and max.in.flight 5 produces to the Event Hubs Premium namespace". The Confluent.Kafka runtime version is unavailable, as stated below; the recorded librdkafka version is 2.16.0. Microsoft states that Event Hubs for Kafka "supports both idempotent producers and idempotent consumers" ([Kafka overview, Idempotency](https://learn.microsoft.com/azure/event-hubs/azure-event-hubs-apache-kafka-overview#idempotency), read 2026-10-26). The four conditions in `expected.yaml` are met:

- `complete_valid_repeats: 5`: all five C1 repeats are `complete_valid`.
- `configuration_fidelity: pass_in_every_repeat`: inferred from pinned code, not read from the candidate, which has no fidelity field. See the next section.
- `verifier_ok: greater_than_zero_in_every_repeat`: each C1 repeat records 186000 ok outcomes.
- `fatal_errors: present_and_empty_in_every_repeat`: each C1 repeat records `fatal_errors: []`.

No eligible repeat records a fatal error, so the `contradicted_when` condition is not met. The file's basis is that librdkafka v2.16.0 transmits no idempotent producer message without a valid producer ID: for an idempotent producer, its broker code does not transmit a partition's messages while the producer ID is not valid ([rdkafka_broker.c L4295-L4300](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka_broker.c#L4295-L4300)). That the native client ran with idempotence enabled is an inference from the configuration fidelity check below. The candidate does not record the native client's effective idempotence state.

**C1.H2 holds.** All five C1 repeats are `complete_valid` and each records zero reorders. librdkafka states "With Idempotent Producer enabled there is no risk of reordering despite `max.in.flight` > 1 (capped at 5)" ([INTRODUCTION.md L536-L537](https://github.com/confluentinc/librdkafka/blob/v2.16.0/INTRODUCTION.md#ordering-and-message-sequence-numbers)). Comparison limit, from `expected.yaml`: C0 differs from C1 in both `enable.idempotence` and `max.in.flight`, so the difference between C0's 25 reorders and C1's zero is not attributed to idempotence alone.

**C0.H3 and C1.H3 are recorded only.** The verifier counts, delivery error codes, fatal errors and broker counts above are their record. They have no pass or fail expectation.

**Verdict.** `expected.yaml` sets `confirmed_when: C1.H1 holds`, so the proposed verdict is `confirmed`. Its subject is Event Hubs Premium support for the idempotent producer of a librdkafka client. H2 and H3 are published without changing the verdict. The exactly-once claim is not tested (N1 below). Baseline effect: none. `enable.idempotence` stays `false` for v1 whatever the verdict, as [Hari decided](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/201#issuecomment-6409664176).

## Not tested

**N1.** Whether Event Hubs discards a duplicate batch that an idempotent producer resends after a retry is not decidable at build scale with the current oracle. ADR-013 invalidates any repeat with a request timeout, retry or asynchronous delivery failure, and no approved live fault produces retries at the approved load. Microsoft's configuration page says to keep idempotence enabled "for exactly-once producer semantics" while listing exactly-once semantics as not currently supported ([configuration page](https://learn.microsoft.com/en-us/azure/event-hubs/apache-kafka-configurations), read 2026-10-26). This result does not resolve that conflict. [#204](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/204) holds it.

**K53.** Whether idempotence survives a producer pod restart is not tested. A restart creates a second registered producer instance in the repeat, which ADR-012 and ADR-020 invalidate, and [Hari decided](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/201#issuecomment-6409664176) to record it as not tested in B04. A non-transactional idempotent producer requests its producer ID without a transactional ID ([rdkafka_idempotence.c L320-L326](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka_idempotence.c#L320-L326)), and librdkafka documents `transactional.id` as the setting that identifies a producer across process restarts ([CONFIGURATION.md](https://github.com/confluentinc/librdkafka/blob/v2.16.0/CONFIGURATION.md)). Inventory amendment 1 also lists K-53 under B10.
