# E01: an empty value and a null value stay distinct on Event Hubs

Across 10 complete synthetic repeats in two deterministic configurations, a produce with an empty value read back as an empty value in all five repeats of C0, and a produce with a genuine null value read back as a null value in all five repeats of C1. Each target followed an independently read non-null seed on the same key and partition, so H_transport holds. The proposed E01 verdict is `confirmed`, for transport on one partition only: compaction, tombstone retention and deletion were not tested.

Proposed verdict: `confirmed`.

Second, a fresh `probe` consumer reads that seed at its delivered location. Third, a fresh `probe` producer writes the target to partition 0 explicitly: an empty byte array in C0 and a genuine null in C1. Fourth, another fresh `probe` consumer reads the target at its delivered location. The seed offset was lower than the target offset, and the key and partition were the same, in all 10 repeats. This is checked by script against the pod captures. C0 is the control: it must read back five empty values before C1 can decide anything.

## Assessment against expected.yaml

The pinned Confluent.Kafka v2.16.0 byte-array [serializer](https://github.com/confluentinc/confluent-kafka-dotnet/blob/v2.16.0/src/Confluent.Kafka/Serializers.cs#L175-L180) returns its input unchanged, and the byte-array [deserializer](https://github.com/confluentinc/confluent-kafka-dotnet/blob/v2.16.0/src/Confluent.Kafka/Deserializers.cs#L237-L246) returns `null` when the record value is null and a copy of the bytes otherwise. So the client keeps the two cases apart at both ends.

Microsoft's [log compaction page](https://github.com/MicrosoftDocs/azure-docs/blob/c479cc3fd5f3727448596c3a3b7b339fe2677227/articles/event-hubs/log-compaction.md) says: "Client applications set tombstones by sending a new event with an existing key and a `null` event payload." It also says consumers "can still see events that are marked to be deleted for the time defined by *Tombstone Retention Time(hours)*". Both lines were read on 2026-11-01 at the pinned revision.

**H_transport holds.** Its question is whether independent readback preserves an empty value versus a genuine null tombstone after a non-null seed. C0 has five complete successful empty reads, so the control passes. All five C1 reads are exact nulls. No C1 repeat read back an empty or non-empty value, and no repeat had an error or a missing target record.

**Verdict.** The verdict rule is "C0 must have five complete successful empty reads ... With that C0, five C1 successful exact null reads -> holds/confirmed". So the proposed verdict is `confirmed`. A script holding these decision rules, transcribed from `expected.yaml` and checked against its pinned SHA-256, derived the same verdict. It equals the verifier's `item_assessment` on C1, and C0 carries a null assessment, as the rules require for a nonfinal configuration.

What this shows: for a keyed record on one partition of this event hub, the Kafka produce and consume path keeps a null value distinct from an empty value. The Microsoft page's way of writing a tombstone, a new event with an existing key and a null payload, therefore reaches the consumer as a null. That is consistent with the page. The documented effects of a tombstone are separate claims and are not tested.

## Not tested

Compaction timing and whether compaction ran, deletion of the seed or of older records for the key, tombstone retention, a consumer that starts after compaction, recovery after deletion, other partitions, several values per key, and other clients. Whether a null produced by a non-Kafka client such as the Event Hubs SDK is seen as a null. No claim about the 168-hour retention setting follows, because it was not observed.
