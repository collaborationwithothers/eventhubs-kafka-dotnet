# F01: our OAuth refresh handler kept the same native clients working under a capped token expiry

In run 41201284963, the token expiry passed to Kafka was capped at 5 s for the test, and in all five producer and five consumer repeats librdkafka called our refresh handler again on the same native clients. Each time the handler called the Identity SDK, the returned token installed, and one delivery or read then succeeded before the 20 s cutoff. The token the SDK returned had the same expiry time on every call, which indicates a cached token, so this tests only our handler's refresh path, not natural expiry, new token issuance, assertion rotation or broker re-authentication.

Proposed verdict: `undocumented`. Microsoft's [Apache Kafka developer guide for Azure Event Hubs](https://learn.microsoft.com/en-us/azure/event-hubs/apache-kafka-developer-guide) lists its OAuth samples as "Java and Go samples for OAuth authentication" (read 2026-11-01), so the .NET refresh-handler path that worked here is not covered by that guidance. A pinned script, not the repository's verifier, judged the refresh-handler records; Hari accepted that for this item only in [decision 6561458447](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/306#issuecomment-6561458447) on issue 306.

## What was tested

The F01 row of docs/blueprint.md ("Inventory amendment 1", line 1103) follows [decision 6532364305](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/245#issuecomment-6532364305). It treats the Identity SDK as a black box and adds a test-only cap on the token expiry passed to Kafka. It then asks four things of the same native producer and consumer clients. Does native scheduling call our refresh handler again? Does the handler call the Identity SDK again? Does the returned token install? Do producer delivery and consumer reads continue? A cached SDK token passes.

The cap is 5000 ms. The section "Separately selected handler refresh-path diagnostic" of `docs/operations/authentication-lifecycle-observation.md` says the test session "is callable only for the fixed 5000 millisecond cap". Production sessions stay uncapped.

The ordinary actors are five C6 seed producers on service account `loadgen` and five C9 action consumers on service account `enrichment-consumer`. The C6 action rows, from service account `probe`, are context only, under the probe namespace-role exception. Each client has a 20 s observation window.
