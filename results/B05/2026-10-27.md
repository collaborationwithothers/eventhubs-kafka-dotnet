# B05: InitTransactions succeeds on Event Hubs Premium

InitTransactions returned without error in all five fresh producers, so H1 holds and the proposed B05 verdict is confirmed. This confirms the transactions page, which says Kafka transactions are in public preview in Premium, and contradicts the configurations page, which lists transactions as not currently supported. Only InitTransactions was tested in these synthetic repeats; begin, commit, abort and exactly-once semantics were not.

Proposed verdict: `confirmed`.

Each repeat is one fresh producer that calls `InitTransactions` once. Configuration C1 sets `transactional.id: b05-probe`, `enable.idempotence: true`, `max.in.flight: 5` and `message.timeout.ms: 60000`. The last three exist so that librdkafka v2.16.0 can construct a transactional producer from the baseline, which sets `enable.idempotence: false`, `max.in.flight: 1000000` and `message.timeout.ms: 300000` explicitly ([BaselineSettingsCatalog.cs L99, L107 and L117](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/blob/7b6834c5e8668e89376597bc2b524c0725326daf/src/Parchwell.Kafka/Configuration/BaselineSettingsCatalog.cs#L99-L117)). librdkafka then rejects `transactional.id` with idempotence explicitly false ([rdkafka_conf.c L4579-L4588](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka_conf.c#L4579-L4588)), an explicit `max.in.flight` above 5 with idempotence ([L4604-L4616](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka_conf.c#L4604-L4616)), and an explicit `message.timeout.ms` above `transaction.timeout.ms` ([L4772-L4781](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka_conf.c#L4772-L4781)). The plan records this as fact F1. These settings are not a transaction recommendation. The action window is 150000 ms.

## Assessment against expected.yaml

This item is documentation conflict 6. The [transactions page](https://learn.microsoft.com/en-us/azure/event-hubs/apache-kafka-transactions) says "Kafka Transactions is currently in Public preview in Premium, and Dedicated tier." The [configuration page](https://learn.microsoft.com/en-us/azure/event-hubs/apache-kafka-configurations) lists Transactions as "Not currently supported." Both were read on 2026-10-27.

**H1 holds.** `InitTransactions` returned in all five repeats. Its rule is `confirmed_when: "Returned InitTransactions confirms S18 and contradicts S1."` S18 is the transactions page and S1 the configuration page.

**H2 is contradicted.** Its `contradicted_when` is the same returned call.

**Verdict.** The verdict rule is "H1 returned InitTransactions confirms S18 and contradicts S1; H2 errored call confirms S1 and contradicts S18." H1 holds, so the proposed verdict is `confirmed`. It confirms the transactions page and contradicts the configuration page's "Not currently supported" entry, for this one call. A script holding these decision rules, transcribed from `expected.yaml` and checked against its pinned SHA-256, derived the same verdict; it equals the verifier's `item_assessment`.

Not tested: `BeginTransaction`, producing inside a transaction, `CommitTransaction`, `AbortTransaction`, `SendOffsetsToTransaction`, `read_committed` consumers, and exactly-once semantics. The transactions page describes `initTransactions()` as the call that "ensures that the producer registers with the broker as a transactional producer". So a returned call is evidence for that registration only. It does not show that a full transaction commits or aborts correctly. This result changes no baseline setting.
