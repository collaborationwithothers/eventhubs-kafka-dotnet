# A04: with `connections.max.idle.ms=180000` each producer's first idle-window disconnect came before 225000 ms and every repeat was kept; with the key omitted, no repeat was kept

In batch run 41602168787 on Event Hubs Premium, five fresh synthetic producers per configuration each produced one record, stayed idle for 420 s and produced again: C0 with `connections.max.idle.ms` omitted, so librdkafka leaves it unmodified, and C1 with `connections.max.idle.ms=180000`, the value Microsoft gives for Java clients and in its troubleshooting table but not in its librdkafka table; both set `metadata.max.age.ms` and `topic.metadata.refresh.interval.ms` to 900000. In every C1 repeat the first idle-window disconnect came 179756 ms to 194777 ms after idle start, after 164753 ms to 179774 ms of quiet, so H_client_close, which is decided by the timing of the first idle-window disconnect whichever side closed it, holds and every C1 repeat was `kept` (5 `kept`), while no C0 repeat was (4 `closed_while_idle`, 1 `timed_out_on_resume`). Because `connections.max.idle.ms` is absent from Microsoft's librdkafka table, the expected.yaml rules fix the verdict as `undocumented`, reason `not_in_librdkafka_table`.

Proposed verdict: `undocumented`.

## Repeat outcomes

The verifier judged every repeat under the [idle-observation judgement](../../docs/operations/verifier-contract.md#idle-observation-judgement). A disconnect is classed only by its quiet period: the smaller of `txidle` and `rxidle` in the statistics report before the disconnect. It counts as `idle_timed` when that period is at least 225000 ms. That threshold is a harness choice, not a measurement: Microsoft's stated 240000 ms idle limit minus one 15000 ms report interval. No report names who closed a connection. A repeat is `closed_while_idle` when an `idle_timed` disconnect falls in the idle window, `stale_on_resume` when one falls only in the resume window, `timed_out_on_resume` when neither does but one broker shows a request timeout, then a disconnect, then a connect after the idle window, and `kept` otherwise; the first three are `not_kept`.

## Assessment against expected.yaml

Microsoft's [client configuration page](https://github.com/MicrosoftDocs/azure-docs/blob/6da87e3c59251e962dd0b37dbd99ae364d767150/articles/event-hubs/apache-kafka-configurations.md) lists `connections.max.idle.ms` in its Java table with default 540000, recommended value 180000 and the constraint "Must be < 240000" (line 59), and its troubleshooting table gives "Set `connections.max.idle.ms=180000` and `metadata.max.age.ms=180000`" for "Expired batches or send timeouts" (line 133). Its librdkafka tables (lines 90 to 123) do not list the key. The page was read on 2026-11-03 at that revision, whose front matter has `ms.date: 12/17/2025`, and the [live page](https://learn.microsoft.com/en-us/azure/event-hubs/apache-kafka-configurations), read the same day, has the same rows. librdkafka v2.16.0 documents `connections.max.idle.ms` as "Close broker connections after the specified time of inactivity", default 0, up to 2 s lower for jitter ([CONFIGURATION.md](https://github.com/confluentinc/librdkafka/blob/v2.16.0/CONFIGURATION.md), line 35).

The precedence in expected.yaml is: "smoke run -> null, `smoke_only`; a missing candidate or any configuration not `complete_valid` -> null, `incomplete_configuration`; any repeat `first_failed` -> `untestable`, `first_produce_failed`; any configuration whose five repeats do not share one survival -> null, `unequal_classes`; then the item rule." The item rule is: "holds when every C1 repeat's first idle-window disconnect has `first_close_quiet_ms >= 163000` and `first_close_after_idle_ms < 225000`; else, including a repeat with no idle-window disconnect, contradicted. `H_default_close` (C0): recorded only. Verdict: undocumented, `not_in_librdkafka_table`." The 163000 ms quiet floor is a harness choice, not a measurement: 180000 ms minus the 2000 ms jitter, minus one 15000 ms report interval.

## The resume timeout class decided C0

`timed_out_on_resume` was designed after batch run 41534423570 was seen, under the silent-drop decision, and is applied only to a later run: this run's source commit contains it, and run 41534423570 was judged at `9014b8effd4f8556d3446bcfbf8f951a52905bb2`, without it. In this run it decided C0. C0 repeat 3 recorded no disconnect in the idle window, although its largest quiet period was 419829 ms. Its second produce succeeded after 60466 ms. In report 33, broker 8 recorded one request timeout, one disconnect after 59744 ms of quiet and one connect, the resume timeout sequence. Recomputed by the generator from the candidate's window counts, not by the verifier: under the rules at `9014b8effd4f8556d3446bcfbf8f951a52905bb2` that repeat would be `kept`, C0 `unequal`, and the item would have no verdict, reason `unequal_classes`. The silent-drop decision records the inference, not a measurement, that such a connection was already unusable after the idle period and that the client learned it only from the request timeout.
