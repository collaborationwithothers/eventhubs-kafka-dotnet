# A02: producer connections were not kept across a 420 s idle period with `socket.keepalive.enable=true`, as without it

In batch run 41602168787 on Event Hubs Premium, five fresh synthetic producers per configuration each produced one record, stayed idle for 420 s and produced again: C0 with `socket.keepalive.enable=false`, the librdkafka default, and C1 with `true`, Microsoft's recommendation, both with the node's keepalive timers unchanged and both metadata timers at 900000 ms. No producer kept its connections in either configuration (C0: 4 `closed_while_idle`, 1 `timed_out_on_resume`; C1: 4 `closed_while_idle`, 1 `timed_out_on_resume`), so the expected.yaml rules select `contradicted`, reason `closed_with_keepalive`, for Microsoft's note that `true` is "Required to prevent idle connection closure". Whether Event Hubs counts TCP keepalive probes as activity (K-37) was not tested, and this result implies no answer to it.

Proposed verdict: `contradicted`. The merged decision rules select it for this run.

## Repeat outcomes

The verifier judged every repeat under the [idle-observation judgement](../../docs/operations/verifier-contract.md#idle-observation-judgement). A disconnect is classed only by its quiet period: the smaller of `txidle` and `rxidle` in the statistics report before the disconnect. It counts as `idle_timed` when that period is at least 225000 ms. That threshold is a harness choice, not a measurement: Microsoft's stated 240000 ms idle limit minus one 15000 ms report interval. No report names who closed a connection. The resume timeout sequence is, on one broker connection, a request timeout, then a disconnect, then a new connection attempt, each counted in a report after the idle window and no later than the first report at or after the second produce's outcome. A repeat is `closed_while_idle` when an `idle_timed` disconnect falls in the idle window, `stale_on_resume` when one falls only in the resume window, `timed_out_on_resume` when neither does and the resume timeout sequence occurs, and `kept` otherwise; the first three are `not_kept`.

## Connections closed after the idle period

In C0 repeat 1 and C1 repeat 3, one broker connection stayed `UP` with no disconnect through the idle window, and its quiet period reached 419281 ms and 419823 ms, above the 225000 ms threshold. After the second produce was sent, one statistics report recorded on that connection a request timeout, a disconnect and a new connection attempt: the resume timeout sequence. The quiet period in the report before that disconnect was 59179 ms and 59747 ms, below the threshold, so the disconnect itself counts as `other_cause`. The client reconnected, and the second record was delivered with a latency of 61073 ms and 60474 ms. Inferred, not measured, as the verifier contract states: such a connection was already unusable after the idle period, and the client learned it only from the request timeout.

In the other eight repeats, the one `idle_timed` disconnect in the idle window followed a quiet period of 284287 ms to 359835 ms, with no request timeout, and the second produce succeeded with a latency of 50 ms to 1581 ms. Every idle window recorded 0 Metadata requests. Which side closed any connection is not recorded.

## Not tested

With the AKS default keepalive time of 7200 s recorded in K-35 of the [research catalogue](../../docs/research/kubernetes-kafka-clients.md), no keepalive probe is expected inside a 420 s idle period; that is inferred, not observed. Also not tested: a pod sysctl or any other keepalive timer, consumers, idle periods other than 420 s, clients other than librdkafka 2.16.0 through Confluent.Kafka 2.16.0.0, tiers other than Premium, and which side closed a connection.
