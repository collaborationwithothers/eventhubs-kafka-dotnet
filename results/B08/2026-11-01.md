# B08: the two librdkafka partitioners send one key to different partitions

Across 10 complete synthetic repeats in two deterministic configurations, the default `consistent_random` partitioner delivered the fixed key to partition 30 in all five repeats, and `murmur2_random` delivered it to partition 2 in all five. Each partition equals the one computed from the pinned librdkafka v2.16.0 algorithms for an event hub with 32 partitions, so H_partition holds. The proposed B08 verdict is `confirmed`, for one key on one 32-partition event hub.

Proposed verdict: `confirmed`.

## Independent check of the partitions

The partitions above are measurements. A separate script computes what the pinned algorithms predict, so the two can be compared. For a non-empty key, `consistent_random` is `rd_crc32(key) % partition_count` and `murmur2_random` is `(rd_murmur2(key) & 0x7fffffff) % partition_count` ([rdkafka_msg.c L1063-L1108](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka_msg.c#L1063-L1108)). `rd_murmur2` is the Java-compatible hash in [rdmurmur2.c](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdmurmur2.c#L57) and `rd_crc32` is the standard reflected CRC-32 in [rdcrc32.h](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdcrc32.h#L161). The script's Murmur2 port reproduces all 11 vectors in the source unit test before it is used.

For the key `b08-synthetic-0` and 32 partitions, CRC-32 is 2046850398, so `consistent_random` gives partition 30. Murmur2 is 2245682434, so `murmur2_random` gives partition 2. These are computed expectations from source, not measurements. The measured partitions equal them in all 10 repeats. The result was not tuned to fit: the key and the partition count are fixed by the approved scenario, and the expectation was computed in the [plan](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/240#issuecomment-6490062145) before the run.

## Assessment against expected.yaml

Microsoft's [client configuration page](https://github.com/MicrosoftDocs/azure-docs/blob/6da87e3c59251e962dd0b37dbd99ae364d767150/articles/event-hubs/apache-kafka-configurations.md) lists `partitioner` with default `consistent_random` under "Configurations to keep at defaults", with the note "Handles null keys well; change only for specific key distribution needs". It also lists "Custom partitioner on server side" as not supported, with the reason "Partition assignment is client-side only". Both lines were read on 2026-11-01 at the pinned page revision, whose front matter has `ms.date: 12/17/2025`. The librdkafka [configuration reference](https://github.com/confluentinc/librdkafka/blob/v2.16.0/CONFIGURATION.md?plain=1#L196) describes `murmur2_random` as functionally equivalent to the default partitioner in the Java Producer.

**H_partition holds.** Its question is whether automatic partition selection matches the pinned client algorithms on Event Hubs. Both configurations are complete and successful, all five delivered and read partitions are 30 in C0 and 2 in C1, and the key, value and location match exactly. Its rule has no contrary-partition, error or incomplete branch to apply: no repeat carries `v2_location`, and no repeat or configuration has an error.

**Verdict.** The verdict rule is "both complete successful configurations, all five delivered/read partitions 30/2 respectively, exact key/value/location -> H_partition=holds, confirmed". So the proposed verdict is `confirmed`. A script holding these decision rules, transcribed from `expected.yaml` and checked against its pinned SHA-256, derived the same verdict. It equals the verifier's `item_assessment` on C1, and C0 carries a null assessment, as the rules require for a nonfinal configuration.

What this shows: with Event Hubs, the client library alone decides the partition for a keyed message, and the two built-in hash partitioners place the same key on different partitions (30 and 2 for this key). That is consistent with the page's statement that partition assignment is client-side. It follows, as an inference not tested here, that changing `partitioner` on an existing event hub changes the partition that a given key maps to, so per-key ordering across the change is not preserved by the broker. The page's advice to keep `consistent_random` is neither confirmed nor contradicted by this run.
