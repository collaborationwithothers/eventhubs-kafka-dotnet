# C5 failure causes

This change set removes two causes that made paired C5 mutation runs on `main` fail without any mutation being at fault, and lets one lost shard be recovered without re-running the whole pair. The first cause is an intermittent verifier test failure: the consumed-metadata capture times its Blob writes on the real clock while the test drives the handler with a manual clock. The second is the companion evidence download deadline of 240 seconds, which one pair exhausted. The recovery item lets the aggregate accept a later attempt's evidence for exactly the shards that were re-run, under the same checks.

Revision R6. Base `main` commit `4ea8fae3d52111e37028c39033430bc0a3c40776`. One pull request, named `494-c5-failure-causes`.

### Diagnosis of the intermittent test

Evidence: [issue 593](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/issues/593) records that Stryker's unmutated initial run in shard `b10-final-projection-codec-p2-a` of [run 45459740602](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/actions/runs/45459740602) failed `B10SweepHandlerTests.Given_FiveEligibleRepeats_When_Swept_Then_ImmutableResultsReceiveFinalCountsAfterCleanup(phase: "C1")` at line 54, `Assert.True(capture.RootElement.GetProperty("complete").GetBoolean())`. The same shard passed on the same commit in run 45449734959.

Source facts, read on `main` at the base commit:

1. `ConsumedMetadataCapture.Seal` (chunk upload) and `ConsumedMetadataCapture.Finish` (`capture.json` write) each create `new CancellationTokenSource(_options.BlobIoTimeout!.Value)` at `src/Parchwell.Verifier/VerifyRun/Window/ConsumedMetadataCapture.cs` lines 179 and 218. That constructor counts on the system clock.
2. Every other Blob or cleanup deadline in the verifier handlers uses the injected clock, for example `B10SweepHandler.Bounded` at `src/Parchwell.Verifier/VerifyRun/B10SweepHandler.cs` lines 305-313 and the cleanup deadline at line 121.
3. `WindowConsumer.Drain` receives that clock as `timeProvider` but calls `capture?.Observe(record)` and `capture?.Finish(complete, interrupted)` without it (`src/Parchwell.Verifier/VerifyRun/Window/WindowConsumer.cs` lines 31, 73, 88 and 93).
4. The test's options come from `HostEvidenceBuilder`, which sets `BlobIoTimeout = TimeSpan.FromMilliseconds(100)` (`tests/Parchwell.Verifier.Tests/Support/HostEvidenceBuilder.cs` line 177). The handler runs on `ManualKafkaTimeProvider`, which never advances in this test (`tests/Parchwell.Verifier.Tests/Support/KafkaSessionTestSupport.cs` lines 149-185).
5. The test store copies the chunk with `content.CopyToAsync(buffer, cancellationToken)` (`tests/Parchwell.Verifier.Tests/Host/B10SweepHandlerTests.cs` lines 557-564). When the real 100 ms expires first, the copy throws, `Seal` records gap `upload_failed`, and `capture.json` is written with `complete` false. A failure of the later `capture.json` write would instead leave no `capture.json` and fail the count assertion at line 46, not line 54.

Reproduction, run in this planning session on 2026-11-24 in a scratch worktree at the base commit, Release build, one run per setting, with a temporary real-time `Thread.Sleep` added before the store's copy:

| Store delay | Without fix | With prototype fix |
|---|---|---|
| none | 2 of 2 cases pass | not run |
| 0 ms | 2 of 2 pass | not run |
| 50 ms | 2 of 2 pass | not run |
| 150 ms | 2 of 2 fail, at line 54 | 2 of 2 pass |
| 1,500 ms | not run | 2 of 2 pass |

The prototype passed the capture's deadlines the clock that `Drain` receives. Conclusion: the cause is that the capture's Blob deadlines use the system clock while the test's handler uses a manual clock with a 100 ms Blob budget, so any real delay of 100 ms or more inside a chunk upload fails the capture. This is established by source and reproduction. Which gap code the CI run recorded is not observable from its log; `upload_failed` is inferred, because it is the only gap path in `Seal` that depends on elapsed time. What delayed the CI run by 100 ms or more is not known; CPU contention from Stryker's parallel test workers is a hypothesis, not a finding.

The fix is in the product, at the cause, not in the test: the capture's deadlines use the clock its caller already uses for every other deadline. Production behaviour does not change, because the verifier host registers `TimeProvider.System` (`src/Parchwell.Verifier/Program.cs` line 104). The assertion at line 54 and the test stay unchanged.

In the failed run, 143 of 146 archives had finished when the 144th request (`workload-p1`, index 143 in sorted order) timed out once and the deadline ended the step. At the same rate the 146 archives would have taken about 245.3 s; that is an estimate from the run's own rate, dated 2026-11-24. The four successful downloads took between 92.7 s and 167.9 s.

New value: `DEADLINE = 600`. Basis: it is 3.57 times the longest successful download and 2.4 times the estimate for the failed one. The deadline only ends a download that is still running; a download that finishes earlier takes the same time as before.

Effect on the paired limit: none for a download that finishes within 240 s. A download that takes between 240 and 600 s now completes, and up to 360 more seconds count against the limit. The terminal checker then reports the campaign as `met` or `missed` with complete evidence, instead of the aggregate reporting it incomplete. Against the earlier 3,000-second limit, once every step except the download is counted, run 45374369955 left 204 s for its download, and run 45459740602 left 8 s; the failed run 45449734959 reached the download step at 2,780 s and needed about 245 s more for downloads alone. Against the 4,200-second limit those margins are 1,404 s and 1,208 s, and the failed run reached the download step with 1,420 s left. This change removes a failure mode; it does not create campaign time.

### Lost-shard recovery design

Facts the design rests on, read on `main` at the base commit unless stated:

1. The aggregate already takes each shard's origin `(run_id, run_attempt)` from the campaign manifest, opens `c5-mutation-<run_id>-<run_attempt>-<shard>`, and requires the receipt's `run_id` and `run_attempt` to equal that origin (`tests/Parchwell.Verifier.Tests/Mutation/c5_workflow.py` lines 1544-1551 and 1586-1591). Its "unexpected shard directories" check compares the input directory with those exact names (lines 1552-1560). So `c5_workflow.py` needs no change if the manifest names the right origins and the input directory holds exactly those archives.
2. `validate_manifest` requires every shard of a run to carry that run's single attempt (`tests/Parchwell.Verifier.Tests/Mutation/c5_campaign.py` lines 125-154, the check `manifest['shards'] == origins` at line 153). Both the aggregate and the terminal check call it. So recovery needs a change to `c5_campaign.py`.
3. The coordinator workflow downloads its own evidence with the pattern `c5-mutation-${{ github.run_id }}-${{ github.run_attempt }}-*` and then runs `c5_companion_artifacts.py --manifest` for the companion (`.github/workflows/verifier-c5-mutation.yml` lines 456-472). In a re-run attempt, that pattern finds only the re-run coordinator shards. The companion downloader is not a qualification input and decides from the manifest what it fetches, so it can also fetch the carried-over coordinator shards. The workflow files need no change.
4. GitHub's documentation, read with a web-fetch subagent on 2026-11-24 ([Re-run workflows and jobs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)), states: "When you re-run failed jobs or a specific job, GitHub also re-runs the jobs that depend on them"; jobs not included "keep their outputs from the previous attempt"; the re-run uses "the same `GITHUB_SHA` (commit SHA) and `GITHUB_REF`"; re-runs are possible "up to 30 days after its initial run"; and "A workflow run can be re-run a maximum of 50 times". It says nothing about the jobs API per attempt or about artifacts of earlier attempts.
5. Observed in this session on coordinator run [44895967958](https://github.com/collaborationwithothers/eventhubs-kafka-dotnet/actions/runs/44895967958), whose attempt 2 re-ran one failed shard and the aggregate: `attempts/2/jobs` lists all 257 jobs, each with a new job ID and `run_attempt` 2. The carried-over jobs keep their attempt-1 `started_at` (for example 10:47:08Z), `completed_at` and conclusion, but get the new attempt's `created_at` (11:49:46Z for `phase-p1`, against `started_at` 10:47:09Z); the same jobs in attempt 1's list have their original `created_at` (10:47:05Z for `phase-p1`). The re-run job's `started_at` is after attempt 2's `run_started_at` of 11:49:44Z. Attempt 1's `created_at` is 10:47:03Z and attempt 2's is 11:49:45Z. The run's artifact list holds both attempts' archives, and only the re-run shard has `-2-` archives. This is one observation, not documented behaviour; every check built on it fails closed.
6. Shard jobs never run `c5_campaign.py`: the only workflow reference is the aggregate job's `prepare` step (`.github/workflows/verifier-c5-mutation.yml` line 442), and `c5_workflow.py` imports it only inside `aggregate` (line 1522). `c5_campaign.py` is in `NON_RENEWABLE` (`c5_runtime.py` lines 337-338), so today any change to it rejects every retained timing record.

Design:

- **Origin rule.** For a run whose latest attempt is N, the origin attempt of a shard is the largest k in 1..N whose attempt document's `run_started_at` is at or before the shard job's `started_at` in attempt N's job list. The shard is accepted from attempt k only if attempt k's job list has a job of the same name with the same `started_at` and conclusion `success`, and attempt N's job list shows it with conclusion `success`. A shard whose origin is above 1 is a re-run shard. This identifies exactly the re-run shards, and the aggregate's existing receipt check then requires the receipt's `run_attempt` to equal that origin.
- **Manifest.** `prepare` writes schema 1, byte for byte as today, when both runs are at attempt 1. Otherwise it writes schema 2, which adds `first_created_at` (attempt 1's `created_at`) to each run and lets a shard's `run_attempt` be any origin from 1 to its run's attempt. The summary artifact `c5-summary-<run>-<attempt>` already contains `campaign.json`, bound by `campaign_manifest_sha256`; that is the record of which shard came from which attempt.
- **Companion attempt.** `prepare` reads the companion run's latest attempt from `actions/runs/<id>` and uses it when it is at or above the dispatched `companion_run_attempt` input; it polls that attempt as today.
- **Downloads.** For a schema 2 manifest, the downloader fetches every companion shard at its origin, and every coordinator shard whose origin differs from the coordinator's current attempt, by exact name from each run's artifact catalogue. For schema 1 it behaves exactly as today.
- **Terminal check.** For schema 2, elapsed time runs from the earlier `first_created_at` to the later completion of the two latest attempts. A carried-over job's timing comes from its record in its origin attempt's job list, because its record in a later attempt carries that attempt's `created_at`; every timing chain starts at `first_created_at`. For schema 1 it is unchanged. This keeps the measurement "from the first run's creation through the last completion" for a recovered campaign; measuring from a re-run attempt's own `created_at` would shorten it.
- **Qualification.** `c5_runtime.py` (the checker, not a qualification input) gains one exact exception in `input_maps`: when a tree's `c5_campaign.py` equals one reviewed hash pinned in the checker, its executable `c5_workflow.py` hash equals the pinned base value and neither the companion workflow nor the coordinator's mutation job mentions `c5_campaign`, the map records `c5_campaign.py` at its base hash. This follows `execution_workflow`, which already normalizes one reviewed workflow step. Every comparison then sees the validator unchanged, so no assessment of it is written. Every other nonrenewable rule is unchanged, and a validator one byte off the pin is compared as today. A prototype of this exception, run in this session on the base commit, gave `not_applicable` with `--base` and `qualified` without it; with the validator one byte off the pin, both gave `rejected` with `invalid_estimate`, `invalid_renewal`, `missing_measurement`, `stale_inputs` and `unaccounted_inputs`.
- **Procedure.** A lost coordinator shard: re-run the coordinator's failed jobs, which re-runs the shard and the aggregate. A lost companion shard: re-run the companion's failed jobs; when that attempt completes, re-run the coordinator's failed jobs, which re-runs the aggregate. Both: companion first.

## External contracts

- **Capture deadlines.** When `WindowConsumer.Drain` is given a `TimeProvider` and a capture, the capture's chunk-upload deadline and its `capture.json` write deadline are each `BlobIoTimeout` measured on that `TimeProvider`. A capture used without a `TimeProvider` keeps the system clock. The `capture.json` wire format, gap codes (`upload_failed`, `write_failed`, `byte_limit`, `row_limit`, `interrupted`, `source_window_incomplete`) and the `complete` rule `sourceComplete && gaps.Count == 0 && observed == captured` are unchanged. How the clock reaches the capture (an optional parameter, a field set at start, or another shape) is the implementer's choice, provided the existing direct callers in `ConsumedMetadataCaptureTests.cs` compile and keep the system clock.
- **Download deadline.** `DEADLINE = 600` in `c5_companion_artifacts.py`. `SPACING = 0.2`, `TIMEOUT = 15` and `ATTEMPTS = 4`, the request, retry, catalogue and verification behaviour, the CLI and its messages are unchanged. The aggregate workflow and its command line are unchanged.
- **Campaign manifest.** Schema 1 is unchanged and is what `prepare` writes when both runs are at attempt 1. Schema 2 has exactly the keys `schema` (2), `repository`, `commit`, `runs`, `shards`, `incomplete_reasons`. Each `runs.<role>` has exactly `id`, `attempt` (the attempt measured, at least 1), `path`, `created_at` (that attempt's) and `first_created_at` (attempt 1's, not later than `created_at`). Each `shards.<shard>` has exactly `target`, `run_id` (its role's run ID as a string) and `run_attempt` (its origin, a decimal string from `"1"` to its run's `attempt`). At least one shard's `run_attempt` differs from its run's `attempt`, or a run's `attempt` is above 1. `validate_manifest` accepts both schemas and returns the per-shard origins. Error messages of existing checks are unchanged; new failures use the reasons named in the requirements.
- **Performance limit.** `BUDGET = 4200` in `c5_campaign.py`; the terminal report's fields, statuses and reasons are unchanged.
- **Attempt limit.** `prepare` considers at most 5 attempts per run (`MAX_ATTEMPTS = 5`). A run whose latest attempt is above 5 adds reason `too many run attempts` and the manifest is incomplete.
- **Aggregate.** `c5_workflow.py`, its CLI, receipts and `summary.json` are unchanged. Both workflow files are unchanged.
- **Qualification.** `c5-runtime-qualification.json` keeps schema version 2, every target record, measured map, timing evidence entry and estimate. Only the top-level `shared_inputs` hashes of the four changed C# shared inputs and their per-context v2 assessments change, as `renew` writes them. Its `c5_campaign.py` entry keeps the base hash under requirement 15.

## Requirements

1. WHEN `WindowConsumer.Drain` drains a window with a capture and its `TimeProvider` does not advance, THEN a store write that takes longer than `BlobIoTimeout` in real time does not cancel the capture's chunk upload or `capture.json` write, and the capture is written with `complete` true.
2. WHEN the `TimeProvider` given to the capture advances by `BlobIoTimeout` or more during a chunk upload, THEN the upload's token is cancelled and a store that honours it leaves gap `upload_failed` at the chunk's first ordinal, as today on the system clock.
3. WHEN the `TimeProvider` given to the capture advances by `BlobIoTimeout` or more during the `capture.json` write, THEN a store that honours the token writes no `capture.json`, as today.
4. WHEN a capture is used without a `TimeProvider`, THEN its deadlines run on the system clock, so a store write that takes longer than `BlobIoTimeout` in real time leaves gap `upload_failed`.
5. WHEN the companion downloader starts, THEN its transport deadline is 600 seconds after construction; a request that would start at or after it raises `transport deadline exceeded` without opening a connection.
6. WHEN an existing test's fixture is rejected by a changed check, THEN the implementer does exactly one of: (a) changes the fixture so it passes the new checks, keeping every assertion and the boundary the test exercises; (b) where invalid input is the test's purpose, keeps the input and changes the expected values to exactly what the plan's checks produce. This rule never permits removing a case, loosening an assertion or changing a check. The PR implementation notes list each change with the check that forces it, and the cold review and Codex review check each listed change. The boundary literals of `test_terminal_performance_accepts_complete_campaign_and_budget_boundary` change under requirement 17, not under this rule: decision 7145295306 changes the limit the test pins, and the PR description lists the change with that decision. Two fixture changes under this rule are already known: `test_error_body_is_not_read_at_the_deadline` and `test_error_body_stops_between_fragments_at_the_deadline` in `test_c5_companion_artifacts.py` set `clock[0] = 240` (lines 179 and 197) to reach the transport deadline; under (a) each becomes `clock[0] = 600`. With `DEADLINE = 600` and no fixture change, they fail and error respectively (observed in this session on the prototype).
