### 4.6 Cohort file upload log line

One line per cohort-file upload attempt, present on the supervisor's stderr before the next cohort-file upload starts and, for a failed attempt, before the failure is reported, in the existing format of `docs/operations/b10-abrupt-contract.md` "Failure report observability":

`b10_abrupt_stage {"role":"supervisor","stage":"cohort_file_uploaded","elapsed_ms":<timeline ms>,"ticks":<monotonic ticks>,"facts":{"name_index":<i>,"file_length":<bytes>,"elapsed_milliseconds":<ms>,"budget_milliseconds":30000,"upload_succeeded":<0 or 1>}}`

- Stage name `cohort_file_uploaded`, added to the contract's closed supervisor stage list.

That the watchdog exits without flushing held lines is an inference from `Environment.Exit` ending the process; it was not run.
- The line is operational. It carries no file name, path, payload or prose, adds no gate, failure name or budget, and changes no failure handling.
- Entry count: trial 7's supervisor wrote 32 stage lines on its successful path (counted by script from the first-pod log); eight more give 40, within the existing cap of 48 entries per process (`B10AbruptDiagnostics.MaximumTimelineEntries`).

## 5. Requirements

Publication:
- R1. WHEN the supervisor publishes the first instance, THEN it publishes the 15 members of 4.1 in that order, and each cohort file's published bytes are the local file's bytes whose `length` and `sha256` equal the binding descriptor in 4.1. WHEN a local cohort file is missing, unreadable, over its read limit, or differs in length or SHA-256 from its binding descriptor at publication time, THEN publication fails with the existing `b10_abrupt_publication_failed`, no later member is published, and `termination.json` is not published.
- R2. WHEN `abrupt-manifest.json` is built, THEN it carries `cohort_files` exactly as 4.2, and `termination.json` binds it by its existing `manifest` descriptor.
- R3. WHEN the successor loads its binding, THEN the accepted `files` member set is unchanged: the six names of `FIRST_FILES` without `journal.jsonl`. A binding that also carries any cohort file is rejected with the existing `b10_abrupt_successor_binding_invalid:receipt_changed`.
- R4. WHEN `b10_abrupt.py` accepts the first publication before successor release, THEN it downloads only `FIRST_FILES`, as today, and additionally requires: `cohort_files` has exactly eight entries with the names of `COHORT_FILES` in order; each entry's `length` is an integer within the 4.1 read limit and equals the length in its binding descriptor; each entry's `sha256` equals its binding descriptor's `sha256`. Failure raises `ValueError` at boundary `first_publication` with failure name `b10_abrupt_publication_failed`, and no successor is released.
- R5. WHEN `b10_abrupt.py collect()` runs and `predecessor-binding.json` exists, THEN, before it handles any `loadgen2` record, it downloads the eight `COHORT_FILES` from the first pod's prefix with the 4.1 limits into the first pod's collection directory, and requires each to match its `cohort_files` descriptor. A missing object records `b10_abrupt_publication_ambiguous`; a mismatch records `b10_abrupt_publication_failed`; both at boundary `first_cohort_publication`, and collection continues with the successor and Job collection as today. `collect()` then returns 1, as it does for every other recorded collection failure (`return int(failed)`, `b10_abrupt.py:667`), so the workflow's collect step fails.

Fatal capture:
- R6. WHEN the error handler installed on the first child's producer, the producer that the host's producer-creation path builds, receives an error callback, THEN one `native_error` message with the next `capture_sequence` reaches the channel's written stream, without blocking and without file or network I/O in the callback, and the same error is still captured by the existing evidence session. The channel's native error count, and the `native_error_count` the next seal object records, equal the highest `capture_sequence` assigned; no seal can record a count whose frames could follow a message the child sends after that seal. WHEN the enqueue fails, THEN the channel latches the existing gap `queue_full`. The successor and the supervisor process do not install this path. (Permitted example, not contract: one shared handler-building member used by the host and by T6.)
- R7. WHEN the supervisor receives `native_error`, before or after the kill request, THEN it validates the members of 4.3 and appends the frame to the journal.
