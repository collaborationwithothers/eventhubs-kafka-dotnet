## External contracts

The existing receipt and observations remain, with the following additive fixed lines. Record no address, resource ID, hostname, raw command output, raw exception, arbitrary environment value or arbitrary child text. New checkpoint records contain exactly `phase`, `stage`, `operation`, `status`, `reason`; phases are `setup`, `C0`, `transition`, `C1`, `cleanup`; status is `passed`, `failed`, `not_attempted` or `unavailable`; reasons are `none`, `check_failed`, `command_failed`, `invalid_data`, `observation_unavailable`. Fixed phase/stage/operation combinations are the table below, and no free text is projected. Records are atomic and bounded; unavailable recording must not turn a failed check into success. Existing runner/pod probe, settings and worker/binding observations remain intact. A missing checkpoint is `not_attempted` only where earlier failure proves execution was never reached; otherwise `unavailable`. Malformed, duplicate, contradictory, unrecognized or injected records project `unavailable`/`observation_unavailable`, without echoing content. A command exit 124 is not independently a proven timeout.

| Phase | Stage | Operations in execution order |
| --- | --- | --- |
| setup | bootstrap | guard, checkout, scenario, terraform, tools, sdk, inputs, namespace_name, login, azure_session, images |
| setup | infrastructure | cluster_init, cluster_start, cluster_plan, cluster_apply, ephemeral_init, initial_cleanup, ephemeral_plan, ephemeral_apply, dns, credentials, namespace_reset |
| C0, C1 | cluster_probe_idle, cluster_probe_active | apply, wait, logs, delete |
| C0, C1 | workload | runtime_binding, blob_baseline, idle_probe, start_line, start_line_binding, loadgen_start, active_probe, loadgen_end, loadgen_completion, loadgen_binding, delivery, verify, verify_binding |
| C0 | preservation | sentinel_capture, storage_creation, worker_delete, workers_absent |
| transition | off | input_validation, plan_create, plan_validation, apply, output_readback, shared_preservation, state_absence, namespace_absence, endpoint_absence, marker_write |
| transition | on | marker_validation, prior_absence, plan_create, plan_validation, apply, output_readback, shared_preservation, namespace_identity, endpoint_identity, dns, marker_remove |
| C1 | preservation | namespace_replaced, endpoint_replaced, shared_identity, storage_creation, sentinel_readback, phase_select |
| cleanup | teardown | worker_delete, ephemeral_destroy, cluster_stop, receipt_build, receipt_upload |

Only the smoke opts in to DNS observations; legacy callers retain identical DNS behavior and output. Existing per-service/per-perspective probes and per-service diagnostic observations provide more detail than these checkpoints; preserve their exact semantics. Each checkpoint means its named existing operation actually ran and passed or failed; never infer state from a later checkpoint alone. Setup and cleanup step outcomes may derive from GitHub step outcomes, validated against fixed allowed values. Upload occurs after the receipt is built: report its outcome in the existing final job summary, and mark receipt_upload unavailable in the receipt rather than claiming upload success before it happens. Receipt creation cannot report its own failure inside an uncreated receipt; the existing final report remains the fallback.

For Blob settings only, `logAnalyticsDestinationType` equal to `Dedicated` is `destination=passed`; absent or JSON null is `destination=unreported`, with record reason `destination_unreported` if all other checks pass. That record's status is `passed` for the smoke's settings configuration gate, but `unreported` is never called a confirmed Dedicated readback or ingestion. `AzureDiagnostics`, empty string, any other string or non-null non-string remain `destination=failed` and `destination_mismatch`. Event Hubs continues to require exactly `Dedicated`; missing/null/other fails. Both services still require exactly their existing target, workspace and enabled categories and metrics. Actual `StorageBlobLogs`, Event Hubs logs and metric ingestion remain separate live prerequisites for production approval and must not be inferred from any setting. Receipt validator accepts `unreported` only for Blob and validates status/reason consistency. Preserve explicit unsupported and malformed responses as failures.

## Requirements and test map

All tests use synthetic inputs and existing actual workflow/lifecycle execution seams, not static checks alone. WHEN a named check fails THEN emit its fixed failed checkpoint before exiting and retain prior passed checkpoints; no later operation is performed except the pre-existing cleanup paths. Preserve the initial wait, operation sequence and all other failure gates.

1. WHEN setup fails, THEN receipt includes every setup step, the failing step, and later skipped outcomes without interpolating raw GitHub data. `setup_receipt`: `ephemeral_plan=failure`, `ephemeral_apply=skipped`, malicious step outcome `private-token` -> fixed `failed`, `not_attempted`, `unavailable` respectively, with no token. Separately exercise absent Terraform, SDK, namespace and login step IDs.
2. WHEN existing DNS or TCP probe fails, THEN preserve the service, operation and existing fixed reason and no private details; no new network probes or calls. Existing probe failure matrix remains; add setup DNS distinction by Event Hubs vs Blob and `dns_error` vs `dns_mismatch`, using fixture answers `10.0.0.1` and `10.0.0.2` and expected status/reason only.
3. WHEN an existing workload, binding, delivery or sentinel check fails, THEN record the corresponding named checkpoint and preserve earlier results. `workload_failure_matrix`: inject individually failing start-line, failed loadgen-active check, absent/malformed ledger, zero delivered messages, mismatched run identity, failed verify, failed binding and mismatched sentinel; expected matching operation `failed/check_failed` (command returns nonzero -> `failed/command_failed`) and all prior checkpoints `passed/none`; later operations `not_attempted`; cleanup still runs. Cover both phases where applicable. Keep probe Job apply, wait, log collection and delete as separate fixed diagnostics, with failure in each represented as `failed/command_failed`, never raw output; preserve independent existing deletion behavior.
4. WHEN an off/on transition reaches input, plan, scope, apply, readback, preservation, absence, marker or DNS validation, THEN record the corresponding operation without changing the transition safety latch or command bounds. `transition_failure_matrix`: inject each named operation in each applicable phase once; first failure `failed/check_failed` or `failed/command_failed` according to its source, preceding checkpoints `passed/none`, later `not_attempted`; an off absence failure produces zero on-plan/apply calls; preservation failure blocks further activation. `124` from a child reports `command_failed`, not timeout.
5. WHEN shared storage/namespace checks or settings in C1 fail THEN preserve which identity, creation-time, sentinel or setting operation failed, without IDs. `c1_preservation_matrix`: changed namespace, endpoint, shared account, storage creation time and sentinel separately -> corresponding fixed operation fails and no later workload; unchanged values pass. Existing exact assertions remain.
6. WHEN settings readbacks are processed THEN apply the destination contract above in both C0 and C1. `destination_matrix`: Blob `Dedicated` -> `passed/none`; null and absent -> `passed/destination_unreported` and `destination=unreported`; `AzureDiagnostics`, `""`, `"Other"`, `false` -> `failed/destination_mismatch`; Event Hubs null or absent -> failed. With null and Blob target/workspace/categories mismatch, retain its existing failure reason instead of `destination_unreported`. Identical target and workspace, exact categories and metrics are required for success. Verify no raw setting or ID appears publicly, and real ingestion is never marked passed.
7. WHEN cleanup or receipt data is malformed THEN retain independent cleanup outcomes and valid prior records, never crash receipt generation due solely to a malformed observation. `receipt_integrity`: malformed timestamps, duplicate JSON keys, private-string injection, unknown key/status/reason, inconsistent status/reason and oversized file -> affected observation `unavailable/observation_unavailable`, no injected text, valid unrelated observations retained. Inject worker deletion failure, destroy failure and stop failure separately; all independent eligible cleanup attempts occur and final result fails. A missing source before attempted work is `not_attempted`, whereas missing after an attempted but interrupted stage is `unavailable`.
8. WHEN the mirror, test fixtures and deployed behavior are checked THEN keep byte equality, triggers, protected job, concurrency, Azure access, scientific gates, timeouts and existing assertion boundaries. Existing test fixtures rejected by the new checks must either satisfy them with every assertion and boundary preserved, or retain intentionally invalid input with the exact new expected rejection; record each in PR implementation notes.
